# Architecture Decision Records (ADR) - I-ITSM

This document records architectural, design, and technical decisions made during the project, documenting the context, alternatives considered, and rationale.

---

## ADR-001: Acceptance of `jakarta.persistence` Annotations on Domain Entities
- **Status**: Accepted
- **Context**: The domain layer must be clean and framework-independent. However, maintaining duplicate entity hierarchies (one pure domain POJO and one JPA entity) introduces substantial boilerplate mapping, bidirectional sync complexity, and potential dirty-checking inconsistencies.
- **Decision**: Allow standard `jakarta.persistence` annotations directly on domain entities while strictly prohibiting any `org.springframework.*` imports in `com.iitsm.domain`.
- **Alternatives Considered**:
  1. *Complete separation*: Pure POJOs in `domain`, separate `@Entity` classes in `infrastructure.persistence` mapped via MapStruct. (Rejected: excessive boilerplate for a 1-semester OOP project without architectural benefit, since `jakarta.persistence` is a vendor-neutral standard specification).
  2. *XML mapping (`orm.xml`)*: Pure POJOs mapped via external XML. (Rejected: brittle, difficult to refactor and maintain).
- **Reason**: Preserves high cohesion and readability of domain entities while keeping the domain completely free of Spring runtime dependencies.

## ADR-002: Pure-Java In-House NLP vs. External Heavyweight ML Libraries
- **Status**: Accepted
- **Context**: The system requires incident text classification, service matching, and duplicate detection.
- **Decision**: Implement TF-IDF vectorization, Cosine Similarity, and Multinomial Naive Bayes entirely in pure Java under `com.iitsm.domain.strategy`.
- **Alternatives Considered**:
  1. *External libraries (Smile, Weka, Apache OpenNLP)*. (Rejected: hides OOP implementation details, introduces dependency bloat, reduces viva defensibility).
  2. *External LLM APIs (OpenAI / Anthropic / Hugging Face)*. (Rejected: nondeterministic, requires API keys/network access, not self-contained for offline evaluation).
- **Reason**: Demonstrates core OOP principles (Strategy, Template Method, immutability, clean interface segregation), remains 100% explainable in code reviews and vivas, and executes deterministically without external dependencies.

## ADR-003: Injected `java.time.Clock` for Temporal Operations
- **Status**: Accepted
- **Context**: SLA tracking, aging calculation, ticket escalation, and simulation require precise temporal control and acceleration.
- **Decision**: Forbid direct calls to `Instant.now()`, `LocalDateTime.now()`, or `System.currentTimeMillis()` in business code; always inject `java.time.Clock`.
- **Alternatives Considered**:
  1. *Static mock frameworks (MockedStatic in Mockito)*. (Rejected: brittle, multi-threading issues, doesn't support interactive simulation).
  2. *Direct system time calls*. (Rejected: impossible to test SLA breaches deterministically or fast-forward time in demos).
- **Reason**: Enables rock-solid unit testing of SLA deadlines, pause-resume windows, and allows the `AdjustableClock` simulation engine to fast-forward time (x1, x60, x600).

## ADR-004: State Pattern with Stateless State Objects in EnumMap
- **Status**: Accepted
- **Context**: Incidents progress through 9 internal states with complex transition rules, action permissions, and SLA pausing.
- **Decision**: Implement the State Pattern where `Incident` delegates actions to `IncidentState` implementations. The state instances are stateless singletons registered in an `EnumMap<IncidentStatus, IncidentState>` within `IncidentStates`.
- **Alternatives Considered**:
  1. *Giant `switch(status)` / `if-else` blocks in services*. (Rejected: violates Tell-Don't-Ask and Single Responsibility Principle, fails OOP criteria).
  2. *Spring State Machine framework*. (Rejected: heavy dependency, leaks framework details into domain, overkill for defined linear/branching transitions).
  3. *State objects with stateful incident reference*. (Rejected: complicates JPA entity lifecycle and caching).
- **Reason**: Zero-allocation per transition, completely thread-safe, encapsulates transition logic cleanly, and enables trivial exhaustive transition matrix testing.

## ADR-005: Hexagonal Repository Ports & Adapters with Optimistic Locking
- **Status**: Accepted
- **Context**: Pure domain repositories must remain free of Spring dependencies, but the persistence layer must leverage Spring Data JPA, handle transactions, and guard against race conditions.
- **Decision**: Define pure Java repository ports in `com.iitsm.domain.repository` and implement them via Spring `@Component` adapters in `com.iitsm.infrastructure.persistence.adapter`. Catch all database errors and optimistic locking collisions (`@Version`) and translate them into domain `PersistenceFailureException`.
- **Alternatives Considered**:
  1. *Spring Data repositories extending domain interfaces directly*. (Rejected: couples domain to Spring Data types like `Pageable`, `Optional` Spring behaviors, and leaks framework infrastructure).
- **Reason**: Maintains strict architectural layer separation (`domain` never imports Spring), enables effortless switching between H2 for tests and PostgreSQL for production, and provides centralized exception translation.

## ADR-006: Stateless JWT Authentication with BCrypt and 5-Strike Lockout
- **Status**: Accepted
- **Context**: The system must provide role-based security across 3 personas (Employee, Technician, Admin) and enforce security boundaries (account lockout after 5 consecutive failed logins).
- **Decision**: Implement stateless JWT authentication via `jjwt` with BCrypt password hashing. Authentication failures track attempt counts and lock accounts on the 5th strike. Centralize 401 and 403 responses into consistent JSON objects.
- **Alternatives Considered**:
  1. *Stateful HTTP Sessions*. (Rejected: hard to scale, poor match for single-page applications and REST APIs).
  2. *OAuth2 / Keycloak*. (Rejected: requires external identity provider server setup, complicating standalone viva and grading evaluation).
- **Reason**: Lightweight, completely self-contained in pure Java, satisfies all security criteria, and returns clean, uniform JSON error contracts.

## ADR-007: Composite ML/Rule-Based Classification and Multi-Factor Priority Engine Architecture
- **Status**: Accepted
- **Context**: Incident intake requires automated category assignment, service association, multi-dimensional business priority scoring, duplicate correlation, and technician routing without external SaaS dependencies or non-deterministic behavior.
- **Decision**:
  1. Build a Composite Classifier combining high-precision Keyword matching with a pure-Java Multinomial Naive Bayes model trained on a 630-sample synthetic corpus with Laplace smoothing and log-space likelihood calculation.
  2. Implement a 6-Factor Composite Priority Engine using the Strategy Pattern ($\sum w_i \times s_i$, where $\sum w_i = 1.0$) coupled with policy override rule chains for security breaches, critical outages, and duplicate ticket avalanches.
  3. Implement swappable Technician Assignment Strategies managed via a thread-safe runtime registry (`AssignmentStrategyRegistry`), enabling zero-downtime routing strategy hot-swapping via Admin REST endpoints.
  4. Perform duplicate ticket detection using TF-IDF vector cosine similarity and Jaccard token similarity over a 72-hour sliding window, bidirectionally linking incidents when similarity exceeds 0.70.
- **Alternatives Considered**:
  1. *Rule-only keyword matching*: Lacks generalization on conversational descriptions or variations in user phrasing.
  2. *Single Naive Bayes model*: Can produce false positives on edge cases where explicit technical terms (e.g. "VPN", "PostgreSQL") clearly dictate the domain.
  3. *Static if-else technician routing*: Violates the Open/Closed Principle and prevents dynamic operational load balancing.
- **Reason**: The composite approach pairs deterministic technical precision with statistical generalization, ensures full transparency and explainability in priority scoring, provides runtime algorithm extensibility (OCP), and runs 100% offline in pure Java.

## ADR-008: Chain of Responsibility for Multi-Tier Escalation and Virtual Time-Accelerated Simulation
- **Status**: Accepted
- **Context**: SLA degradation and high-impact outages require progressive multi-tier escalation (Tier 1 Technician Reminder -> Tier 2 Team Lead Intervention -> Tier 3 System Administrator Action -> Tier 4 IT Operations Manager Breach Notification) governed by dynamic SLA thresholds (75%, 90%, 100% hard breach) and service criticality. Live evaluation, testing, and viva demonstration of temporal degradation requires accelerating time without modifying system clocks or sleeping.
- **Decision**:
  1. Implement the **Chain of Responsibility Pattern** (`EscalationHandler`, `AbstractEscalationHandler`) with 4 distinct tier handlers (`Tier4ItManagerHandler`, `Tier3SystemAdminHandler`, `Tier2TeamLeadHandler`, `Tier1TechnicianHandler`) assembled via `EscalationChainBuilder`.
  2. Implement `AdjustableClock` extending `java.time.Clock` with virtual epoch tracking, dynamic speed multipliers ($\times 1$, $\times 60$, $\times 600$), discrete fast-forward jumps (`fastForward(Duration)`), and state resets.
  3. Decouple SLA evaluation into domain model logic (`SlaTracker.evaluateStatus`, continuous risk scoring $0.0 \dots 1.0$), application service orchestration (`SlaService`), and scheduled background scanning (`SlaMonitoringScheduler`), publishing `DomainEvent.SlaWarning`, `DomainEvent.SlaViolated`, and `DomainEvent.IncidentEscalated`.
  4. Build a deterministic `SimulationService` orchestrating 5 core demonstration scenarios (S1 Happy Path, S2 Critical Outage & Multi-Tier Escalation, S3 Wrong-Domain & Triage Reassignment, S4 Duplicate Storm Avalanche, S5 Rejection Loop & SLA Clock Pausing).
- **Alternatives Considered**:
  1. *Monolithic if-else blocks in SlaService*: Violates the Open/Closed Principle and Single Responsibility Principle; adding or reordering escalation tiers requires modifying application service code.
  2. *OS system time manipulation or Thread.sleep in tests*: Flaky, dangerous, causes timeout in CI/CD, and cannot support interactive simulation speed adjustments.
- **Reason**: The Chain of Responsibility pattern isolates escalation criteria into independently testable classes with clear precedence; `AdjustableClock` provides instantaneous temporal simulation with zero thread blocking; and domain events seamlessly trigger notifications and audit logs across all tiers.

## ADR-009: Evidence-Based Triage Gating for Automatic Technician Assignment
- **Status**: Accepted
- **Context**: Tickets stopped being auto-assigned. Intake only assigns when classification confidence is at least 0.60; otherwise the ticket is flagged `needsTriage` and `UnassignedIncidentDispatcher` deliberately skips it, so only an admin can release it. The composite classifier capped confidence at 0.55 whenever the keyword classifier scored 0.50 or lower, which sent almost every short or conversational ticket to triage even when Naive Bayes agreed. Measured on the seeded corpus, Naive Bayes alone is badly overconfident on vague text (0.84 to 0.97 with zero keyword hits), so it cannot be trusted without corroboration.
- **Decision**:
  1. `KeywordClassifier` scores a single keyword hit found in the ticket title at 0.55 (`SINGLE_TITLE_MATCH_CONFIDENCE`); a single hit only in the description stays at 0.50.
  2. `CompositeClassifier` caps confidence at 0.55 (routing to triage) when: no keyword matched; or a single keyword matched outside the title; or models disagree and keyword support is below 0.60; or neither model reaches 0.60. All thresholds are named constants.
  3. `TechnicianAssignmentService`, `IncidentIntakePipeline` and `UnassignedIncidentDispatcher` handle only expected contention (`TechnicianOverloadedException`, `ObjectOptimisticLockingFailureException`), log a WARN when no technician has capacity, and let unexpected failures propagate. A lost lock race no longer aborts the whole dispatcher cycle.
  4. `findAvailableTechnicians` is null-safe for `availability_status` and `max_capacity` (a NULL capacity is treated as uncapped by the query; the domain `hasCapacity()` check then applies the mapper default of 5).
- **Alternatives Considered**:
  1. *Trust Naive Bayes when keywords abstain*: rejected after measurement; it auto-assigned vague and gibberish tickets to arbitrary teams.
  2. *Auto-assign any single keyword (no title rule)*: rejected; indistinguishable from ambiguous tickets such as F5 ("screen" only in the description), which the regression suite requires to go to triage.
  3. *Keep the original rule (single keyword goes to triage)*: rejected; clear tickets such as "VPN keeps dropping" would never auto-assign.
  4. *Let the dispatcher also release triage tickets automatically*: rejected as an unlisted feature; human triage stays the owner of low-confidence tickets.
- **Reason**: Evidence-weighted gating keeps the human-in-the-loop safeguard for genuinely ambiguous tickets while restoring automatic assignment for clear ones, keeps the policy inside the Composite/Strategy classifier so callers still depend only on `IncidentClassifier`, and replaces silent failure with explicit, observable handling (CLAUDE.md rules 9 and 15).

## ADR-010: Dedicated Read Model for the Admin Ticket Inspection Dialog
- **Status**: Accepted
- **Context**: Administrators need a full inspection view of one ticket (reporter, IT service and criticality, support team, SLA, explainable priority breakdown, notes, resolution, feedback, linked tickets, audit trail). `AdminIncidentView` already carries most of this, but it is also the row type of the Command Centre list, which maps every row with two user lookups and one audit query. Adding service and team lookups to it would make every table load pay for data only the single-ticket dialog needs.
- **Decision**:
  1. `GET /api/admin/incidents/{id}` returns a new `AdminIncidentDetailView`; the list endpoint keeps returning `AdminIncidentView`.
  2. The detail view embeds `AdminIncidentView` with `@JsonUnwrapped`, so every existing top-level JSON field is unchanged and current consumers keep working.
  3. A new read-only application service, `AdminIncidentDetailService`, assembles an application-layer `AdminIncidentDetail` (incident, reporter, assignee, IT service, support team, audit records). Access control is inherited by loading the incident through `IncidentLifecycleService`. `IncidentDtoMapper.toAdminDetailView` projects it to the web DTO.
  4. Support team resolution: the assignee's own team when assigned, otherwise the owning team of the incident's IT service. "Last modified" is derived from the newest audit record, because `Incident` has no modification timestamp of its own.
  5. Controllers stay free of repositories (ArchUnit rule A1); all lookups live in the application service and degrade to `null` for dangling references.
- **Alternatives Considered**:
  1. *Extend `AdminIncidentView` with the extra fields*: simplest, but adds N+1 lookups to the list endpoint.
  2. *Resolve the extra data in `AdminController`*: violates "controllers call one application service method" and the A1 architecture rule.
  3. *Separate endpoints per section, fetched lazily by the UI*: more round trips and more partial-failure states for no user benefit.
- **Reason**: A purpose-built read model keeps the list cheap, keeps the dependency direction `web -> application -> domain`, and is backward compatible. It follows the persona-specific DTO rule (CLAUDE.md rule 12) and Interface Segregation: callers get exactly the projection they need.

## ADR-011: Persist the Priority Factor Breakdown
- **Status**: Accepted
- **Context**: The Flyway schema has a `factor_contributions` table, but no JPA mapping existed. `IncidentMapper` rebuilt every loaded `PriorityDecision` with an empty factor list, so the explainable priority breakdown (a core requirement of the multi-factor priority engine, ADR-007) was computed at intake and then silently lost on the first save and reload. Administrators saw an empty matrix.
- **Decision**:
  1. Add `FactorContributionJpaEntity` mapped to the existing table (no new migration), owned by `IncidentJpaEntity` through `@OneToMany(mappedBy, cascade = ALL, orphanRemoval = true, fetch = EAGER)`.
  2. Use a `Set` ordered with `@OrderBy("id ASC")` rather than a `List`: the aggregate already fetches its notes eagerly as a `List` (a Hibernate bag), and a second eager bag raises `MultipleBagFetchException`. Generated identity ids preserve the calculator's factor order.
  3. `IncidentMapper` writes the breakdown on save and reads it on load. The domain `PriorityDecision` and `FactorContribution` value objects are unchanged, so the domain layer stays pure.
  4. Because `save` merges a freshly built entity, the factor rows are deleted and re-inserted on each incident save (at most six small rows). This is correct and bounded; avoiding it would require a natural key and a schema change.
- **Alternatives Considered**:
  1. *`@ElementCollection` of an embeddable*: same multiple-bag problem for a `List`, and the table already has a surrogate id column.
  2. *Recompute factors on read*: depends on mutable inputs (reporter history, ticket age), so it would not reproduce what was decided at the time.
  3. *Store the breakdown as JSON on the incident row*: loses queryability and duplicates the existing table.
- **Reason**: The explainability requirement is only met if the decision that was actually made is what administrators later inspect. Mapping the table that already exists is the smallest change that achieves this and keeps the aggregate boundary intact. Tickets saved before this change have no stored rows; the UI states that the breakdown was not recorded for them.

## ADR-012: Multi-Value Priority and Category Filters in Incident Search
- **Status**: Accepted
- **Context**: The Admin Command Centre can filter the incident directory by one priority and one category only. Administrators need to view, for example, P1 and P3 tickets together, or NETWORK and HARDWARE tickets together. The search path is `AdminController` -> `SearchService` -> `IncidentSearchPort` -> `IncidentSearchAdapter` -> `IncidentSpecifications`.
- **Decision**:
  1. `GET /api/admin/incidents` keeps the parameter names `priority` and `category` but binds them to `Set<Priority>` and `Set<IncidentCategory>`. Clients send repeated parameters (`?priority=P1&priority=P3`). A single value and the comma-separated form still bind, so existing callers are unaffected.
  2. `SearchService.IncidentSearchCriteria` and `IncidentSearchPort.SearchCriteria` carry `priorities` and `categories` sets. A null or empty set means "no filter".
  3. `IncidentSpecifications` gains `hasPriorityIn` and `hasCategoryIn` (`IN` predicates). Values within one filter are OR-ed, different filters stay AND-ed. The single-value `hasPriority` and `hasCategory` remain for existing callers and tests.
  4. Filter categories are the real `IncidentCategory` values. The legacy `ACCESS` option never existed in the enum and made the request fail (an unknown enum value surfaces as HTTP 500 through the global handler's catch-all), so it is not offered.
- **Alternatives Considered**:
  1. *Comma-separated single parameter (`priorities=P1,P3`)*: needs custom splitting and a new parameter name; Spring already binds repeated parameters to a collection.
  2. *Keep single-value fields and add parallel list fields*: two sources of truth per criterion and branching in the adapter.
  3. *Replace the single-value specifications*: needless churn in tests and any future caller; the new ones cover the single-value case anyway.
- **Reason**: Reusing the Specification pattern keeps the change inside the infrastructure and application layers, leaves controllers free of logic (rule 11), and is backward compatible with single-value requests.

## ADR-013: Department-Based Ticket Numbers (`DEPT-YEAR-SEQUENCE`)
- **Status**: Accepted (all 5 phases built: domain types, gap-free counters, generation, migration of existing tickets, staff display name, web display)
- **Context**: Ticket ids are `INC-` plus eight random hex characters (`IncidentFactory`). They are unique but carry no meaning, cannot be read out on a call, and give no sense of volume. Employees already have a `department`, and the id is the primary key of `incidents`, referenced by notes, audit records, links, notifications and technician workloads.
- **Decision**:
  1. The permanent ticket id is `<DEPT>-<YEAR>-<SEQUENCE>`, for example `FIN-2026-000142`. The department is the reporter's department (code of 2-4 uppercase letters), the year comes from the injected `Clock`, and the sequence is a zero-padded counter (minimum six digits, never truncated) kept per department code and per year. It restarts at `000001` each year.
  2. Only data that is known and fixed at creation goes into the id. Category, priority, team and assignee are excluded because they are assigned after creation and change later (reclassification, override, reassignment); an id that tracks them would have to be rewritten across every referencing table.
  3. `TicketNumber` (value object) formats and parses the id. `DepartmentCodeResolver` (Strategy) maps a free-text department to a code; the default `RegistryDepartmentCodeResolver` holds the eight seeded departments (ENG, FIN, HR, SAL, OPS, CSU, LEG, EXE), accepts new registrations at runtime, and falls back to the first three letters of an unregistered name, or `MISC` when the name has fewer than two letters. `TicketSequenceRepository` is the port for the counters.
  4. Priority appears only in a derived, staff-only display name, the current priority in front of the ticket id (for example `P2-FIN-2026-000142`, hyphens only, no spaces). `TicketDisplayName` builds it and is computed on every render of the technician and admin views (`displayId` next to the unchanged `id`); it is never stored, so an override is reflected at once and the id (the primary key referenced everywhere) never changes. `EmployeeIncidentView` has no such field, so hiding the ticket's priority from employees is still enforced by response type (rule 12). Lookups (`loadIncident` in `IncidentLifecycleService` and `AdminIncidentService`) and the admin text search accept either the plain id or the complete display name; a half-typed name such as `P2-FIN` is not guessed at. The text search now also matches the ticket id (it only searched title and description before).
  5. Existing tickets are renamed into the same format by Flyway migration `V4__rename_legacy_tickets` (a Java migration that delegates to `LegacyTicketRenamer`, so the same `RegistryDepartmentCodeResolver` and `TicketNumber` rules apply and the logic is testable). Department = the reporter's, year = the ticket's creation year (UTC), sequence = creation order within department and year, continuing after any numbers already issued. The ticket id is the primary key, so the migration re-creates the nine foreign keys that point at `incidents(id)` with `ON UPDATE CASCADE` (their delete rules are kept; constraint names are read from the JDBC metadata because they differ between PostgreSQL and H2), updates the three tables that hold an incident id without a foreign key (`technician_active_incidents`, `incident_linked_ids.linked_incident_id`, `audit_records`), rewrites ids quoted in system generated text (`notifications` subject and message, `audit_records.description`), and advances the counters. It runs in Flyway's transaction, so on PostgreSQL a failure rolls everything back and the application refuses to start rather than run on a half-renamed database. It does nothing on a database without old-style ids. Rejected: leaving old tickets as they are (two id formats forever), and copying each incident row to a new id (needs every column listed and breaks on future columns).
  6. Counters live in the `ticket_sequences` table (Flyway V3), one row per department code and year. The number is reserved inside the ticket's own transaction (`TicketSequenceRepositoryAdapter.next`, propagation MANDATORY): an atomic `UPDATE ... SET last_sequence = last_sequence + 1` followed by a read. The row lock queues concurrent callers, and if the intake rolls back the increment rolls back with it, so **the sequence never skips a number**. Only the first ticket of a department and year needs a separate short transaction to create the counter row (starting at 0, which is not an issued number); a lost creation race is ignored and the increment is simply repeated. The accepted cost: tickets of one department and year are issued one transaction at a time, because intake is a single transaction and the next ticket waits for it to finish. A side benefit is that a ticket raised right after a similar one now sees it for duplicate detection. Rejected: reserving the number in a separate transaction (no waiting, but a failed intake would leave a gap).
- **Alternatives Considered**:
  1. *Category in the id*: category is only a classifier guess at creation; triage and admin reclassification would leave a wrong prefix.
  2. *Priority frozen into the id, or an id that changes with priority*: goes stale on override or aging, or forces rewrites of every reference; either way it shows priority to employees.
  3. *Date-based `INC-YYYYMMDD-NNNN`*: no department, and a daily reset makes the counter meaningless.
  4. *Keep random ids and add a separate display number*: two identifiers per ticket to explain and search.
  5. *Database sequence per department*: needs DDL per new department, which breaks runtime extensibility of the department list.
- **Reason**: A short, meaningful, permanent id that can be read aloud, sorts by year and department, and is unique through a locked counter row. Keeping the id immutable preserves every reference and every id already quoted in emails, while the display name still gives staff the priority at a glance. The resolver and registry keep the department list open for extension without editing existing classes (OCP).

## ADR-014: Employees See Only Non-Sensitive Entries of a Ticket's Activity History
- **Status**: Accepted
- **Context**: `EmployeeIncidentView` is built so it cannot carry the ticket's priority, but its activity history was built from every audit record of the ticket. Audit descriptions such as "Calculated priority P3 (Score: 0.3975)" and "Priority changed from P3 to P1" therefore showed employees the priority and score, against the rule that employees never see priority (rule 12). Found while building the staff display name (ADR-013); it was already present before.
- **Decision**:
  1. `IncidentDtoMapper.toEmployeeView` keeps only audit entries whose action is in an allow-list (`EMPLOYEE_VISIBLE_AUDIT_ACTIONS`, expressed with the event classes so names cannot drift). Hidden: `PriorityCalculated`, `PriorityOverridden`, `SlaWarning`, `SlaViolated`, `IncidentEscalated` (priority, SLA state, escalation roles/reasons). Everything an employee saw before is still shown, including duplicate and reassignment entries, which do not reveal priority.
  2. The list is an allow-list, so a new event type is hidden from employees until someone adds it. A test requires every `DomainEvent` type to be either shown or in the hidden set, so adding an event forces that decision.
  3. Technician and admin views are unchanged; the stored audit records are unchanged.
- **Alternatives Considered**:
  1. *Deny-list of the priority events*: smaller diff, but any new event that quotes the priority would leak by default.
  2. *Store a separate employee-safe description on each audit record*: cleaner long term, needs a migration and changes every event type.
  3. *Hide duplicate and reassignment entries too*: they expose other ticket ids and a technician's reason, but they do not reveal priority, so they are left for a separate decision.
- **Reason**: Enforces the privacy rule at the one place that builds the employee projection, with a safe default for future events and no schema change.


## ADR-015: Store ticket text verbatim and record the admin's user id (stress audit C1, C2)
- **Context**: The 2026-10-31 stress audit found two critical defects. (C1) `Incident` HTML-escaped title and description in its constructor, and `IncidentMapper.toDomain` re-ran the constructor on every load, so text with `& < > " '` grew on each save until it failed the 120-character check; the ticket could no longer be edited and the SLA scan, which saves every active ticket in one transaction, failed for every ticket. Escaped text could also exceed the `VARCHAR(255)` title column (120 apostrophes -> 720 characters, HTTP 500). (C2) Admin `assign` and `acceptTriageSuggestion` stored the login email in `reassignment_requests.reviewed_by_admin_id`, a foreign key to `users(id)`, so every admin action on a wrong-domain ticket failed with HTTP 500 and the request stayed pending.
- **Decision**: (1) `Incident` keeps text exactly as entered (trimmed); escaping is done on output only, which the web client already does (`escapeHtml`). (2) `AdminIncidentService` passes `admin.getId()` to `ReassignmentRequest.approve`.
- **Alternatives**: keep escaping and add a reconstitution factory that skips it (does not fix the 255-column overflow and leaves `can&#x27;t` in classifier and duplicate-detection input); resolve the principal to a user id in every controller (larger change, deferred).
- **Consequences**: JSON, email and SMS now carry raw text, so any non-HTML consumer must escape for its own context. Rows already stored escaped keep their escaped text; a one-off unescape migration is needed for a persistent database (the dev and test H2 databases are rebuilt on start).
- **Audit finding C3 withdrawn**: the audit reported duplicates bypassing technician capacity. That is the documented design (`CorrectnessRegressionTest.F4`: a duplicate follows its parent's technician and uses no slot). The extreme counts (56 tickets on one technician) came from false duplicate clustering (unseen words get the lowest IDF in `TfIdfVectorizer`), which remains open.

## ADR-016: Duplicate Detection - Precision First, Recall Raised Within That Limit
- **Status**: Accepted (checkpoint 1, 2026-10-31)
- **Context**: The 2026-10-31 stress audit reported that duplicate detection merges unrelated tickets. Measurement (H1 Phase 0: 280 labelled pairs written for the purpose, plus a 168-ticket live replay through the unchanged pipeline) showed:
  1. Realistic tickets are almost never linked wrongly: 0 of 99 same-category different-fault pairs, 0 of 40 cross-category pairs, 5 of 5 correct live links.
  2. Two false-link patterns exist. (a) Tickets whose specific details are words absent from the training corpus: `TfIdfVectorizer` gives every unseen word IDF 1.0 while corpus words get 0.77-4.38, so hostnames, sites and codes barely count; 47 of 47 live false links were of this kind. (b) Near-empty generic tickets ("Strange behaviour today" / "Everything is sluggish"), 2 of 4 linked, which get worse once unseen words are weighted properly.
  3. Real duplicates are rarely caught: 9 of 87 natural paraphrases pairwise, 5 of 58 live (9%). Of the 53 live misses, 34 were compared and scored below 0.70; 17 were never compared because the reports got a different category or IT service.
  4. Smaller paths: a new ticket joins the cluster root even when it does not resemble the root (7 of 47 false links); when no open ticket shares service and category, the candidate list falls back to every ticket of that category ever raised (2 of 47).
- **Decision**:
  1. **Precision first.** A wrong link hides a ticket in another ticket's cluster, hands it to that technician without a capacity slot (by design, `CorrectnessRegressionTest.F4`) and counts towards the P1 avalanche rule; a missed duplicate only costs one separately handled ticket. When precision and recall conflict, precision wins.
  2. **Acceptance targets** (measured on the Phase 0 pair set and replay, re-run unchanged):
     - Pair set: precision >= 95 %; **zero** links among same-category different-fault, cross-category, near-empty generic and random-word template pairs; identical text and the S4 demo pairs 100 % linked; natural-paraphrase recall >= 59 % (today 10 %; amended from 60 % at checkpoint 3: the measured 59.8 % is one pair short, and a lower threshold would remove the 0.05 safety margin).
     - Safety margin: the chosen threshold sits at least 0.05 above the highest-scoring non-duplicate pair.
     - Live replay: zero false links among realistic and template tickets; recall at least 15 of 58 (today 5). The 17 never-compared misses are out of scope, which caps what this ADR can reach.
     - `F3` (five duplicates raise the parent to P1), `F4`, `DuplicateDetectionTest` and simulation scenario S4 keep passing; their numeric assertions may be updated to the new threshold, not their intent.
  3. **Scoring** (`TfIdfVectorizer`, domain layer): an unseen word gets the highest corpus IDF instead of 1.0; a word repeated in one ticket counts once. Exact formula chosen in Phase 2 against the pair set.
  4. **Content guard**: a pair links only if the two tickets also share at least a minimum number of content-bearing terms. The definition of "content-bearing" (domain vocabulary such as the classifier lexicon or corpus-known terms, rather than any rare word) is chosen in Phase 3 from data; required outcome: 0 of 4 near-empty generic pairs linked.
  5. **Threshold**: the fixed 0.70 is replaced by a calibrated value; provisional default 0.30, final value fixed at Checkpoint 3.
  6. **Candidates**: only open tickets (not RESOLVED, VERIFIED or CLOSED) created within the recency window and sharing service and category. The all-time `findByCategory` fallback is removed.
  7. **Clusters**: a new ticket joins the root's cluster only if it also meets the threshold against the root; otherwise it links to its best match alone. The root remains the ticket whose link count drives the avalanche rule.
  8. **Configuration** (no magic numbers): `iitsm.duplicates.similarity-threshold` (0.30 provisional), `iitsm.duplicates.min-shared-terms`, `iitsm.duplicates.recency-window-hours` (72). Bound in `infrastructure/config` and passed to `DuplicateDetectionService` through its constructor; the domain classes receive plain values and stay free of Spring.
  9. **Unchanged**: duplicates still use no technician capacity slot (F4); the avalanche rule; the 72-hour window length. Not addressed here: comparing across services within a category (option c), duplicates skipping the triage gate (audit H2), and concurrent duplicate reports returning HTTP 500 (audit H3).
- **Alternatives Considered**:
  1. *Fix only the unseen-word weight and keep 0.70*: closes the template false links but recall stays near today's level and near-empty generic tickets link more often.
  2. *Switch to the existing `JaccardSimilarity`*: best raw recall on the pair set (87 % at 95 % precision) but only at a threshold of 0.11, too close to the noise to be stable.
  3. *Also compare within the category across services (option c)*: addresses 9 of the 17 never-compared misses; deferred until measured on its own.
  4. *Embedding models or an ML library*: rejected; the stack is deliberately pure Java with no heavy ML dependencies.
- **Consequences**:
  1. More duplicates will be linked. Each linked duplicate rides its parent's technician without a capacity slot (F4) and adds to the parent's avalanche count, so higher recall increases uncounted technician workload and P1 escalations. Phase 5 reports the worst technician load; whether F4 should change is a separate product decision.
  2. `DuplicateDetectionTest` asserts scores >= 0.70; those assertions move to the configured threshold.
  3. Links already stored are not recomputed.
  4. All numbers come from a synthetic pair set written during the audit; real ticket data may move them, which is why the threshold is configurable.
- **Reason**: Removes the measured false-link paths, raises recall several-fold within a precision floor the product owner chose, keeps the existing duplicate behaviours (F3, F4, S4) intact, and makes every tuning value visible in configuration.
- **Outcome (2026-10-31, after phases 2-5)**: implemented as decided, with these measured results and deviations. Pair set (290 pairs, synthetic plus hand-adjudicated live pairs): recall 72 % at 98.9 % precision; natural paraphrases 52/87 = 59.8 % (target amended to 59 %, see above); 0 links among different-fault, different-category, near-empty and random-word pairs; one known false link (two different dock faults, score 0.33) accepted rather than raising the threshold to 0.34 (about 9 points of recall). Live replay: duplicates caught 5 -> 29 of 58, random-word templates linked 43 -> 0 of 45, largest cluster 8 -> 3. The 0.05 margin is thin (top genuine non-duplicate 0.2455); the threshold is configurable. Defaults applied without an explicit answer at checkpoint 4: cluster rule kept, the dock link accepted, F4 unchanged. Details: `docs/duplicate-detection-fix-summary.md`.

## ADR-017: Concurrent-Update Conflicts Return 409; Notifications Are Delivered After Commit (stress audit H3, H10 in part)
- **Status**: Accepted (checkpoint 1, 2026-10-31)
- **Context**: Two actions on the same row that overlap in time lose to optimistic locking (`@Version` on the incident and user rows), which is correct. The way the loss is reported is not. Phase 0 of the H3 work (six race scenarios, every request released together behind a barrier, 572 requests; every exception recorded with Java Flight Recorder) showed:
  1. 423 of 572 requests (74 %) returned HTTP 500. 419 `ObjectOptimisticLockingFailureException`s were recorded.
  2. **Conflicts thrown at commit** (252): acknowledge, admin assign, reject, verify, resolve. They are thrown after the service method returned, so no adapter can catch them; they reach the catch-all handler and become "An unexpected server error occurred".
  3. **Conflicts thrown inside a read query** (167): when intake updates the cluster root, the next query (`IncidentRepositoryAdapter.findByReporterId`) auto-flushes, throws, and the adapter wraps it as `PersistenceFailureException("Failed to retrieve incidents for reporter...")`, also a 500 with a misleading message.
  4. The only existing mapping to 409 (`IncidentRepositoryAdapter.save`, using `java.util.ConcurrentModificationException`) never fired: 0 of 419. `save` only merges; the version check happens at flush or commit.
  5. State stayed consistent (no ticket in an impossible state, no event recorded twice, audit records roll back with the transaction).
  6. **Notifications do not roll back.** `NotificationObserver` runs inside the transaction, so every lost commit race still sent its message: 233 "Incident Acknowledged" SMS were sent for 60 committed acknowledgements; the 173 extra are the 173 failed requests.
  7. In the real UI the 500 needs two writes within about 50 ms (browser test: 0 ms gap gave 500 in 3 of 3; gaps of 50 ms or more gave a clean 409). Realistic triggers are two staff acting at the same moment, a background job, and bursts of identical reports during an outage. Intake bursts are the worst case: 83 of 96 and 84 of 96 requests failed in the two storm scenarios.
- **Decision**:
  1. **Conflicts are reported as HTTP 409 with code `ERR_CONCURRENT_MODIFICATION`** and a plain message ("This record was changed by someone else at the same time. Reload and try again."). No entity internals in the message. Logged at WARN without a stack trace (an expected condition). No automatic retry in this ADR.
  2. A new `ConcurrentUpdateException extends IitsmException` (code above) replaces `java.util.ConcurrentModificationException` (CLAUDE.md rule 9). `IncidentRepositoryAdapter.save` throws it. `resolveStatus` maps it to 409.
  3. `GlobalExceptionHandler` maps Spring's `OptimisticLockingFailureException` (covers the commit path) directly, and unwraps `PersistenceFailureException` when its cause chain contains one (covers the query path). The 59 adapter catch blocks are not edited, because the wrapped exceptions keep their cause. The dead `java.util.ConcurrentModificationException` handler is removed.
  4. **Notifications are delivered after the transaction commits.** `DomainEventListener` gets `default boolean deferUntilCommit() { return false; }` (still a functional interface; the domain stays free of Spring). `NotificationObserver` returns `true`. A new infrastructure `TransactionAwareDomainEventPublisher` registers the immediate listeners (the audit trail, which must match the committed state) with the existing in-memory publisher, and hands the deferred listeners' work to one dedicated worker thread from `TransactionSynchronization.afterCommit` (amended, see the Amendment below: the first version ran them on the request thread in a `REQUIRES_NEW` transaction and could deadlock the connection pool). The worker opens a plain transaction per listener, catches and logs every exception (a failure after commit must never turn a successful request into an error), delivers in publishing order from a bounded queue (a full queue drops the new event with a warning and a counter, it never blocks a request) and drains its queue on shutdown. Nothing is handed over when the transaction rolls back. With no active transaction the event goes straight to the worker.
  5. **UI**: action buttons (technician Acknowledge, Start, Resolve and the other action buttons; employee Verify and Reject; admin Reassign and Override) are disabled while their request is in flight; a 409 `ERR_CONCURRENT_MODIFICATION` shows a friendly message and the list is refreshed; the list is also refreshed after any failed action. Asset cache-bust moves to `?v=3.5`.
  6. **Acceptance criteria**, measured with the Phase 0 scenarios (barrier, about 0 ms gap, 20 runs each) plus the browser checks:
     - zero HTTP 500 from a lock conflict;
     - every loser gets a 4xx with a stable code (`ERR_CONCURRENT_MODIFICATION` or the existing `ERR_INVALID_STATE_TRANSITION`);
     - the number of "Incident Acknowledged" notifications equals the number of committed acknowledgements (phantom notifications: zero);
     - ticket and event state stay consistent;
     - the 0 ms double-click in the real UI shows no red "unexpected server error" toast.
  7. **Intake bursts (decision pending, see below).** With 1-6 alone, an 8-way burst of identical reports still creates about one ticket and returns 409 to the rest. Options: accept it (a clear message; the employee resubmits); bounded retry of the whole intake (now safe because notifications are deferred, and the ticket number rolls back with the transaction, so numbering stays gap-free; but with a three-attempt cap it can rescue at most about three of eight simultaneous reporters, since each round lets one writer through); or serialize the linking step on the cluster root (a pessimistic lock or per-cluster lock, which could let all eight succeed, but needs a design that works on H2 and PostgreSQL and a spike). Phase 5 of the H3 plan measures the options; this ADR does not choose.
- **Alternatives Considered**:
  1. *Map to 409 only*: fixes the status code but leaves the phantom notifications measured above.
  2. *Retry everything*: unsafe while notifications fire before commit, and wasted effort for most single-ticket actions where a retry just produces a normal "already acknowledged" 409.
  3. *Spring `@TransactionalEventListener` with Spring's own event bus*: equivalent effect, but replaces the project's own `DomainEventPublisher` port and pulls Spring into every publisher of events.
  4. *Transactional outbox table*: durable delivery, but a schema change and a poller for a prototype whose event spine is in-memory.
  5. *503 instead of 409*: suggests a server fault; a conflict is a client-resolvable state.
  6. *Pessimistic locking everywhere*: removes the conflicts but adds waiting and deadlock risk to every write path.
- **Consequences**:
  1. Clients see 409 for lost races. The UI handles it; other API clients must treat `ERR_CONCURRENT_MODIFICATION` as "reload and retry".
  2. A notification can now be lost if the process dies between commit and delivery (no outbox). Before, it could be sent for a change that never happened. Accepted.
  3. Notification delivery now runs on a worker thread after the response is committed: a slow or failing mail server no longer delays the request or holds its database connection, and cannot fail it. A notification can arrive a moment after the response; tests that count messages wait for the worker (`awaitIdle`).
  4. Tests that expect notifications inside a rolled-back `@Transactional` test will see none; they must commit or assert differently (found by the full suite in Phase 3).
  5. `InMemoryDomainEventPublisher.getPublishedHistory()` still records every published event, including events of transactions that later roll back; it is a verification aid, not a delivery log. It also grows without bound (pre-existing; not changed here).
  6. Out of scope: the one-transaction SLA scan (rest of audit H10), the SLA tracker rules (H4-H7), the technician-capacity counter drift (1 of 24 technicians differed after the races; not investigated).
- **Reason**: Removes every measured source of HTTP 500 for lock conflicts with small, local changes, stops false notifications at their cause, and keeps retry and locking decisions open until measured.
- **Amendment (2026-10-31, found in the H3 phase 5 spike, fixed by redoing phase 3)**: the first implementation ran the after-commit listeners on the request thread, each in a `REQUIRES_NEW` transaction. Spring releases the request's JDBC connection only after the after-commit callbacks finish, so every committing request held one connection while asking for a second. With as many simultaneous commits as connections (the default pool has 10) every connection was held by a thread waiting for another, and the application stalled until the pool timeout; in `NotificationPoolStarvationRegressionTest` (pool of 3, eight simultaneous valid writes) one valid acknowledge returned HTTP 500. The phase 3 checks had missed it because they never had more than one successful commit at a time. Fixed by the single worker thread above, which needs at most one connection at a time and holds nothing while it waits, so no wait cycle can form. Verified live on the default pool: 40 simultaneous independent writes, all 200, slowest 167 ms. The same nested-connection pattern still exists elsewhere (technician assignment during intake, `TicketSequenceRowCreator`, `LoginAttemptService`, all `REQUIRES_NEW` while the caller holds a connection); 30 simultaneous distinct intakes on the default pool give 6 errors and 4 s latency, and none with a 60-connection pool. That is a separate, pre-existing defect, handled in phase 5.

## ADR-018: Ticket Intake Runs One Report at a Time per Instance (stress audit H3, intake bursts)
- **Status**: Accepted (implemented at checkpoint 5; awaiting the product owner's confirmation)
- **Context**: Phase 0 of the H3 work showed that simultaneous identical reports (the outage case) mostly failed: with ADR-017 alone, 7 of 8 reporters got a clean 409 and no ticket (12.5 % created in the 8-way bursts, about 19 % in a 24-way burst). The cause is structural: every report of the same outage updates the same cluster root, so all but one lose the optimistic-lock race. The phase 5 spike (a throwaway copy of the code, fresh application per mode, the same bursts of 96 / 144 / 96 requests) measured the options after the phase 3 defect was fixed:

  | Option | 8 with parent | 24 with parent | 8 first reports | Worst latency |
  |---|---|---|---|---|
  | Accept (409) | 12.5 % created | 18.1 % | 12.5 % | 160 ms |
  | Retry x3 | 50 % | 41.7 % | 41.7 % | 523 ms |
  | Retry x10 | 100 % | 89.6 % | 100 % | 1,158 ms |
  | One intake at a time | 100 % | 100 % | 100 % | 1,250 ms |
  | One at a time + retry x3 | 100 % | 100 % | 100 % | 1,220 ms |

  A second, older defect showed up in the same bursts: intake holds a database connection while it opens a nested `REQUIRES_NEW` transaction for technician assignment, and it takes a row lock on the department's ticket counter. With as many simultaneous intakes as pool connections (the default pool has 10) every connection is held by an intake waiting for another and the counter locks time out: 30 simultaneous distinct reports gave 24 tickets, 6 HTTP 500 and about 4.3 s latency; on a pool of 60 the identical burst gave 30 of 30 in 258 ms.
- **Decision**:
  1. A new `IntakeGate` (application layer) lets **one ticket intake run at a time inside an application instance**, first come first served (a fair lock). `IncidentService.createIncident` is no longer wrapped in a transaction of its own (`Propagation.SUPPORTS`); the gate encloses the intake pipeline's own transaction, commit included, so the next report starts after the previous one is visible.
  2. A report that cannot get its turn within `iitsm.intake.gate-timeout-ms` (default 30 s) gets HTTP **503** `ERR_SERVICE_BUSY` ("The system is busy handling other reports. Please try again in a moment."), a new `ServiceBusyException`.
  3. `iitsm.intake.serialized` (default `true`) switches the gate off.
  4. No automatic retry, no database-level locking.
- **Alternatives Considered**:
  1. *Accept the 409*: rejected, one ticket out of eight during an outage.
  2. *Retry the whole intake (x3, x10)*: x3 rescues at most about half; x10 reaches 90-100 % but multiplies database work under load and still loses reporters in the 24-way burst; it does not remove the connection starvation.
  3. *Gate plus retry*: no measurable gain over the gate alone.
  4. *Pessimistic lock on the cluster root (`SELECT ... FOR UPDATE`)*: would also work across instances, but the root is already loaded by the candidate query, so a lock needs a refresh-after-lock design that behaves the same on H2 and PostgreSQL; not needed for a single-instance deployment. It is the follow-up if the application is ever scaled out.
  5. *A bigger connection pool*: hides the starvation (30 of 30 on a pool of 60) but does not remove the cycle, and does nothing for the lost reporters.
- **Consequences**:
  1. Every reporter in a burst gets a ticket, and simultaneous duplicates are now correlated: in the live bursts all duplicates were linked to their parent (96 of 96 and 144 of 144; before, only the winner was created at all). This closes audit finding M9.
  2. Intake latency is additive: reports queue behind each other. On the real build, 8 simultaneous reporters: median 150 ms, slowest 294 ms; 24 simultaneous: median 832 ms, slowest 2.5 s; 30 simultaneous distinct: slowest 1.2 s. Each intake currently vectorises every open candidate, so its cost grows with the number of open tickets; at about 100 ms per intake a burst of roughly 300 simultaneous reports would reach the 30 s limit and start receiving 503.
  3. The gate protects **one application instance**. With several instances the optimistic lock stays the safety net and losers still get 409 (ADR-017).
  4. Callers that invoke `createIncident` from inside their own transaction (none in production; the simulation service) are serialised only for the intake work, not for their outer commit.
  5. `CorrectnessRegressionTest.F7` raced two near-identical reports for one technician slot. With intake serialised the second report sees the first and is linked to it as a duplicate (F4), which is correct, so the test now uses two reports that differ in content; its capacity assertions are unchanged.
  6. The nested-connection pattern remains in `LoginAttemptService` and `TicketSequenceRowCreator` (first ticket of a department and year only); they are outside ticket intake bursts and not changed here.
- **Reason**: The measured option that gives every reporter a ticket, removes the connection starvation by construction (one intake cannot starve the pool), needs no schema change, and keeps the optimistic lock as the safety net.

## ADR-019: A Paused SLA Clock Is Read at the Pause Instant (stress audit H4)
- **Status**: Accepted (implemented; awaiting the product owner's confirmation)
- **Context**: While a ticket waits for the employee (`PENDING_INFO`) the SLA clock is paused, but `SlaTracker.evaluateStatus` compared the real time against the old, not yet extended deadlines and only looked at the pause flag afterwards. The deadline moves only when the employee replies (`resumeClock`). The scheduled SLA scan therefore marked such tickets `BREACHED`, published `SlaViolated` (an SMS went out) and let the escalation chain alert team leads and admins. After the reply the deadline moved and the status flipped back to `ON_TRACK`. `getRiskScore` had the same flaw and `Tier2TeamLeadHandler` compared the raw `responseDueAt` itself.
- **Decision**:
  1. `SlaTracker` gets a private `effectiveNow(now)`: the pause instant while the clock is paused, the real time otherwise. `evaluateStatus` and `getRiskScore` read time only through it, for the response check, the resolution check and the elapsed ratio. The late `if (isPaused()) return;` is removed.
  2. A new `SlaTracker.isResponseOverdue(now)` answers "no response yet and past the response target on the SLA clock"; `Tier2TeamLeadHandler` asks it instead of comparing deadlines.
  3. `resumeClock` is unchanged: it still extends the deadlines by the paused window.
  4. The 0.75 and 0.90 thresholds become named constants.
- **Alternatives Considered**:
  1. *Early `return` while paused at the top of `evaluateStatus`*: rejected, it would hide a ticket that had already breached before it was paused and would not fix the risk score or the Tier 2 check.
  2. *Skip paused tickets in `SlaService`*: rejected, it puts a domain rule in a service (Tell, Don't Ask) and leaves the tracker wrong for every other caller.
  3. *Extend the deadlines continuously while paused*: rejected, it needs a timer or a write on every scan, and the audit trail would show deadline changes nobody made.
- **Consequences**:
  1. A paused ticket keeps the status it had at the pause (`ON_TRACK`, `AT_RISK`, `WARNING` or `BREACHED`) until the clock resumes; no `SlaViolated`, `SlaWarning` or escalation is produced for the waiting period.
  2. Tickets already wrongly marked `BREACHED` in a persistent database keep that status until the employee replies and `resumeClock` re-evaluates; no data migration was written.
  3. `IncidentUrgencyOrdering` still orders by `resolutionDueAt`, which for a paused ticket is the not yet extended deadline. Left alone on purpose; it affects queue order only.
  4. Out of scope: the other SLA tracker findings (H5-H7).
- **Reason**: One rule in the one class that owns the clock fixes the status, the risk score, the alerts and the escalations together, with no change to services or schema.

## ADR-020: The Confidence Triage Gate Applies to Duplicate Tickets (stress audit H2)
- **Status**: Accepted (implemented)
- **Context**: ADR-009 says humans own low-confidence tickets: below `iitsm.classification.min-confidence` (0.60) a ticket is flagged `needsTriage`, stays `CLASSIFIED` and `UnassignedIncidentDispatcher` skips it. `IncidentIntakePipeline` evaluated that gate only in the non-duplicate branch (`if (isDuplicate) ... else if (confidence >= min) ... else triage`). A ticket linked to a parent as a duplicate therefore never reached it: it was saved with `needsTriage=false`, copied the parent's technician if there was one, and otherwise sat `CLASSIFIED`, unassigned and not in triage, where the dispatcher assigned it. In the audit, OPS-2026-000019 (confidence 0.35) and OPS-2026-000020 (0.41) were linked to parents in triage and then auto-assigned, so a vague ticket reached a technician only because it resembled another vague ticket.
- **Decision**:
  1. The gate is evaluated once for every new ticket, before and independently of the duplicate branch: `confident = classResult.confidence() >= minConfidence`.
  2. A duplicate is always linked and always triggers the recalculation of its cluster root's priority (unchanged).
  3. A confident duplicate behaves as before (F4): it takes the root's technician if the root has one, and consumes no capacity slot.
  4. A low-confidence duplicate does not inherit the root's technician and is flagged `needsTriage`, whether or not the root is assigned.
  5. `processIntake` step 6 is split into `linkToParentCluster`, `refreshParentPriority`, `assignAutomatically` and `routeToTriage` (same logic, moved), which shortens the method (rule 15).
- **Alternatives Considered**:
  1. *Follow the parent's state (inherit its assignee or its triage flag)*: rejected, a low-confidence ticket would still reach a technician when its parent was assigned, and it makes the child's fate depend on a different ticket's classification.
  2. *Triage only when the parent is in triage*: rejected for the same reason; the gate is a property of the ticket's own text.
  3. *Move the gate into `DuplicateDetectionService`*: rejected, the confidence belongs to the classifier result held by the pipeline, and the service should only decide similarity.
  4. *Make the dispatcher skip duplicates of triage tickets*: rejected, it hides the ticket from humans instead of putting it in their queue.
- **Consequences**:
  1. A low-confidence duplicate now appears in the admin triage queue, linked to its parent. Triage volume rises slightly, and more so when the parent is already assigned.
  2. Tickets saved with the bug (`needsTriage=false`, possibly already assigned) are not changed; no data migration was written.
  3. When an admin assigns or reclassifies the parent, the triaged duplicate is not updated with it; it stays in the queue until an admin handles it.
  4. A confident duplicate of an unassigned parent (waiting for capacity) is still not flagged: it inherits nothing and is left to the dispatcher, as before; pinned by a regression test. A confident duplicate of a parent that sits in triage is likewise left to the dispatcher; that case is not pinned and is a known gap (CLAUDE.md section 7).
- **Reason**: One rule, "humans own low-confidence tickets", now holds for every ticket, in the one place that already owns the gate, without touching the duplicate detector, the state machine or the dispatcher.

## ADR-021: Reclassify Keeps a Ticket's History and Moves It to the Owning Team (stress audit H7; the reclassify door to H4)
- **Status**: Accepted (implemented; awaiting the product owner's confirmation)
- **Context**: `Incident.reclassify` rebuilt the SLA tracker from the creation time and replaced the priority decision. A manual override, the recorded response time, a paused clock and the verdict of a resolved ticket were lost, and the assignee stayed in the old team. Losing the paused clock is the H4 symptom through another door: a `PENDING_INFO` ticket that an admin reclassified started breaching while it waited for the employee. The failing-first tests `IncidentReclassifyTest` (5) and `ReclassifyStateRegressionTest` (6) pinned the contract.
- **Decision**:
  1. `Incident.reclassify` always changes category and service. If the ticket has a manual priority override, or its tracker already has a `resolvedAt`, it keeps its priority decision and tracker as they are. Otherwise it adopts the new decision and calls `SlaTracker.reanchor` on the existing tracker (response time and pause state survive); it creates a tracker only when there is none.
  2. `AdminIncidentService.reclassify` then calls `rerouteToOwningTeam`: an `ASSIGNED`, `ACKNOWLEDGED` or `IN_PROGRESS` ticket whose technician is not in the new service's owning team is released (technician capacity freed), returned to `CLASSIFIED` (`flagWrongDomain`, or the same direct reset that admin reassignment already uses for `IN_PROGRESS`) and offered to technicians of the owning team only; with no capacity it waits for the dispatcher.
  3. A `PENDING_INFO` ticket is not rerouted.
- **Alternatives Considered**:
  1. *Recalculate everything and only restore the lost fields in the service*: rejected, the rule belongs to the aggregate (Tell, Don't Ask) and would be missed by the other caller (`acceptTriageSuggestion`).
  2. *Reroute `PENDING_INFO` tickets too*: rejected, it returns them to `CLASSIFIED` with a paused clock that only the employee's reply (`PendingInfoState`) resumes, so the clock would stay paused for good. It contradicts the paused-clock test.
  3. *Fall back to any team when the owning team is full*: rejected, it would put the ticket straight back with a technician outside the owning team; the dispatcher already has the cross-team fallback.
- **Consequences**:
  1. A reclassify can no longer shorten, lengthen or restart an SLA that was earned or paused; a closed ticket keeps its priority and MET verdict.
  2. A `PENDING_INFO` ticket stays with its old technician after a cross-team reclassify; an admin can move it with `assign`, which resumes the clock.
  3. An `IN_PROGRESS` ticket loses its in-progress state when rerouted (same as an admin reassignment today).
  4. The paused duration is persisted in whole seconds (`paused_duration_seconds`) while the deadlines keep full precision, so after a pause cycle the deadline can differ from `created + target + pausedDuration` by under a second. Breach checks use the exact deadline, so no false breach; only a warning threshold can move by under a second per pause. Not changed: it would need a schema migration.
- **Reason**: One rule in the aggregate closes the last known way to lose a paused clock, and reroutes only where the state machine can carry the ticket through safely.

## ADR-022: A Rejected Fix Reopens the SLA Clock (stress audit H5)
- **Status**: Accepted (implemented; awaiting the product owner's confirmation)
- **Context**: `InProgressState.resolve` calls `SlaTracker.recordResolution`, which sets `resolvedAt` and the verdict (`MET` or `BREACHED`). `ResolvedState.reject` moved the ticket back to `IN_PROGRESS` and incremented the reopen count but never told the tracker. The reopened ticket kept `resolvedAt` and the first verdict: `evaluateStatus` returned at once on `MET`, `pauseClock` refused to pause (`resolvedAt != null`), and `resumeClock` did not extend the deadline. In all 10 rejection loops of the audit the status stayed `MET`, an info request paused nothing (0 s, deadline shift 0), and a reopened ticket could never warn, breach or escalate. The tickets customers are unhappy about were outside SLA monitoring.
- **Decision**:
  1. `SlaTracker.reopen(now)` undoes the resolution. If the ticket was never resolved it does nothing. Otherwise it credits the time the ticket waited in `RESOLVED` for the employee's verdict to `resolutionDueAt` (never a negative window), clears `resolvedAt`, resets the status and re-evaluates it at `now`. The recorded response time and the paused duration are kept.
  2. `ResolvedState.reject` calls `reopen(now)` (null-safe, like the other states) before the transition.
  3. Deadline rule: the original deadline stays, plus the verdict wait (option A below).
- **Alternatives Considered**:
  1. *Keep the original deadline and credit nothing*: rejected, the technician would be penalised for the employee's slow reply.
  2. *Start a fresh resolution window at the reject time*: rejected, a failed fix would get a clean slate and a repeat failure would look like a new incident.
  3. *Reset the tracker from a service (`IncidentLifecycleService.reject`)*: rejected, the rule belongs to the aggregate (Tell, Don't Ask) and any other caller of `Incident.reject` would miss it.
  4. *Make `evaluateStatus` ignore a stale `MET`*: rejected, it cannot tell a rejected resolution from a real one, and `resolvedAt` would stay set, so pausing would still fail.
- **Consequences**:
  1. A reopened ticket is scanned like any in-progress ticket: `AT_RISK`, `WARNING`, `BREACHED`, `SlaWarning`/`SlaViolated` and escalation all work again, and an info request pauses and shifts the deadline.
  2. A reopened ticket whose first resolution was late stays `BREACHED` (the extended deadline is still before `now`).
  3. Reports change as intended: MTTR skips a reopened ticket until its final resolution, and SLA compliance no longer counts it as `MET` while it is open.
  4. Tickets already rejected in a persistent database (`resolvedAt` set while `IN_PROGRESS`, status `MET`) are not repaired; no data migration was written. No schema change was needed (`resolved_at` is nullable).
  5. The audit trail records no separate SLA event for the reopen; the existing `IncidentReopened` entry is the record.
- **Reason**: One method in the one class that owns the clock puts reopened tickets back under monitoring, with no change to services, reports or schema.

## ADR-023: Reclassify Records What It Applied, Closes Open Requests and Routes by Category (follow-up to ADR-021, stress audit H7)
- **Status**: Accepted (implemented; awaiting the product owner's confirmation)
- **Context**: Reading ADR-021's code against a wider set of tests found four gaps: (1) `reclassify` and `acceptTriageSuggestion` always published `PriorityCalculated` with the recomputed priority, also when the ticket kept its manual override or its earned verdict, so the audit trail named a priority the ticket did not have; (2) a ticket handed to a new technician by `rerouteToOwningTeam` published no `IncidentAssigned`, so that technician was never notified and the assignment was not audited (`assign` does publish it); (3) a pending wrong-domain `ReassignmentRequest` stayed `PENDING` after a reclassify (`assign` and `acceptTriageSuggestion` approve it); (4) the reclassify dialog in `app.js` posts only `{category, reason}`, so `service` was null, the owning team was null and `rerouteToOwningTeam` returned at once: from the web app a reclassify never moved a ticket.
- **Decision**:
  1. `Incident.isPrioritySettled()` (was a private helper) is public. The service reads it before the call and publishes `PriorityCalculated` only when the recalculated decision was applied. Both `reclassify` and `acceptTriageSuggestion` use the shared helpers `recalculatePriority`, `slaPolicyFor` and `publishPriorityIfApplied`.
  2. `rerouteToOwningTeam` returns the technician it assigned; `reclassify` publishes `IncidentAssigned` for that technician after the save.
  3. `approvePendingReassignments` (one helper, now also used by `assign` and `acceptTriageSuggestion`) is called by `reclassify`.
  4. `owningTeamFor(service, category)`: the chosen service's owning team, else the team that handles the new category (`SupportTeamRepository.findByHandledCategory`). `AdminIncidentService` takes `SupportTeamRepository` in its constructor.
- **Alternatives Considered**:
  1. *Change `app.js` to send a service id*: rejected, the dialog has no service picker and inventing a service for a category would be a new feature.
  2. *Publish `PriorityCalculated` with the kept decision*: rejected, the event means "a priority was calculated and applied"; a kept override is already on record as `PriorityOverridden`.
  3. *Move the PENDING_INFO case too*: still rejected (ADR-021).
- **Consequences**:
  1. The audit trail of a reclassify matches the ticket. Tickets reclassified before this change may carry a `PriorityCalculated` entry that was never applied; not repaired.
  2. A reclassify from the web app routes the ticket. The ticket's service is unchanged when only a category is sent, so the service may belong to another team than the technician; the team queue follows the technician, the service's owner stays as it was.
  3. If two reclassifies overlap on one ticket, the loser gets 409 `ERR_CONCURRENT_MODIFICATION` (ADR-017); verified with 12 overlapping requests, 0 server errors.
- **Reason**: The aggregate already keeps history; the service must also tell the truth about what it did and must route on the information the real client sends.

## ADR-024: A Priority Override Re-anchors the SLA Deadlines (stress audit H6)
- **Status**: Accepted (core fix in commit `6cd386b`; credit field, V5/V6 migrations, tests and documentation added afterwards; awaiting the product owner's confirmation)
- **Context**: `Incident.overridePriority` replaced only the `PriorityDecision`. The `SlaTracker` kept the deadlines of the original priority, so a P4 ticket raised to P1 kept its 24 h deadline and stayed `ON_TRACK` long after a P1's 30 minute target, while its staff display name already read `P1-...`. Warnings, breaches and escalations for the ticket followed the old priority. A second gap showed once the tracker moved with the override: the override changes the status inside the admin's transaction, so the next SLA scan saw "no change" and never published `SlaViolated` or `SlaWarning` (no audit entry, no notification).
- **Decision**:
  1. `Incident.overridePriority(newPriority, adminId, reason, slaPolicy, now)` takes the `SlaPolicy` of the new priority and calls `SlaTracker.reanchor(policy, now)`. A policy for a different priority is rejected (`ValidationException`) before anything changes; a null policy changes the decision only.
  2. `SlaTracker.reanchor` delegates to `updatePolicy` (deadlines = `createdAt` + new targets + time already paused, status re-evaluated) unless the ticket has `resolvedAt`; a resolved ticket keeps its deadlines and its `MET`/`BREACHED` verdict.
  3. Deadlines are measured from the ticket's creation, not from the override: a ticket that is already older than the new priority's target is `BREACHED` at once. The recorded response time and the paused duration are kept; a currently paused ticket stays paused.
  4. `AdminIncidentService.overridePriority` looks the policy up (`SlaPolicyRepository.findDefaultByPriority`, factory default as fallback, as `reclassify` does), remembers the status before the call and, after the save, calls `SlaService.announceTransition(incident, previousStatus, now)`. That method is the event publishing the scan already did (`SlaWarning` for `AT_RISK`/`WARNING`, `SlaViolated` for `BREACHED`, nothing when the status did not change), extracted so both callers share it. The scan uses it too.
- **Alternatives Considered**:
  1. *Restart the clock at the override time*: rejected, an old ticket raised to P1 would look fresh and the real age would be hidden; the override would also be a way to extend a deadline.
  2. *Keep the old deadlines*: rejected, that is the bug.
  3. *Let `AdminIncidentService` set the tracker's deadlines*: rejected, the tracker owns its deadlines (Tell, Don't Ask), as with H4 and H5.
  4. *Not evaluate the status in `reanchor` and let the next scan announce the change*: rejected, the status and the audit trail would lag by a scan interval (60 s by default), and the domain method would carry a hidden precondition.
  5. *Publish the SLA event from the domain or from a new listener*: rejected, publishing is an application concern, and a second code path would risk double events.
- **Consequences**:
  1. Raising a ticket shortens its deadlines and can breach it immediately; lowering it lengthens them and can clear a breach. Each status change publishes exactly one SLA event; repeated overrides to the same priority publish none.
  2. The employee still sees nothing: the view has no SLA fields and the audit allow-list (ADR-014) hides `PriorityOverridden`, `SlaWarning`, `SlaViolated` and `IncidentEscalated`.
  3. A ticket reopened by a rejected fix (ADR-022) gets a credit on `resolutionDueAt` for the time it waited for the verdict. Recomputing from creation would have dropped it, so `SlaTracker` now keeps the credit in its own field (`creditedDuration`, `reopen` adds to it, `updatePolicy` adds it back: deadline = `createdAt` + target + paused + credit). It applies to the resolution deadline only and is stored in whole seconds (Flyway `V5__sla_credited_duration.sql`, column `credited_duration_seconds`, default 0), like the paused duration, so a deadline can differ from the exact sum by under a second. Credit earned before V5 was not recorded and counts as 0; an override or reclassify of such a ticket still drops it.
  4. Tickets overridden before this change are repaired by the Java migration `V6__repair_override_deadlines` (`OverrideDeadlineRepairer`). It rewrites a ticket only if it is unresolved, overridden, its audit trail names the priority it had before its first override, and its stored deadlines still equal `created` + that priority's target + paused time (5 s tolerance). Then both deadlines are set to the current priority's policy (the `sla_policies` row, else the factory default). Everything else is left alone: a deadline the repair cannot explain (extra credit, a reclassify, no audit entry) is never rewritten. The status column is not touched, so the next scan re-evaluates it and announces a breach. Idempotent; tested on H2 and on a real PostgreSQL. A ticket that already holds credit in its deadline no longer equals the old target, so it is skipped and the repair cannot strip credit.
  5. The override and the tracker change commit in one transaction with the announcement; if the announcement throws, the whole override rolls back.
- **Reason**: One method on the class that owns the clock moves the deadlines with the priority, and one shared method tells the rest of the system, with no change to the schema, the reports or the web app.

## ADR-025: Test Isolation Rule, Fast Test Lane and Measurement Harnesses (remaining-defects plan, Phase A)
- **Status**: Accepted (2026-11-05)
- **Context**: Before fixing the remaining stress-audit defects, the test suite had to be able to show regressions reliably and quickly. Four problems: (1) `IncidentRepositoryAdapterTest` failed when run alone (it relied on another class seeding the shared in-memory H2 database first; audit item P5). Running every class in its own JVM found a second one: `SimulationControllerTest.testRunScenarioS1` is `@Transactional` and seeded inside the test transaction, but ticket intake assigns technicians in a separate transaction (`TechnicianAssignmentService`, `REQUIRES_NEW`) that cannot see uncommitted rows, so scenario S1 got no technician when the class ran first. (2) A full run takes about 5.6 minutes, two thirds of it in the three embedded-PostgreSQL classes. (3) About 1,600 WARN lines per run come from e-mail notifications failing in test classes that run no SMTP server, and bury real warnings. (4) The later phases change classification, routing and capacity accounting, and there were no recorded baseline numbers to measure them against.
- **Decision**:
  1. **Isolation rule**: every test class must pass alone. It is checked by running the whole suite with one JVM per class (`-DforkCount=1 -DreuseForks=false`), which gives every class an empty in-memory database. A class that needs the company seed seeds it itself; a `@Transactional` class whose code under test opens its own transaction seeds in `@BeforeTransaction`, so the seed is committed before the test transaction starts.
  2. **Tags and the fast lane**: `@Tag("postgres")` on `LegacyTicketMigrationPostgresTest`, `OverrideDeadlineRepairPostgresTest` and `TicketNumberingPostgresRegressionTest`; `@Tag("benchmark")` on the report-only benchmarks. The Maven profile `fast` (`mvn -o test -Pfast`) excludes both tags and skips JaCoCo. Phase gates still run the full `mvn clean verify`.
  3. **Test logging**: in the test profile `EmailChannel` and `NotificationRouter` log at ERROR. Their failure isolation is tested by `NotificationSystemTest`, and the mail tests assert on received messages, not on log lines.
  4. **Benchmarks (report only)**: `ClassificationBenchmarkTest` (held-out `test_tickets.csv` and the new `classification/audit_examples.tsv`; accuracy, triage rate, share of tickets routed to the team of their true category, general-service fallbacks; runs on its own in-memory database `benchmarkdb`) and `DuplicateBenchmarkTest` (link rate per labelled group, precision, the known false link, the highest non-duplicate that passes the content guard, and how many paraphrase links can be lost before `DuplicatePairSetTest` fails). Reports go to `target/benchmarks`. They assert only that their data loaded; phases F and G turn the numbers into acceptance checks.
  5. **Capacity check helper**: `testsupport.CapacityInvariant` compares each technician's stored slots with the tickets naming the technician and reports phantom slots, missing slots and orphaned duplicates (a linked ticket whose cluster holds no slot, the F4 trade-off). Phase B uses it for its invariant test and its repair endpoint.
- **Alternatives Considered**:
  1. *Always run one JVM per class*: catches order dependencies on every run, but doubles the run time (about 11 minutes); kept as a phase-gate check instead.
  2. *A separate database per test class*: the strongest isolation, but changes all 45 Spring test classes; not needed while the rule above holds.
  3. *`@DirtiesContext`*: slower, and does not help: the in-memory database outlives the context (`DB_CLOSE_DELAY=-1`).
  4. *Silence the mail warnings by running an SMTP server for every class*: more moving parts for no test value.
  5. *Assert the benchmark numbers now*: the thresholds are product decisions for phases F and G (D14, D15, D17).
- **Consequences**:
  1. The fast lane does not run the PostgreSQL migration tests; a phase gate must.
  2. The classification benchmark starts one extra Spring context (about 9 s).
  3. Six other `@Transactional` classes still seed inside the test transaction (`SearchServiceTest`, `AdminIntelligenceEndpointsTest`, `AuthControllerTest`, `EmployeePrivacyControllerTest`, `NotificationControllerTest`, `ReportControllerTest`). They pass alone today; if a later change makes their code under test open its own transaction, they need the `@BeforeTransaction` pattern. Phase B removes `REQUIRES_NEW` from technician assignment, which removes most of that risk.
  4. The shared SMTP port remains; the mail tests already count only their own messages, so a late message from another class cannot fail them.
- **Reason**: Later phases change behaviour on purpose; a suite that passes in any order, a two-minute lane for routine work and recorded baselines make an unintended change visible.

## ADR-026: A Capacity Slot Is Saved Together With the Assignment It Belongs To (remaining-defects plan, Phase B; stress audit H8, M6, P2)
- **Status**: Accepted (implemented 2026-11-05)
- **Context**: A technician's capacity slot (`technician_active_incidents`) was taken by `TechnicianAssignmentService.tryAssignTechnician` in a transaction of its own (`REQUIRES_NEW`), which committed at once. The ticket's own change (assignee, status) committed later in the caller's transaction. Whenever the caller then failed, the slot stayed and the ticket did not get the technician: a phantom slot that no ticket accounts for, permanently reducing the technician's capacity. Phase A's capacity check and four new regression scenarios (`CapacityAccountingRegressionTest`) reproduced four ways in:
  1. **Intake**: a failure after the assignment (any later rollback of the intake transaction) lost the reporter's ticket and kept the slot.
  2. **Reclassify (audit M6)**: a reclassify with an unknown service id reserved a slot at the new team's technician, then failed at commit on the `incidents.service_id` foreign key: `PHANTOM_SLOT|TECH-SEC-1|ENG-2026-000001`, a security technician holding a slot for a VPN ticket that still belonged to a network technician.
  3. **Accept-suggestion (audit H8)**: on an already assigned ticket it reserved a slot, `incident.assign` then threw, and a broad `catch (Exception)` swallowed it: HTTP 200, slot kept, assignee unchanged.
  4. **Dispatcher**: one transaction around the whole cycle with a committed slot per ticket inside it; a failure on one ticket rolled back every ticket's assignment of that cycle but not their slots.
  Because ticket numbers are given back on rollback (gap-free, ADR-013), a phantom slot can later name a *different* ticket that receives the same number. This is the most likely cause of the "1 of 24 technicians" mismatch the audit saw after its race runs (a hypothesis supported by the reproductions above; not proven for the original runs).
- **Decision**:
  1. `tryAssignTechnician` has propagation **MANDATORY**: it saves the slot in the caller's transaction and fails loudly when there is none. It still absorbs only `TechnicianOverloadedException`.
  2. New `TicketDispatchService.dispatchOne(incidentId, actor)` (one waiting ticket, one transaction): picks candidates, takes the slot, assigns, saves, publishes `IncidentAssigned`. Outcomes `ASSIGNED`, `NOT_WAITING`, `NO_CAPACITY`, `NOT_ASSIGNED`. The rule "classified, unassigned, not in triage" moved into the aggregate as `Incident.isAwaitingAutomaticAssignment()`.
  3. `UnassignedIncidentDispatcher` is no longer transactional itself: it calls `dispatchOne` once per ticket. It is a scheduler boundary: a lost race is logged as WARN, any other failure as ERROR with its stack trace, and the cycle goes on. Its schedule is configurable (`iitsm.dispatcher.interval-ms`, `initial-delay-ms`, defaults unchanged); the test profile sets one hour, because every cached test context runs its own background dispatcher against the shared database.
  4. **Intake in two steps.** `IncidentIntakePipeline.processIntake` saves the ticket (transaction 1) and returns an `IntakeResult` (confident and not a duplicate means "awaiting automatic assignment"). `IncidentService.createIncident` then calls `dispatchOne` as transaction 2, still inside the `IntakeGate` (ADR-018), so reports do not race each other for one technician's last slot. A failure in step 2 is an isolation boundary after the point of no return (the ticket is committed): a lost race is logged as WARN, anything else as ERROR, the ticket stays `CLASSIFIED` for the dispatcher and the reporter gets it. A duplicate that rides its parent's technician (F4) is assigned in step 1, because it takes no slot.
  5. `AdminIncidentService.acceptTriageSuggestion` no longer catches `Exception`. The reclassify reroute and accept-suggestion run in the admin's one transaction, so a failure rolls the slot back with the rest; a technician conflict is HTTP 409 and the administrator retries.
  6. **Capacity check and repair.** Domain: `CapacityAudit` (pure) and `CapacityDiscrepancy` (kinds `PHANTOM_SLOT`, `MISSING_SLOT`, `ORPHANED_DUPLICATE`, each with its own repair), `IncidentStatus.holdsTechnicianSlot()`. Application: `CapacityReconciliationService` reads technicians and tickets in one REPEATABLE_READ snapshot (without it, a ticket resolved between the two reads would look like a missing slot and a repair would create a leak). Web: `GET /api/admin/capacity/reconcile` reports, `POST` repairs: a phantom slot is released, a missing slot is taken when the technician has room, an orphaned duplicate is only reported (linked duplicates carry no slot by design). `CapacityStartupAudit` logs one INFO or WARN line at start-up (`iitsm.capacity.startup-check`, default on, off in the test profile). Repair is a manual administrator action, never automatic.
  7. **Linked duplicates keep using no slot (decision D1, F4 unchanged).** `GET /api/admin/technicians` gains `carriedDuplicateCount` next to `activeIncidentCount`; the web app does not show it yet (Phase J).
- **Alternatives Considered**:
  1. *One transaction for everything, including intake (D2-A)*: simplest, but a conflict on the technician's row at commit would roll back the reporter's ticket (HTTP 409 for a new report). Rejected for intake and the dispatcher; adopted for admin actions, where the administrator can simply retry.
  2. *Keep `REQUIRES_NEW` and give the slot back when the caller rolls back (D2-B)*: the give-back can itself fail or never run when the process dies, and done inline it would hold two connections at once (the pool-starvation pattern of ADR-017 and ADR-018).
  3. *An automatic repair job*: hides the cause of a leak; the explicit endpoint keeps it visible.
  4. *Pessimistic locks on technician rows*: removes the optimistic conflicts but adds waiting and deadlock risk; the optimistic conflicts are already handled cleanly.
  5. *Derive the slots from the tickets instead of storing them*: removes the possibility of a mismatch, but is a schema and design change across the capacity model, out of scope here.
- **Consequences**:
  1. A new ticket is visible as `CLASSIFIED` and unassigned for a few milliseconds before step 2 assigns it. Notifications keep their order (the events of transaction 1 are handed over after its commit, those of transaction 2 after its own).
  2. A lost race in step 2 delays the assignment by up to one dispatcher cycle (30 s); before, the intake transaction could fail altogether.
  3. **Behaviour that changed on purpose:** accept-suggestion on an already assigned ticket now fails with HTTP 409 (`InvalidStateTransitionException`) and changes nothing; before, it answered 200, kept a phantom slot and left the ticket unchanged. Phase C2 adds the explicit status rule (decision D4).
  4. Inside a `@Transactional` test, intake and assignment both run in the test transaction (the propagation is REQUIRED), so tests no longer need the committed-seed workaround for assignment (it stays harmless).
  5. **Not changed**: the first-ticket counter row (`TicketSequenceRowCreator`) and the login counter (`LoginAttemptService`) still open a nested transaction (audit P1, deferred or Phase E); an employee's reject still takes the slot back and fails with 409 when the technician is full; the capacity check cannot tell a slot leaked before this fix from a slot that is simply wrong today, it only reports and (on request) repairs.
  6. The unknown service id of M6 is still stored until Phase C1 turns it into a 404; its slot leak is closed here.
- **Reason**: The slot and the assignment describe one fact, so they are saved in one transaction; where the caller must not lose its own work (the reporter's ticket) the ticket is committed first and the assignment is a retryable second step. Making the propagation MANDATORY turns a silent mistake into an immediate error. The mutation checks (REQUIRES_NEW put back, one transaction around the dispatcher cycle, the broad catch put back, a failure after intake rethrown) each make tests fail, and the audit and repair make any future leak visible and fixable without database surgery.

## ADR-027: Bad Client Input Is a 4xx With a Stable Error Code, Converted at Its Source (remaining-defects plan, Phase C1; stress audit M5, M6, M7, M8)
- **Status**: Accepted (implemented 2026-11-05)
- **Context**: `GlobalExceptionHandler` mapped the `IitsmException` hierarchy, unreadable JSON, bean validation, security errors, lost write races and, for everything else, a catch-all that answers HTTP 500 and logs an ERROR with a stack trace. Errors the client causes but that reach the catch-all were therefore reported as server faults:
  1. **Standard web errors**: an unknown enum value or an unparseable date in a request parameter (`/api/admin/incidents?priority=P9`, `category=PRINTER`, `status=LIMBO`, `fromDate=yesterday`), a number that is not a number, a wrong HTTP method (`GET /api/auth/login`, found in Phase A: `SecurityRegressionTest.S8` sends it), and the `/favicon.ico` every browser asks for (one 500 and one ERROR log per browser session, because the page declares no favicon).
  2. **`IllegalArgumentException` thrown on client input**: `Enum.valueOf` in `AdminController` (accept-suggestion `{"category":"PRINTERS"}`, designation `OVERLORD`), `AssignmentStrategyRegistry.setActiveStrategy("NOPE")`, `SimulationService.runScenario("S99")`, `AdjustableClock.setSpeedMultiplier(-5)`.
  3. **Silently accepted bad input**: reclassify and accept-suggestion looked the service up with `orElse(null)`, so an unknown `serviceId` was stored and failed on the foreign key at commit (HTTP 500, audit M6); accept-suggestion without a category forced `SOFTWARE` (audit M7: an AUTHENTICATION ticket became SOFTWARE and went to a database technician); `POST /api/simulation/advance?minutes=-30` moved the clock from 11:04 to 10:34 (audit M8), and `minutes=9223372036854775807` overflowed into a 500.
  Found while testing: `Round3RegressionTest.N1` posted the service id `SRV-NET-001`, which is not in the seeded catalogue; it only passed because the unknown id was ignored.
- **Decision**:
  1. **New handlers** in `GlobalExceptionHandler`, each with a stable code and the offending parameter named in `fieldErrors`: `MethodArgumentTypeMismatchException` -> 400 `ERR_INVALID_PARAMETER` (for an enum, also the valid values, also when the parameter is a `Set` of the enum); `MissingServletRequestParameterException` -> 400 `ERR_MISSING_PARAMETER`; `HttpRequestMethodNotSupportedException` -> 405 `ERR_METHOD_NOT_ALLOWED` with an `Allow` header; `HttpMediaTypeNotSupportedException` -> 415 `ERR_UNSUPPORTED_MEDIA_TYPE`; `NoResourceFoundException` -> 404 `ERR_NOT_FOUND`. They log at DEBUG (the domain errors keep their WARN). Client text echoed in a message is cut at 50 characters (`EnumText.echo`).
  2. **Everything else is converted where the error arises, to the exception that already maps to a status**, and there is **no global `IllegalArgumentException` handler**. `EnumText.parse` (`IncidentCategory.fromText`, `Designation.fromText`) throws a `ValidationException` that names the field and lists the valid values; `AssignmentStrategyRegistry`, `SimulationService.runScenario` and `AdjustableClock` throw `ValidationException`; `SlaService.evaluateIncident` throws `ServiceNotFoundException` for a missing ticket. An `IllegalArgumentException` that reaches the catch-all is a bug and stays a logged 500.
  3. **Decision D6**: `AdminIncidentService.findServiceOrFail` makes an unknown `serviceId` a 404 (`ServiceNotFoundException`, `ERR_SERVICE_NOT_FOUND`) in both `reclassify` and `acceptTriageSuggestion`; a request with no service id is unchanged. Nothing is changed, saved or published before the lookup fails.
  4. **Decision D5**: a missing category in accept-suggestion (no body, or none in it) means "the classifier's suggestion", the same one the triage queue shows (`AdminIncidentService.suggestedCategory`); an explicit category always wins; an unknown one is a 400. The `SOFTWARE` default is gone from the controller (no business rule there, CLAUDE.md rule 11).
  5. **Decision D7**: `SimulationService.advanceClockByMinutes` accepts 1 to `MAX_ADVANCE_MINUTES` (ten years; the bound also keeps the arithmetic from overflowing) and the clock's `fastForward` refuses zero and negative durations, so the advance endpoint can no longer move time backwards; a speed of zero or less is a 400. `resetToRealTime` and `setTimeTo` are unchanged: reset stays a demo tool that may move the clock back.
- **Alternatives Considered**:
  1. *A global `IllegalArgumentException` -> 400 handler*: the smallest change, but it would report every programming error as the client's mistake and hide real bugs; two guard tests fail when it is added.
  2. *Extend `ResponseEntityExceptionHandler`*: covers every Spring MVC exception at once, but its handlers for unreadable bodies and bean validation clash with the existing ones and would change their JSON; larger than the cases that occur.
  3. *Bean Validation annotations on the request parameters (`@Min`, `@Max`)*: needs a handler for `HandlerMethodValidationException` and would not protect the clock below the controller.
  4. *Declare a favicon in `index.html`*: a UI change with an asset version bump, and it would leave every other missing resource a 500.
  5. *Case-insensitive enums in the JSON deserializer*: changes deserialization for the whole API; `fromText` keeps the existing trim and upper-case behaviour only where it was already used.
- **Consequences**:
  1. Every example the audit observed, and the wrong-method case, now ends as a 4xx with a stable code (`InputValidationRegressionTest`, 14 scenarios, 11 of which failed before the change).
  2. A browser's favicon request is a quiet 404; the ERROR log line per browser session is gone.
  3. **Behaviour that changed on purpose**: accept-suggestion without a category uses the classifier's suggestion instead of `SOFTWARE`; an unknown service id is refused instead of stored or ignored (`Round3RegressionTest.N1` now uses the real service `SVC-VPN`); an advance of zero, a negative number or more than ten years is refused; `fastForward(zero)` is refused.
  4. The web app needs no change: it shows the server's `message`, and none of its requests are affected (asset version stays `?v=3.5`).
  5. **Known limits**: reset and `setTimeTo` can still move the clock back (decision D7); a missing ticket reuses `ServiceNotFoundException`, whose text reads "IT Service '...'" (existing wording); an empty `{}` body on the designation endpoint is still a silent 200 no-op; 406 and similar rarer client errors still reach the catch-all.
- **Reason**: Reporting the client's mistake as a client error is what lets the caller correct it and keeps the server log for real faults. Converting at the source keeps each message specific (field, bad value, valid values) and keeps the catch-all honest: anything it still receives is a bug.

## ADR-028: Which Administrator Actions Are Allowed in Which Status (remaining-defects plan, Phase C2; stress audit L5, H8; CLAUDE.md section 7 item 3)
- **Status**: Accepted (implemented 2026-11-05)
- **Context**: Three administrator actions had no status rule, because none had been decided:
  1. **Priority override** was accepted on any ticket, also on a RESOLVED, VERIFIED or CLOSED one. ADR-024 already made the tracker keep a resolved ticket's deadlines and verdict, so the override changed nothing but the stored priority and the staff display name (`P1-...`): a closed ticket showed a priority that never applied to it.
  2. **Reclassify** is accepted in every status. ADR-021 made it only relabel a finished ticket (an override and a resolved ticket's priority and tracker are kept); that was true but not pinned for CLOSED.
  3. **Accept-suggestion** worked on any ticket: on an assigned ticket it reserved a slot and then failed or was swallowed (audit H8, slot leak closed in ADR-026), and on a ticket that merely waited for the dispatcher it assigned it behind the dispatcher's back. It also never published `IncidentAssigned`, so the technician it assigned was not notified and the assignment was not audited.
- **Decision** (decision D4):
  1. `IncidentState.allowsPriorityOverride()` (default true) is false in `ResolvedState`, `VerifiedState` and `ClosedState`. `Incident.overridePriority` asks its state first and throws `InvalidStateTransitionException` (HTTP 409 `ERR_INVALID_STATE_TRANSITION`, "Action 'overridePriority' is not allowed when incident is in state 'RESOLVED'..."). The rule lives in the state classes, not in a service (CLAUDE.md rule 2). A ticket that was never classified still reports the missing classification first.
  2. Reclassify stays allowed in every status; from RESOLVED on it only changes category and service, with no priority, SLA or routing effect. Pinned by `StatusRulesRegressionTest` for a CLOSED ticket.
  3. `AdminIncidentService.acceptTriageSuggestion` is only for a ticket in triage: held back by the intake (`needsTriage`) or with a pending wrong-domain request. Otherwise `NotInTriageException` (HTTP 409 `ERR_NOT_IN_TRIAGE`, naming the ticket and its status). A confident ticket that waits for capacity is the dispatcher's, not the administrator's. On success it publishes `IncidentAssigned` (as the administrator) like the other assigning paths.
- **Alternatives Considered**:
  1. *Refuse both override and reclassify from RESOLVED on*: reports and filters need a closed ticket to be re-filed, and the relabel has no side effect.
  2. *Allow everything and document it*: a closed ticket would keep a priority that nothing honours.
  3. *The status check in `AdminIncidentService`*: the rule would be missed by any other caller of `Incident.overridePriority`.
  4. *Reuse `InvalidStateTransitionException` for accept-suggestion*: its message talks about the state's allowed actions (the technician's), which is misleading for "this ticket is not in triage"; a precise exception costs one small class.
- **Consequences**:
  1. **Tests changed on purpose**: `PriorityOverrideSlaRegressionTest.resolvedTicketKeepsItsSlaVerdict` and `PriorityOverrideSlaEventsTest.resolvedTicketStaysMetAndSilent` overrode a resolved ticket and asserted that the verdict stayed; they now assert the refusal (and, for the second, that nothing is recorded). The invariant they protect is unchanged. `SlaTracker.reanchor` still refuses to move a resolved ticket's deadlines; it is now only a second line of defence for the override.
  2. A resolved ticket's priority can no longer be corrected by an administrator; relabelling the category still can.
  3. An administrator who used accept-suggestion on a waiting ticket gets 409 and should wait for the dispatcher or use assign. The web app never called accept-suggestion.
  4. The error handler maps `NotInTriageException` to 409 like the other state conflicts.
- **Reason**: The aggregate knows which of its states are final, so the rule is expressed where the states live; the one action that decides on behalf of the intake is limited to the tickets the intake handed over.

## ADR-029: The Wrong-Domain Workflow (remaining-defects plan, Phase C2; stress audit M10 sub-gaps a, b and c)
- **Status**: Accepted (implemented 2026-11-05)
- **Context**: A technician who finds out that a ticket belongs to another team can flag it ("wrong domain"); it returns to the pool, the technician is excluded from it and an administrator decides. The audit and Phase 0 found these gaps (sub-gap d, closing the request on reclassify, was fixed by ADR-023):
  1. **(a)** Only ASSIGNED and ACKNOWLEDGED tickets could be flagged. A technician usually finds out while investigating, when the ticket is IN_PROGRESS and the only way out was to ask an administrator. The administrator's own reassignment and the reclassify reroute bypassed the state machine for IN_PROGRESS (`clearAssignee` plus `transitionTo(CLASSIFIED)`).
  2. **(b)** A flagged ticket appeared twice in the administrator's triage queue (as `LOW_CONFIDENCE`, because the flag sets `needsTriage`, and as `WRONG_DOMAIN`), and the web card labelled every entry "Flagged Out-of-Scope", with "Requesting Tech" empty for the low-confidence ones.
  3. **(c)** The model has `ReassignmentRequest.reject` but no endpoint used it, and `approve`/`reject` could be called on an already decided request.
  Found while testing: `IncidentLifecycleService.flagWrongDomain` released the slot of the user who flags, not of the technician who holds the ticket. A team lead may flag a ticket on a technician's behalf; the technician then kept a phantom slot that the Phase B capacity check reports (`PHANTOM_SLOT`).
- **Decision** (decision D8):
  1. **(a)** `InProgressState` allows `flagWrongDomain`: the assignee is released and the ticket returns to CLASSIFIED; notes, the recorded first response and the SLA clock stay. PENDING_INFO still cannot be flagged (ADR-021: the paused clock would never resume). Because the action shows up in `allowedActions`, the web app offers "Flag Out-of-Scope" on IN_PROGRESS cards with no code change. `AdminIncidentService.assign` and `rerouteToOwningTeam` release ASSIGNED, ACKNOWLEDGED and IN_PROGRESS tickets through the state machine; only PENDING_INFO keeps its explicit reset (resume the clock, then clear the assignee), as before.
  2. **(b)** `getUnifiedTriageQueue` returns one entry per ticket. A ticket with a pending request is a `WRONG_DOMAIN` entry (technician, reason, request time and the new `requestId`); other tickets in triage stay `LOW_CONFIDENCE`; every entry carries the classifier's suggestion. If a ticket somehow has two pending requests the newest is shown. The card is drawn per type, shows "Flagged by technician" or "Low confidence", the current category and the suggestion. The two empty `catch (Exception ignored)` blocks of the old code became one logged WARN (the queue still lists the ticket, without a suggestion).
  3. **(c)** `POST /api/admin/reassignments/{requestId}/reject` with `{"reason": "..."}` (administrator only): the ticket goes back to the technician who flagged it (ASSIGNED, slot taken, that technician removed from the ticket's exclusions, triage flag cleared), the request becomes REJECTED with the administrator as reviewer, the reason is added to the ticket as an internal note by the administrator, and `IncidentAssigned` is published (audit and notification to the technician). All in one transaction (ADR-026): a technician without free capacity gives HTTP 409 and nothing changes. A request that is not pending is HTTP 409 `ERR_REQUEST_NOT_PENDING` (new `ReassignmentRequestNotPendingException`; `ReassignmentRequest.approve` and `reject` now refuse a decided request). The web app shows a "Reject request" button on `WRONG_DOMAIN` cards only, with a dialog that requires the reason. Asset version `?v=3.6`.
  4. **At most one pending request per ticket** follows from the state machine and needs no extra code: only a ticket that holds a technician can be flagged, and every administrator action that takes the ticket out of triage (assign, reclassify, accept-suggestion, reject) closes its pending requests. `WrongDomainWorkflowRegressionTest.atMostOnePendingRequestPerTicket` pins it.
  5. The flag releases the slot of the **holder** of the ticket (`IncidentLifecycleService`).
- **Alternatives Considered**:
  1. *Store the rejection reason in a new column of `reassignment_requests` (Flyway V7)*: the reason would sit with the request, but the technician looks at the ticket, and a note needs no migration. The request still records who rejected it and when.
  2. *Reject only closes the request and leaves the ticket in the queue (D8 option B)*: the technician would have given the ticket up and nobody would own it.
  3. *A new domain event for the rejection*: `EmployeeAuditTrailPrivacyTest` requires every event to be classified for the employee history; `IncidentAssigned` already carries the facts.
  4. *A separate "reassign" state action for the administrator instead of reusing `flagWrongDomain`*: cleaner names, but a new action in every state class and in the transition table for no behavioural gain; the existing code already used `flagWrongDomain` for the administrator's reassignment of ASSIGNED and ACKNOWLEDGED tickets.
  5. *Hide the second entry in the web app only*: the API would keep returning duplicates.
- **Consequences**:
  1. **Tests changed on purpose**: `IncidentStateTransitionTableTest.testInProgressStateTransitions` (IN_PROGRESS now allows `flagWrongDomain`; the parameterized illegal-transition test follows each state's allowed actions and needed no change); the three static-asset tests that pin the version (`?v=3.6`).
  2. A technician can now give a ticket back at any point of the investigation except while waiting for the employee; the administrator's reject sends it back to him, which can ping-pong a ticket between them (each step is audited, notes keep the history).
  3. A reject of a request whose ticket was meanwhile handled by other means is impossible: those paths close the request first, so the second call is HTTP 409.
  4. `TriageQueueItemDto` gained `requestId` (additive JSON).
  5. **Known limits**: the rejection reason is only on the ticket (internal note), not on the request; a PENDING_INFO ticket cannot be flagged by the technician (the administrator can still reassign it); a team lead's flag excludes the lead, not the technician who held the ticket, from the ticket (unchanged).
- **Reason**: The state machine already knew how to release a ticket from three states; the fourth follows the same rule. One triage entry per ticket is what an administrator decides on, and a way to say "no, this is yours" closes the workflow instead of leaving flagged tickets that only the administrator can move.

## ADR-030: A Response Breach Is Remembered (remaining-defects plan, Phase D; stress audit M1; decision D9-A)
- **Status**: Accepted (implemented 2026-11-05)
- **Context**: `SlaTracker` kept one status for two targets. The scan marked a ticket BREACHED when no response had come by the response deadline, but `recordResponse` only stored the time: a later `evaluateStatus` looked at the response only while `respondedAt` was null, so (1) a ticket the scan had marked BREACHED went back to ON_TRACK, AT_RISK or WARNING as soon as it was acknowledged, (2) a late response followed by a timely resolution ended `MET`, and (3) every `SlaViolated` event said `RESOLUTION_TARGET`, even when the response target was missed. A second door to the same symptom: a technician's late acknowledge happens inside the technician's transaction, so the scan afterwards saw "no change" and never announced the breach.
- **Decision** (D9-A, no migration):
  1. The response verdict is **derived from stored fields**: the response target is missed when `respondedAt` is after `responseDueAt`, or when there is no response yet and the SLA clock has passed `responseDueAt` (`SlaTracker.responseBreached`). The status is the worse of the response and the resolution verdicts: `evaluateStatus` returns BREACHED for a response breach before it looks at the resolution, and `recordResolution` ends BREACHED (not MET) when the response was late.
  2. `updatePolicy` (override, reclassify) adds the paused time to the response deadline only while there is no response. After the response, later waits for the employee must not make a late response look on time. The policy change itself still moves the response deadline (ADR-024 kept: a ticket raised to P1 after a 7 minute response is late, lowered to P3 it is on time).
  3. `SlaTracker.breachedTarget(now)` returns `RESPONSE` (checked first) or `RESOLUTION` with the labels `RESPONSE_TARGET` / `RESOLUTION_TARGET`; `SlaService.announceTransition` puts the label into `SlaViolated`.
  4. `IncidentLifecycleService.acknowledge` and `resolve` call `announceTransition` with the status from before the action, as the priority override does (ADR-024), so a breach first noticed by the action is announced once, and one the scan already announced is not repeated.
- **Alternatives Considered**:
  1. *A stored `response_breached` flag (Flyway V7)*: simple to read, but a second source of truth next to `respondedAt` and `responseDueAt`, one more column to keep right across override, reclassify and reopen, and a migration for old rows. The derived verdict is always consistent with the deadlines.
  2. *Two statuses on the tracker (response status and resolution status)*: the API, the escalation chain and every view read one `SlaStatus`; two would change all of them for no use the product has.
  3. *Announce only from the scan and run the scan after every action*: the scan is a one-minute poll; the action already knows the transition.
  4. *Fix only the label and leave the verdict alone*: the wrong status is what the administrator and the escalation chain see.
- **Consequences**:
  1. **Tests changed on purpose**: `SlaTrackerPauseModelTest` and `SlaTrackerReopenModelTest` (the models now remember at which working time the response happened and judge it against the current policy; both failed against the new rule until updated), and the seven tests that construct `SlaService` by hand (new constructor argument, see ADR-031).
  2. A ticket that was acknowledged late before this change and is still active (status forgiven back to ON_TRACK, AT_RISK or WARNING) is BREACHED at the next scan, with one `SlaViolated` `RESPONSE_TARGET` and the escalation that follows. Tickets already MET stay MET (not rewritten).
  3. `Tier2TeamLeadHandler` and the escalation chain are unchanged: they read the status and `isResponseOverdue`.
  4. **Known limits**: the label of an event that is announced late (the first scan after a restart) is derived from the tracker's state at that moment, not from the moment of the breach; a ticket that missed both targets is announced as `RESPONSE_TARGET` only (the first miss); a policy change does not re-check the resolution verdict of a resolved ticket (ADR-024).
- **Reason**: The status is a function of the stored times and the policy. Deriving the verdict keeps it correct across every path that already moves those times, and needs no schema change.

## ADR-031: The SLA Scan Runs One Transaction Per Ticket (remaining-defects plan, Phase D; stress audit H10)
- **Status**: Accepted (implemented 2026-11-05)
- **Context**: `SlaService.evaluateAllActiveIncidents` loaded every active ticket and evaluated them all inside the one class-level transaction. A ticket that failed (a listener that threw, a lost write race, a data problem) rolled back the evaluation, the saved statuses and the escalations of every other ticket, the scheduler logged one ERROR, and the same ticket failed again on the next scan: all breaches stayed unannounced for as long as one ticket was broken. The transaction also stayed open for the whole scan.
- **Decision** (D9):
  1. The scan asks the repository for the **ids** of the active tickets (`IncidentRepository.findActiveIncidentIds`, one cheap query) and evaluates each in its own transaction through an injected `TransactionOperations` (`SlaService` gets it as a constructor argument; Spring Boot provides it as the `TransactionTemplate` bean). The method itself is `SUPPORTS`, so no transaction wraps the loop.
  2. A failure of one ticket is caught at that boundary and logged: a lost write race as WARN (expected under contention, `ConcurrencyConflicts`), anything else as ERROR with the stack trace. The ticket is evaluated again by the next scan. A ticket that was closed or deleted between the id query and its turn is skipped. The result list holds the tickets that were evaluated.
  3. **No nested transaction**: each ticket's transaction starts with nothing open (no `REQUIRES_NEW`; item 19 of CLAUDE.md section 7 is not made worse). A caller that already has a transaction (a test) simply joins it.
  4. The single-ticket `evaluateIncident(id)` keeps the class-level transaction.
  5. `iitsm.sla.scan-interval-ms` is set to one hour in the `test` profile (like the dispatcher and the capacity check), so a background scan never changes a ticket a test is asserting on; tests call the scan themselves.
- **Alternatives Considered**:
  1. *A separate bean with a `REQUIRES_NEW` method per ticket*: needs a second bean and a call through the proxy, and `REQUIRES_NEW` inside an outer transaction is what ADR-026 removed from assignment.
  2. *A `@Transactional` method called on `this`*: self-invocation is not proxied, so it would silently run without a transaction.
  3. *Catch per ticket inside the one transaction*: a persistence exception marks the transaction rollback-only; the surviving tickets would still be undone at commit.
  4. *Batches of N tickets per transaction*: fewer transactions, but a failure still undoes up to N-1 innocent tickets.
- **Consequences**:
  1. The scan loads each ticket on its own (one `findById` per ticket instead of one query for all of them): a longer scan on a large board, but every transaction is short and no connection is held for the whole scan.
  2. A ticket that keeps failing logs one ERROR per scan (once a minute) until it is fixed; it no longer hides the others.
  3. The escalation of a ticket is part of that ticket's transaction: if the escalation fails, the status change rolls back with it and both are retried at the next scan.
  4. `SlaMonitoringScheduler` is unchanged (its catch remains as the last line of defence for the id query).
  5. **Tests**: `SlaServiceScanTest` (9), `SlaScanIsolationRegressionTest` (2); the seven hand-built `SlaService` sites pass `TransactionOperations.withoutTransaction()`.
  6. **Known limits**: a ticket evaluated while another transaction changes it can still lose the write race (it is retried at the next scan).
- **Reason**: The unit that must succeed or fail together is one ticket (its status, its events and its escalation). Making that the transaction boundary isolates failures without a nested transaction.

## ADR-032: Access Rules for the Team Queue and for Notifications (remaining-defects plan, Phase E; stress audit M2 and M3; decision D10)
- **Status**: Accepted (implemented 2026-11-06)
- **Context**: Two reads and writes skipped the application-layer access policy that CLAUDE.md section 1 rule 13 requires.
  1. **M2, the team queue.** `IncidentLifecycleService.getTeamQueue` loaded every ticket (`findAll`) and kept those whose IT service the actor's team owns. It never asked `AccessPolicy` about a ticket, so a technician saw the tickets, and the internal notes, that colleagues were working on, although `Technician.canViewIncident` says a technician may see only their own tickets and the unassigned tickets of their team.
  2. **M3, notifications.** `POST /api/notifications/{id}/read` took a notification id and marked it read for whoever called it. Any signed-in user who knew an id could change another user's notifications.
- **Decision** (D10):
  1. `getTeamQueue` keeps the roles of the old rule and applies the access policy to every ticket: an **administrator** gets everything; a **team lead** the tickets of the services the team owns (and their own); a **technician** the tickets assigned to them and the unassigned tickets of their team. The candidates come from two queries (`IncidentRepository.findByServiceIdIn` for the services of the team, `findByAssigneeId` for the actor) instead of loading every ticket; each candidate then passes `AccessPolicy.canViewIncident` (new non-throwing form of `enforceCanViewIncident`, same rule). An employee is still refused.
  2. `NotificationService.markDelivered(notificationId, actorId)` marks a notification only for its recipient. For anyone else the notification does not exist: `ServiceNotFoundException`, HTTP 404 `ERR_SERVICE_NOT_FOUND`, nothing changed. An id that was never issued gives the same answer, so the endpoint is no oracle for ids.
- **Alternatives Considered**:
  1. *Filter in the web controller*: the rule would sit outside the application layer (rule 11 and 13) and the next caller would repeat the bug.
  2. *Return 403 for someone else's notification*: it confirms that the id exists. 404 for both cases leaks nothing.
  3. *Keep the whole-team view for technicians (as it was)*: a colleague's notes are internal; the Team Lead tab already gives the whole team to the role that needs it.
  4. *A new repository query "unassigned tickets of the team"*: the policy decides, and the candidate set (team services plus own tickets) is small; one rule in one place.
- **Consequences**:
  1. **Tests changed on purpose**: `Round3RegressionTest.testVpnIncidentCreationAndTechnicianQueue` asserted that the ticket appears in the team queue of `tech.network@`, whichever network technician got it; it now asserts it for the assignee and for the team lead. The Team Lead tab of the web app lists only unassigned and at-risk tickets (unchanged), so the lead's whole-team view is the API (`/api/technician/team-queue`).
  2. The technician's "Team Queue" button now shows the unassigned tickets of the team plus their own; its label says so ("Unassigned Team Tickets"). Team leads see the whole team on the Team Lead tab (unchanged).
  3. A ticket assigned to a technician of another team (an overflow, ADR-026) shows in that technician's own list, as before, and not in the owning team's technician view; the owning team's lead still sees it.
  4. **Known limits**: the notification id is a UUID, so guessing is not the realistic attack (the bug was that knowing one was enough); `POST /api/notifications/{id}/read` for a read notification writes it again (idempotent, no change); the team queue of an administrator is still every ticket (no paging).
- **Reason**: The rule already exists in the domain (`canViewIncident`); the application layer must apply it to every ticket it returns and every record it changes for a user.

## ADR-033: Login, Lockout and Exposure (remaining-defects plan, Phase E; stress audit P1 (login half), M4 and L4; decisions D11 and D12)
- **Status**: Accepted (implemented 2026-11-06)
- **Context**:
  1. **P1, login.** `UserService.authenticate` ran in the class-level transaction and so held a connection from its first query; `LoginAttemptService.recordFailedAttempt` then asked for a second connection in a `REQUIRES_NEW` transaction. With as many simultaneous logins as pool connections every connection waited for another: on a pool of 3, twelve simultaneous logins (half with a wrong password) ended in HTTP 500 after the 3 s connection timeout. The same shape as the intake starvation of ADR-018.
  2. **M4, lockout.** Five failed logins set `locked`, but `locked_until` was never written, so the lock lasted until an administrator unlocked the account: anyone could lock any account, administrators included, for good with five wrong passwords. `isCurrentlyLocked(now)` existed and nothing called it.
  3. **L4, exposure.** Anyone could self-register with any e-mail domain; the department was free text, so a typo created a department code and a ticket counter of its own; Swagger was open in every profile including production; two classes carried a login alias (`tech.database@` signed in as `tech.db1@`).
- **Decision** (D11, D12):
  1. **Login.** `UserService` has no class-level `@Transactional` and `authenticate` carries none, not even `SUPPORTS` (measured: with `SUPPORTS` Spring opens an empty transaction scope whose persistence context keeps the connection of the first query until the method ends, and the pool still starved). The write methods declare their own transaction. `LoginAttemptService` uses ordinary transactions that start when it is called, so the failure counter is committed before `InvalidCredentialsException` is thrown (the S2 contract of `SecurityRegressionTest` holds) and no login holds a connection while it waits for another.
  2. **Lockout.** `User.recordFailedLogin(max, now, lockDuration)` sets `lockedUntil` when the limit is reached; a lock that has expired is forgotten first (the count starts again, so one wrong password after the lock does not lock at once); a failure inside an active lock changes nothing, so attempts cannot extend it. `isCurrentlyLocked(now)` decides in `authenticate`, in `IitsmUserDetails` (the JWT filter, through `CustomUserDetailsService` with the injected `Clock`) and in the technician roster. The duration is `iitsm.security.lockout-minutes` (15). The answer is the same generic "Invalid credentials" for a locked account, a wrong password and an unknown user. Administrators follow the same rule. A successful login, or an administrator's unlock, clears the lock and its expiry. A lock without an expiry (set by an older version) stays until an administrator lifts it.
  3. **Registration.** New `RegistrationPolicy` (application layer): `iitsm.security.allowed-email-domains` (comma separated, empty = any domain: dev and test; prod and demo default to `nimbusfinserve.com`, environment variable `ALLOWED_EMAIL_DOMAINS`), exact domain match, case-insensitive; and the department must be registered in the `DepartmentCodeResolver` (any profile; the 400 lists the valid departments). `RegistryDepartmentCodeResolver` gains `isRegistered` and `registeredDepartments` and registers "Human Resources" (HUM) and "Risk & Compliance" (RIS), the two departments the registration form offers, with the codes the fallback already gave them, so existing ticket numbers and counters do not change.
  4. **Swagger.** `springdoc.api-docs.enabled` and `springdoc.swagger-ui.enabled` are false in the prod profile; dev and demo keep the documentation (it is part of the demo).
  5. **Alias.** The `tech.database@` login alias is removed from `UserService` and `CustomUserDetailsService`.
- **Alternatives Considered**:
  1. *Keep `authenticate` in a `REQUIRES_NEW`-free but still transactional method*: removes the second connection but still holds one through the BCrypt check (about 100 ms) for every login.
  2. *A separate non-transactional `AuthenticationService` bean*: cleaner names, but `UserService.authenticate` has callers in the controller and in tests; the annotation change is smaller and a contract test pins it.
  3. *Exponential back-off or a CAPTCHA instead of a timed lock*: more machinery for a course project; the timed lock removes the permanent lock-out, which was the defect.
  4. *Release the lock only through an administrator (as it was)*: it is the denial of service.
  5. *Validate the department only in prod*: a typo creates a counter of its own in every environment.
  6. *Remove the Swagger paths from the security allow-list in prod*: with the documentation switched off the paths answer 404 anyway; the list stays one list for all profiles.
- **Consequences**:
  1. **Tests changed on purpose**: none of the S2 or S7 tests changed (they pass as they were). `UserHierarchyTest` and `UserRepositoryAdapterTest` still use the one-argument `recordFailedLogin(max)` (a lock with no expiry); the application no longer calls it.
  2. A locked account whose lock expired still shows `locked = true` in the database until its next successful login; every reader decides with `isCurrentlyLocked(now)`.
  3. Self-registration with an e-mail address outside the configured domains, or with an unknown department, is HTTP 400 `ERR_VALIDATION_FAILED`; the registration form shows the message.
  4. **Known limits**: the lock counts failures per account, not per source address, so someone can still lock an account for 15 minutes at a time (the lock expires, which was the point); `LoginAttemptService` still swallows its own persistence errors so a login answer is not lost (a broad catch at a boundary); `TicketSequenceRowCreator` still opens a nested transaction (CLAUDE.md section 7 item 19, the ticket-counter half of P1, deferred by D22); the token of a user who was locked is not revoked (the filter refuses it while the lock lasts).
- **Reason**: A login must not hold a resource while it waits for another, a lock must end, and what is open to the world (registration, API documentation) should be decided by configuration per environment.
- **Amendment (2026-11-19, authentication hardening, ADR-046 to ADR-048)**: the lockout is unchanged for passwords, and three things now sit around it. A per-address rate limit answers 429 before the login, so a refused request never counts as a failed login or locks an account (ADR-046). Token refresh judges the lock with the shared clock and ends the session of a locked user (ADR-047). Wrong two-step verification codes count toward the same five failures, and for an account with two-step verification the password step no longer clears the failure count; only a correct code does (ADR-048).

## ADR-034: Classification Evidence Rules (remaining-defects plan, Phase F; stress audit H9 causes 2 to 4, L2; decisions D13, D14)
- **Status**: Accepted (implemented 2026-11-06)
- **Context**: The stress audit (H9) showed tickets that were not IT incidents, or were misread, reaching a technician with a high confidence: a coffee machine "power switch" went to the Network team, a locked desk drawer with a "pin" to Authentication, a parking garage "service" door to Application, and a phishing mail that mentioned an Excel macro to Software. Causes found in `KeywordClassifier` and `CompositeClassifier`: (1) a repeated word counted for every occurrence (`switch` in the title and in the description made two matches and 0.75), (2) three or more matches took the whole decision even when another category had nearly as many, without asking Naive Bayes, (3) Naive Bayes won every disagreement with a keyword result by confidence alone, and (4) the lexicon held words that are ordinary English outside IT (`power`, `switch`, `locked`, `pin`, `port`, `service`, `order`, `connection`). Baseline (Phase A, 2026-11-05): held-out 32/36 correct, 0/36 in triage; audit examples 8/12 (A01 to A04 wrong).
- **Decision** (D13: keep the 0.60 switch and the 0.55 cap, pinned by `ClassificationThresholdTest`; D14: the acceptance budget, enforced by `ClassificationBudgetTest` and `ClassificationBenchmarkTest`):
  1. **Distinct terms.** Every term counts once per ticket (`KeywordClassifier.Evidence`, a value object with the best category, its terms, the count per category and the security flag). "vpn vpn vpn" is one term, a single keyword in the title: 0.55.
  2. **Clear lead.** Three or more distinct terms give the strong 0.90 (which `CompositeClassifier` adopts without asking Naive Bayes) only when the best category leads the next one by at least two terms (`CLEAR_LEAD`); otherwise the keyword confidence is 0.75 and Naive Bayes is consulted.
  3. **Ties.** A tie for the best count is split evidence: confidence 0.55 and `ClassificationResult.tiedWith()`. Naive Bayes may break the tie (its answer is one of the tied categories, so the models agree); an answer outside the tie, or a Naive Bayes below the gate, goes to triage.
  4. **Disagreement.** When the keywords are confident (at least 0.60) and Naive Bayes names another category, Naive Bayes is trusted only if it is itself confident and at least one lexicon term supports its category (`ClassificationResult.supportFor`). Otherwise the keyword label wins and the ticket is capped at 0.55, so a person decides. (The plan said "cap every disagreement". That sent 7 of 36 held-out tickets to triage, over the budget of 3, because Naive Bayes is right and backed by a keyword in most of them; the corroboration condition keeps the cap for the cases the audit found.)
  5. **Security indicator.** A strong security term (`phishing`, `malware`, `ransomware`, `breach`, `unauthorized`, `hacker`, `trojan`, `suspicious`, `compromised`, `vulnerability`) in a ticket that another category wins is capped at 0.55 and the strong-keyword shortcut no longer skips it: a person decides whether it is a security incident. Broad lexicon words (`scan`, `security`, `threat`) raise no alert. The audit label for this case is "SECURITY or triage" (`CATEGORY|TRIAGE` in `audit_examples.tsv`).
  6. **Lexicon.** The generic words are removed (`KeywordClassifier.GENERIC_WORDS`, asserted absent by `KeywordClassifierRulesTest`); `attack`, `brute` and `exploit` are added to SECURITY, which fixed "Brute force attack" without a rule.
- **Alternatives Considered**:
  1. *Cap every keyword/Naive Bayes disagreement (plan step 3 as written)*: measured, 7 of 36 held-out tickets in triage against a budget of 3; undone as the plan says to do when a step breaks the budget.
  2. *A larger clear lead (three terms)*: phishing-with-Excel (3 against 1) would still be strong, and it is the same shape as a legitimate banking ticket (3 against 1), so a count alone cannot separate them; the security indicator does.
  3. *Weight title terms more than description terms*: more tuning surface and nothing in the audit asks for it.
  4. *Retrain Naive Bayes with out-of-domain examples ("coffee machine", "garage door") as a TRIAGE class*: needs a new class in the model and labelled data that does not exist.
  5. *Remove only the six words the audit named*: `switch` and `pin` are needed too (the coffee machine and the drawer); the list is the eight above and is asserted by a test, so a word cannot return unnoticed.
- **Consequences**:
  1. **Measured** (Phase A harness, before then after): held-out correct 32/36 then 33/36; held-out in triage 0/36 then 3/36 (8.3 %, budget 3); audit examples 8/12 then 12/12 (5 of the 12 now correctly in triage). The three held-out triage tickets are genuinely mixed (a power supply with no other word, "Azure App Service" with two categories, a SAN switch). Removing `power` costs the held-out "Desktop PC power supply unit failed" its accidental hit (it counted `power` twice before); it is now a triage ticket for a person, not a wrong automatic assignment.
  2. **Tests changed on purpose**: `KeywordClassifierDomainTermTest` (the vocabulary moved, ADR-035; replaced by `WordListDomainVocabularyTest`); `CompositeClassifierTest` gains the rules above (its existing cases are unchanged and pass). `CorrectnessRegressionTest.F5`, `AutoAssignmentRegressionTest`, the duplicate triage gate tests and the simulation scenarios S1 to S5 keep their intent and pass unchanged.
  3. `ClassificationResult` gains two components (`keywordSupport`, `securityAlert`) and two methods; all existing callers use the four-argument `of`.
  4. CLAUDE.md section 7 item 4 (a ticket without a keyword but with a service match goes to triage) is unchanged; item 5 (an accidental keyword in the title auto-assigns when Naive Bayes agrees) is narrowed: the generic words no longer count, and a title keyword that Naive Bayes contradicts goes to triage; a title keyword that Naive Bayes confirms still auto-assigns, which is the rule of ADR-009.
  5. **Known limits**: `CLEAR_LEAD` and the alert list are tuned on 36 held-out and 12 audit tickets; Naive Bayes is still overconfident out of its vocabulary (the audit's out-of-domain tickets are caught by the keyword rules, not by Naive Bayes); an out-of-domain ticket that happens to contain two real IT words ("the coffee machine needs a firewall") is still classified.
- **Reason**: Each rule answers one observed failure with evidence the ticket itself contains (how many different technical words, how much they lead, whether a second model has any lexical backing, whether a security word is present), and the budget decides whether a rule stays.

## ADR-035: Frozen Duplicate Vocabulary and the Corpus Repair (remaining-defects plan, Phase F; stress audit L7; decision D16-A)
- **Status**: Accepted (implemented 2026-11-06)
- **Context**: (1) `DomainVocabulary`, the word list duplicate detection needs two tickets to share (ADR-016), was the classifier's own lexicon (`KeywordClassifier` implemented it). Cleaning the lexicon (ADR-034) would silently change which tickets link as duplicates, and the duplicate benchmark has no slack (paraphrase recall 52 of 87 with 52 needed). (2) `sim/corpus.csv` pairs titles with the descriptions of other tickets: 70 distinct titles but 20 (HARDWARE 30) distinct descriptions per category, cycled in a different order, so 431 of 630 rows share no content word between title and description. The category of every row is right.
- **Decision**:
  1. **Vocabulary split.** The lexicon as it was on 2026-11-05 is frozen in `src/main/resources/sim/duplicate-vocabulary.txt` (201 words) and read by the new `WordListDomainVocabulary` (words and their stems; blank and `#` lines ignored). `IntelligenceConfig` exposes it as the `DomainVocabulary` bean; `DuplicateMatchPolicy` depends on the interface as before. `KeywordClassifier` no longer implements `DomainVocabulary`. The file keeps the generic words the classifier dropped, and says so. Change it only together with `DuplicatePairSetTest` and the duplicate benchmark. Done first and alone: the duplicate benchmark output was byte-identical before and after this step.
  2. **Corpus repair.** `scripts/data/repair_corpus.py` (kept in the repository, deterministic): a row whose description shares a content word with its title is kept; any other row gets the description of its category that shares the most words with its title (ties: the description used by the fewest rows, then the first); a row with no match is kept. 417 rows changed; rows without a shared word 431 then 14 (21 when compared as stemmed tokens, `CorpusPairingTest`). Categories and row counts are unchanged.
- **Alternatives Considered**:
  1. *Let the duplicate vocabulary follow the cleaned lexicon*: moves duplicate scores with every lexicon edit, and the benchmark has no room.
  2. *Hard-code the frozen words in a class*: a resource is reviewable as data and the test can read the same file.
  3. *Re-generate the descriptions*: invents training data; the repair only re-pairs what exists.
  4. *Leave the corpus alone*: the pairing affects the TF-IDF document frequencies that every duplicate score uses, and a reader sees nonsense tickets.
- **Consequences**:
  1. **Measured** (duplicate benchmark, before then after the repair; the split alone changed nothing): paraphrase recall 52/87 (0.598) then 54/87 (0.621), so the benchmark now has two links to spare instead of none; precision 91/92 then 93/94 linked pairs are duplicates, still exactly one false link (L02, cosine 0.3291 then 0.3624, still the same known pair); safety margin of the best non-duplicate under the content guard 0.0545 then 0.0564 (ADR-016 requires 0.05). `DuplicatePairSetTest` and its targets are unchanged and pass; no new baseline needed (D15).
  2. Held-out classification is unchanged by the repair (33/36); one more ticket lands in triage (3), within budget.
  3. **Tests changed on purpose**: `KeywordClassifierDomainTermTest` is replaced by `WordListDomainVocabularyTest`; the four duplicate test classes build their vocabulary with `WordListDomainVocabulary.duplicateVocabulary()` instead of `new KeywordClassifier()`.
  4. **Known limits**: the repair re-pairs by word overlap, so 14 rows keep a description that shares no plain word with the title; the corpus is still synthetic (20 descriptions per category); the duplicate vocabulary is a snapshot that will not follow improvements to the lexicon until someone edits the file on purpose.
- **Reason**: Two lists that look alike but serve different jobs must be able to change independently, and training data that pairs a ticket's title with another ticket's description is a defect whichever model reads it.

## ADR-036: Routing in One Place: the Category Decides the Team (remaining-defects plan, Phase G; stress audit H9 cause 1, L6; decisions D17, D18)
- **Status**: Accepted (implemented 2026-11-06)
- **Context**: Which team gets a ticket was decided in four places, by two different rules, and the rules disagreed with the classification the system had just made.
  1. The intake and the dispatcher (`TicketDispatchService`) took the owning team of the ticket's matched **service**; a ticket that matched no service fell back to the general service `SRV-GEN-001`, owned by the Service Desk. A DNS ticket, correctly classified NETWORK, went to the Service Desk (audit H9; Phase A measured 13 of 36 held-out tickets with no matching service).
  2. When that team had nobody free, `TicketDispatchService` offered the ticket to **anyone** with capacity (an unskilled technician of any team); `AdminIncidentService.acceptTriageSuggestion` had its own copy of the same fallback.
  3. The administrator's reclassify rerouted by the **service's** owner when a service was sent and by the category only when it was not.
  4. The access rules (`IncidentLifecycleService.resolveOwningTeamId`, the team queue of ADR-032, the support team of the admin detail view) also took the service owner, so "whose ticket is this" and "who was offered it" could differ.
  The audit-replay numbers of Phase A: 15 of 36 held-out tickets reached the team of their true category (the benchmark replayed the service rule).
- **Decision**:
  1. **The classified category decides the team** (D17). New pure rule `RoutingPolicy` (domain): the support team that handles the category, the smallest team id when several do; when no team handles the category (a gap in the set-up) the owner of the ticket's service is the fallback, so a ticket is never left without a team. The IT service keeps its other jobs: business criticality, priority and SLA policy.
  2. **One router, four callers.** New application service `TicketRouter` (`owningTeamId`, `candidates`, `categoriesHandledBy`) composes `RoutingPolicy` and `CandidateFilter`. It is used by the intake and the dispatcher (through `TicketDispatchService.dispatchOne`), by the administrator's reclassify reroute, by accept-suggestion, and by the access rules (`resolveOwningTeamId`, `getTeamQueue`, the admin detail's support team). The duplicated fallbacks are gone.
  3. **Overflow only to skilled technicians** (D18). `CandidateFilter.filterCandidates(technicians, owningTeamId, category, exclusions)`: the owning team's technicians with free capacity first; when none is free, technicians of other teams who have the category's skill (`Technician.hasCategorySkill`); otherwise nobody and the ticket waits in `CLASSIFIED` (`Outcome.NOT_ASSIGNED`, the dispatcher retries it with the same rule; the SLA response escalation covers a long wait). An unskilled technician never receives the ticket. Exclusions (a technician who flagged the ticket) apply everywhere.
  4. **Team queue by category.** `IncidentRepository.findByCategoryIn`; a team lead sees the tickets of the categories the team handles, a technician their own tickets and the team's unassigned ones (ADR-032 with "services the team owns" replaced by "categories the team handles").
  5. The general service id is one constant, `ItService.GENERAL_SERVICE_ID`.
- **Alternatives Considered**:
  1. *Keep the service owner and fix the fallback (a DNS service in the catalogue)*: every uncatalogued fault type would need its own service, and a service that another team owns would still override the classification.
  2. *Keep "anyone with capacity" as the last resort*: a ticket in the hands of a technician with no skill for it is worse than a ticket that waits and escalates; the audit showed exactly that.
  3. *Let the ticket wait without any overflow*: simpler, but a full team would block a ticket although a skilled colleague elsewhere is free; D18-B allows skilled overflow.
  4. *Route by the best-scoring technician across all teams*: the assignment strategies already score within the candidate set; mixing team choice into the score hides the rule.
- **Consequences**:
  1. **Measured** (Phase A routing replay through the real router; before = the service rule): held-out auto-routed tickets reaching the team of their true category 15/36 then 31/33 (the two misses are classification errors, H8 and H17); audit examples 5/8 then 7/7; held-out and audit together 38/40 = 95.0 % (target 95 %, asserted by `ClassificationBenchmarkTest`). By construction every auto-assigned ticket goes to the team of the category it was given (`TicketRoutingContractTest`, 24 cases across the four callers).
  2. **Tests changed on purpose**: `ReclassifyRoutingRegressionTest` (T1, T4, T5: the target team is the team of the new category; T4 reclassifies inside the network team's own category), `ReclassifyEndpointRegressionTest` E3 (was "an explicit service wins over the category's team", now "the category's team wins, the service only sets criticality"), `ReclassifyStateRegressionTest` R5, `CorrectnessRegressionTest.F7` (the single free slot is a network technician and both reports are network tickets, because a ticket no longer goes to anyone), `CapacityRaceRegressionTest` (clears slots each round: all its tickets are network tickets), `TeamQueueAccessRegressionTest` (the network lead is offline so tickets go to regular technicians), `TicketDispatchServiceTest` (the "any technician" case became skilled overflow and a new "unskilled never" case), `AssignmentStrategyTest.testCandidateFilter` (new signature), the constructors of the three `AdminIncidentService*Test` classes and `AdminIncidentDetailServiceTest`. `AutoAssignmentRegressionTest`, `UnassignedIncidentDispatcherTest` and the simulation scenarios pass unchanged.
  3. The Service Desk receives far fewer tickets (only HARDWARE and what it is skilled for); tickets of a full team wait. The live run shows the dispatcher continuing with other teams' tickets (`NOT_ASSIGNED` does not stop the cycle).
  4. `IncidentStatus.canBeRerouted()` replaces a status comparison in `AdminIncidentService`.
  5. **Known limits**: the seeded technicians have skills only for their own team's category, so no overflow happens until an administrator gives a technician another category's skill (there is no screen for skills); the seeder gives a multi-category team's members the skill of one of its categories only (their own team handles all of them, so routing is unaffected); a ticket that waits is visible to the whole owning team and to its administrators, not to the skilled outsiders; the live run shows one team (Network, 3 technicians and a lead) can fill up under a burst of network faults, after which new network tickets wait.
- **Reason**: Which team owns a ticket is a business rule about what the ticket is, so it belongs to the classification, in one place that every caller asks; the service is data about impact.

## ADR-037: Actors Are Stored as User Ids, and the Employee History Is Neutral (remaining-defects plan, Phase H; CLAUDE.md section 7 items 2 and 13; decisions D19, D20)
- **Status**: Accepted (implemented 2026-11-07)
- **Context**:
  1. Spring Security names the signed-in user by login e-mail, and every controller passed `authentication.getName()` on to the services. The services stored what they were given, so the **e-mail** became the actor of an assignment, a priority override (`overriddenBy`), a note (`authorId`; its `authorName` fell back to the e-mail too, because the controller looked a user up by e-mail with the id lookup), the resolver (`resolvedBy`) and most audit entries, while the system's own events used ids (`SYSTEM`, `EMP-DEMO-01`). One column held two kinds of value.
  2. The employee's activity history is built from the audit trail. Two entries quoted internal facts: "Marked as duplicate of FIN-2026-000042 (Similarity: 0.61)" named another ticket (possibly another person's), and "Technician TECH-NET-2 requested reassignment: <reason>" repeated a technician's internal reason (ADR-014 had hidden only the priority-related entries).
- **Decision**:
  1. **One helper for "who is signed in"**: `web.security.CurrentUser.idOf(Authentication)` turns the login e-mail into the user's id (an id is returned as it is; an e-mail that matches nobody is refused with a `ValidationException`). The four controllers that act for a user (technician, employee, admin, notification) use it. `ArchitectureRegressionTest.controllersDoNotReadTheLoginNameDirectly` fails the build when a controller (other than `AuthController`, which needs the e-mail for `/me`) calls `Authentication.getName()`.
  2. **The services store ids whatever they are given** (defence in depth, because the application layer is also called from tests, simulation and other services): `IncidentLifecycleService` and `AdminIncidentService` use `actor.getId()` for the audited actor, the event actor, the note author, the resolver (the `Resolution` is re-signed with the actor's id) and the override. A note is always signed with the author's own name: `addNote` lost its `authorName` parameter (nobody can sign a note as someone else, and the controller no longer looks the name up with the wrong key).
  3. **Names in the staff views, read in one query**: `UserRepository.findAllByIds`, `ActorNames` (application, package-private) and `UserService.namesById` return `id -> name`; `IncidentActors` lists the ids a ticket needs (override, resolver, audit actors; the reporter and assignee are looked up as before and notes carry their name). The admin detail read model carries `actorNames`; the admin and technician list endpoints make one lookup for the whole list. New fields: `PriorityDecisionView.overriddenByName`, `ResolutionView.resolvedByName`, `AdminAuditRecordView.actorName`; they are `null` for an actor that is not a user (`SYSTEM`, an old e-mail actor), and the view then shows the stored text. The admin dialog shows "Name (id)" (`tdActor` in `app.js`, both escaped); asset version 3.7.
  4. **Neutral wording for employees (D19-B)**: `IncidentDtoMapper.employeeText` replaces the text of the `DuplicateDetected` entry with "Linked to an earlier report of the same problem" and of the `ReassignmentRequested` entry with "Passed to a better suited team" **when the employee view is built**. The stored description is unchanged (staff read it, and Flyway V6 reads `audit_records.description`), and rows written before this change are covered too.
- **Alternatives considered**:
  1. *Convert old e-mail actors with a Flyway V8 migration (D20-B)*: only worthwhile when a production database holds such rows (D21 is unknown and assumed "no"); an old e-mail actor still displays as the stored text. If D21 turns out to be yes, V8 is the next migration number and must not touch `audit_records.description`.
  2. *Resolve the id inside every service only* and leave the controllers alone: it works, but the rule "controllers pass ids" would be a habit; the architecture test makes it a rule.
  3. *Store the neutral text in the audit record*: loses the information staff need and does not repair old rows; the render-time choice does both.
  4. *Hide the two entries from employees altogether*: the employee would no longer see that their report was linked or handed over; a neutral sentence keeps the history honest.
  5. *Look the names up row by row in the mapper*: simple but one query per audit row; the batch costs one.
- **Consequences**:
  1. **Tests**: `ActorIdentityRegressionTest` (4, over HTTP and direct service calls: stored actors are ids after assign, override, note, resolve, verify and feedback; the names appear in the staff views; services normalise an e-mail), `EmployeeHistoryPrivacyRegressionTest` (1: across every employee view of a seeded run, no view contains another ticket's id or the technician's reason), `EmployeeAuditTrailPrivacyTest` (+3), `AdminIncidentDetailMapperTest` (+2), `AdminIncidentDetailServiceTest` (+1, one batch lookup), `IncidentActorsTest` (3), `CurrentUserTest` (4), `ActorNameMarkupTest` (3), the architecture rule (+1). Changed on purpose: the two Mockito admin tests (`AdminIncidentServiceOverrideTest`, `AdminIncidentServiceInputTest`) give their mock administrator an id, `WrongDomainWorkflowRegressionTest` (new `addNote` signature) and the four markup tests that pin the asset version (3.7).
  2. The new tests close the tickets they create: an open VPN ticket left in the shared test database became the duplicate parent of a ticket in `AutoAssignmentRegressionTest`, which then rode its parent's technician (found by the full run).
  3. **Known limits**: rows written before this change keep their e-mail actors and show them as text (no name); a ticket's note authors and the reporter/assignee names are resolved as before (notes store the name at writing time); the notification and e-mail texts and the triage queue are unchanged (items 14 of section 7); `IncidentIntakePipeline` still accepts an id or an e-mail for the reporter and stores the reporter's id.
- **Reason**: "Who did this" must be one kind of value that survives an e-mail change and can be joined to a user; what an employee reads about other tickets and staff reasoning is a privacy rule that belongs where the employee view is built.

## ADR-038: A Bounded Event History, Notification Metrics and a Pinned Duplicate Case (remaining-defects plan, Phase I; stress audit P4, item R-N, test T1; decisions D21, D22)
- **Status**: Accepted (implemented 2026-11-07)
- **Context**:
  1. **P4**: `InMemoryDomainEventPublisher` kept every event it ever published in a list that only grew (`getPublishedHistory`, a verification aid for tests and the lifecycle demo). The running application's publisher (`TransactionAwareDomainEventPublisher`, which wraps it) therefore leaked a little memory with every ticket action for as long as the process lived.
  2. **R-N**: the number of notifications waiting for the delivery worker and the number dropped (queue full, or shutting down) were visible only through Java methods; an operator could not see a backlog or a loss. The same section of the plan asked for them as Actuator metrics.
  3. **T1**: CLAUDE.md section 7 item 20 recorded that a *confident* report that duplicates a ticket *sitting in triage* "is still left to the dispatcher", and that no test pinned it.
  4. **R-C1** (old rows saved before ADR-015 may still be HTML-escaped) needs a one-off migration only when a production database holds such rows. D21 (does one exist?) is unknown and assumed **no**.
- **Decision**:
  1. **Bounded history**: `InMemoryDomainEventPublisher(int historyLimit)` keeps at most the newest `historyLimit` events (oldest dropped first); `0` keeps none. The no-argument constructor keeps `DEFAULT_HISTORY_LIMIT` = 1000, so even the demo and the tests are bounded. `getPublishedHistory()` returns an immutable snapshot, `clearHistory()` keeps the bound. `TransactionAwareDomainEventPublisher` takes the limit as a third constructor argument; `DomainEventConfig` reads `iitsm.events.history-limit` (environment variable `EVENT_HISTORY_LIMIT`): **1000** in the base configuration and **0** in the `prod` profile.
  2. **Metrics**: `NotificationMetrics` (a Micrometer `MeterBinder`, bean in `DomainEventConfig`) registers the gauge `iitsm.notifications.pending` and the function counter `iitsm.notifications.dropped` over the publisher's existing counters. They are served at `/actuator/metrics/<name>`. The Actuator endpoints other than health were open to **every signed-in user**; `SecurityConfig` now requires the administrator role for `/actuator/**` (health stays public for probes).
  3. **T1 pinned** (`DuplicateOfTriageParentRegressionTest`): at intake the duplicate is linked to the parent, is not in triage and stays `CLASSIFIED` and unassigned (it has no technician to ride, F4); the next dispatcher cycle gives it a technician of its own; the parent stays in triage, unassigned, and the dispatcher never touches it. No behaviour change, the test fixes today's behaviour so a later change is deliberate.
  4. **R-C1 / V7 skipped** (D21 = no). The next free Flyway number stays V7. If a production database with escaped rows exists, the migration is the one described in `docs/remaining-defects-phase-details.md` (unescape the five sequences, only rows saved before the fix, repeat until nothing changes, tested on H2 and PostgreSQL).
- **Alternatives considered**:
  1. *Remove the history from the publisher*: tests and the demo use it; a bound keeps them working and removes the leak.
  2. *Make production unbounded but "small enough"*: any growth proportional to traffic is a leak; zero is simplest in production.
  3. *A ring buffer class of its own*: a `Deque` under one monitor is enough for a verification aid; no contention-sensitive path reads it.
  4. *Expose the counters through a custom endpoint*: Micrometer is already on the class path and operators expect `/actuator/metrics`.
  5. *Leave Actuator open to signed-in users*: the metrics (and later others) describe internal state; administrators only is the safe default.
  6. *Write V7 anyway "just in case"*: a data migration that rewrites text columns should not ship without a database that needs it (it cannot be proven correct against data nobody has).
- **Consequences**:
  1. **Tests**: `InMemoryDomainEventPublisherHistoryTest` (7: bound, zero, default, snapshot, negative limit, clear, eight parallel publishers), `TransactionAwareDomainEventPublisherTest` (+1), `NotificationMetricsTest` (4), `EventHistoryConfigContractTest` (2: base 1000, prod 0), `EventHistoryWiringTest` (2: the configured limit reaches the application's publisher, the metrics are in the meter registry), `ObservabilityEndpointsRegressionTest` (3: administrator reads both metrics, anonymous 401, employee and technician 403, health stays public), `DuplicateOfTriageParentRegressionTest` (2). The test profile's `application.yml` exposes `metrics`, because it hides the shipped one.
  2. `DomainEventConfig.domainEventPublisher` now returns the concrete `TransactionAwareDomainEventPublisher` (every injection point asks for the interface and still works).
  3. **Known limits**: the metrics are per application instance; the counters restart at zero with the process; events still in the queue when the process dies are lost (ADR-017, unchanged); the history in dev, demo and tests is a verification aid and holds the newest 1000 events only; R-C1 remains open until D21 is answered.
- **Reason**: Memory that grows with traffic is a defect even when it is "only for tests"; operational numbers belong where operators already look; a behaviour that is documented but untested is a behaviour that will change by accident.

## ADR-039: Front-End Closure: Submit Guards, Refresh After a Refusal, Keyboard Focus, and What the Button Run Found (remaining-defects plan, Phase J; CLAUDE.md section 7 items 6 and 14)
- **Status**: Accepted (implemented 2026-11-07)
- **Context**: ADR-017 guarded every write that goes through `apiCall` against a double click and refreshed the list after a conflict. Four gaps remained, and the plan asked for every action button to be clicked in a real browser, which had never been done for all of them.
  1. **Sign-in and registration** do not go through `apiCall`. Sign-in disabled only its own button, so the demo pills and persona chips (which call `loginUser` directly) could start a second login; registration had no guard at all (two submits created or attempted two accounts).
  2. A write refused with **400 or 403** (the ticket changed, or is no longer the user's) left the list stale; only 409, 404 and 5xx refreshed it.
  3. A disabled button loses **keyboard focus**; when the button was enabled again, a keyboard user had to Tab from the top of the page. Dialogs did not hold Tab inside themselves and did not return focus to the control that opened them.
  4. Small items of the list: the composite score showed 2 decimals beside weighted contributions with 3 (item 6), and the triage cards had no staff ticket name (item 14).
- **Decision**:
  1. **Guards**: `loginInFlight` and `registerInFlight`. `loginUser` returns at once when a login is in flight, whatever called it; the registration handler does the same, disables its button (`aria-busy`) and releases both in `finally`. The guard is the first statement, before any `await`.
  2. **Refresh**: `refreshAfterFailedWrite` now also reacts to 400 and 403 (`refreshActiveTab()`).
  3. **Focus**: `beginWrite` remembers whether the button had focus; when the cool-down ends the button gets it back (`restoreFocus`), or its re-rendered twin (same `btn-...` action class and `data-id`) when the list was drawn again, unless the user already moved focus elsewhere. `openModal` moves focus into the dialog and remembers the opener; `closeModal` gives the focus back (and again to the twin after the redraw). One document-level `keydown` handler (`trapTabKey`) wraps Tab and Shift+Tab inside the open dialog, the action dialog and the admin ticket dialog alike.
  4. **Numbers and names**: the composite score shows three decimals (the tooltip keeps four); `TriageQueueItemDto` carries `displayId` (`TicketDisplayName.of(priority, id)`) and the triage card shows it next to the id with `ticketNameHtml`. Asset version 3.8.
  5. **Real-browser run**: `scripts/live-checks/action_buttons_browser.py` signs in through the login form as technician, employee, team lead and administrator, clicks every action button (Acknowledge, Start investigation, Add note, Request info, Resolve, Flag out-of-scope; Raise ticket, the specialist button, View timeline, Provide info, Reject fix, Verify; Acknowledge & Handle, Inspect Escalation; Reject request, Reclassify & Reassign, Override, Reassign, the ticket dialog, Activate strategy), confirms each result through the API, and exercises the guards above. It is committed with the other live checks.
- **Defects the button run found and this phase fixed** (none was in the plan):
  1. **The employee's "Provide Requested Info" button never appeared.** The card showed it when `status === 'PENDING_INFO'`, but an employee only receives the public status (a ticket waiting for their reply is `IN_PROGRESS`), so an employee could not answer a technician's question in the web app (the API worked). The "waiting for you" counter of the employee screen had the same flaw and always showed 0. Employee buttons and the counter now follow `allowedActions`, which the server sends (`awaitsMyReply`); Verify and Reject follow it too.
  2. **After registering and signing out, the registration card was shown instead of the sign-in card** (`showAuthView` did not reset the two cards).
- **Alternatives considered**:
  1. *Put sign-in and registration through `apiCall`*: it would give the same guard for free, but `apiCall` signs the user out on 401, which is the answer to a wrong password; a separate guard is smaller and safer.
  2. *Refresh only the list the failed button belongs to*: more precise, but the buttons do not know their list; one refresh of the active tab is cheap.
  3. *A focus-trap library*: the project has no dependencies in the browser (CSP, no CDN); the trap is 30 lines.
  4. *Add a "claim" action for the team lead* (see the known limit): a new feature that needs a decision about who may take an unassigned ticket; out of scope for a defect programme.
- **Consequences**:
  1. **Tests**: `FrontEndClosureMarkupTest` (11, structure pinned as text because there is no JavaScript test runner), `AdminIncidentServiceWrongDomainTest` (+1, the triage entry's `displayId`); changed on purpose: the markup tests that pin the asset version (3.8), `WriteGuardMarkupTest` (the refresh condition), `TicketDisplayNameMarkupTest` (one more staff use of `displayId`, the triage card). The behaviour is proved by the browser script; mutation checks broke the script on nine front-end mutations (see the summary).
  2. **Known limits**: the team lead's "Acknowledge & Handle" on an **unassigned** ticket cannot work: the server only lets the assignee acknowledge, so the answer is HTTP 409 and the message "This ticket was just updated by someone else", which is misleading (the lead has no way to take a ticket; an administrator or the dispatcher assigns it); the multi-select menus still do not trap focus or remember their selection (section 7 item 11); notification and e-mail texts for staff still use the plain ticket id; the browser script moves no simulation clock and changes the assignment strategy only temporarily (it puts the original back).
- **Reason**: A button must do what it says for a keyboard user and a double-clicker, and the only way to know is to press every one of them in a real browser; the two defects found that way had survived every unit test because no test looked at the page.

## ADR-040: Suggested Resolutions from Resolved Tickets (spec feature G, Phase K1)
- **Status**: Accepted (implemented 2026-11-07, Phase K1 of the suggested-resolution plan; votes K2, knowledge base K3 and the web screen K4 follow as ADR-041 to ADR-043)
- **Context**: When a technician works on a ticket, the system should suggest the top 3 fixes used for similar past problems, each with a similarity score and an explanation. The building blocks existed: every resolved ticket stores a `Resolution` (root cause, steps, preventive action), and duplicate detection already compares ticket texts with the wired `SimilarityMeasure` (TF-IDF cosine, ADR-016) and a frozen domain vocabulary (ADR-035). What did not exist: a ranking for past fixes, a way to read resolved tickets cheaply, and an endpoint. A rejected fix sends a ticket back to `IN_PROGRESS` with its old resolution still stored, so "has a resolution" is not the same as "was fixed by it".
- **Decision**:
  1. **Strategy**: the domain interface `ResolutionSuggester` (package `domain/strategy/suggestion`) ranks candidates for a `SuggestionQuery`. `TfIdfResolutionSuggester` is the wired implementation; another ranking is a new class registered as the bean (`SuggestionConfig`), with no change to the service or the web layer (`ResolutionSuggestionServiceTest.anotherSuggesterPlugsIn` proves it with a second implementation).
  2. **Candidates**: tickets whose status has a confirmed resolution (`IncidentStatus.hasConfirmedResolution()`: RESOLVED, VERIFIED, CLOSED). A candidate's matching text is title + description + root cause + steps; the preventive action is shown but not compared.
  3. **Rules, in the domain** (`SuggestionPolicy`, `SuggestionQuery`, `TfIdfResolutionSuggester`): the ticket itself and every ticket in its `linkedIncidentIds` (duplicate links are stored both ways, so parent and children) are never suggested; with `same-category-only` (default true) a candidate must have the ticket's category, and a ticket without a category gets nothing; a candidate must reach `min-similarity` (0.20) **and** share `min-shared-terms` (1) domain terms with the ticket (the same content guard as duplicate detection, so filler-word matches are not suggested); best first, ties in source-id order, cut to `max-results` (3). An empty list is the answer when nothing qualifies.
  4. **Explanation**: the domain terms both texts share, shown as the ticket wrote them (lower case, `postgres` and not the stem `postgr`), alphabetical, at most `explanation-terms` (5).
  5. **Cost bound (the intake lesson of CLAUDE.md section 7 item 18)**: one request reads at most `candidate-window` (200) candidates with **one** query: a projection (`ResolvedCaseRow`, `SpringDataResolvedCaseRepository`) over `resolutions` joined with `incidents`, newest resolution first, limited by `Pageable`. No ticket aggregate is loaded (an `Incident` loads its notes, factor rows, SLA tracker and links eagerly). The ranking then makes about 2 x (200 + 1) TF-IDF transforms, because the measure transforms both texts on every call; the benchmark measured a median of 5 to 6 ms and a worst case of 12 to 13 ms per request over a full window (development laptop, in-memory ranking only). Fixes older than the newest 200 of their category are not seen; K3's knowledge base is the way to keep a good fix suggestable.
  6. **Port**: `ResolvedCaseRepository` (domain, read only) rather than another method on `IncidentRepository`, so the light projection is a separate concern and no other implementation of the incident port has to change.
  7. **Endpoint**: `GET /api/technician/incidents/{id}/suggested-resolutions` (new `ResolutionSuggestionController`, `SuggestedResolutionView`, `SuggestionDtoMapper`). Roles come from the existing `/api/technician/**` rule (technician, team lead, administrator; employee 403, no token 401). The service loads the ticket through `IncidentLifecycleService.getIncident`, so the ticket's access rules apply (a technician who may not view the ticket gets 403 `ERR_UNAUTHORIZED_OPERATION`, an unknown ticket 404 `ERR_SERVICE_NOT_FOUND`, a staff display name is accepted as the id). No new exception, error code or event.
  8. **Privacy**: a suggestion shows the source ticket's title, root cause, steps and preventive action, its id and its staff display name, the score and the terms. It never shows the source's description, reporter, assignee or notes: the description is used for matching only. Candidates are **not** filtered by whether the viewer may open the source ticket (decision 2 of the K1 plan): a technician sees only their own and their team's unassigned tickets (ADR-032), so such a filter would leave almost nothing to suggest; the exposure is limited to technical content that staff share anyway. No field was added to any employee view, and no domain event was added.
  9. **Configuration**: `iitsm.suggestions.max-results`, `min-similarity`, `min-shared-terms`, `same-category-only`, `candidate-window`, `explanation-terms` (environment variables `SUGGESTION_*`). A value outside its range stops the application at start-up.
- **Alternatives considered**:
  1. *Load resolved `Incident` aggregates through `IncidentRepository.findByCategory`*: simple, but every ticket of a category with its eager collections on every request, the cost pattern of section 7 item 18.
  2. *Vectorise the query once and compare vectors directly*: about half the transforms, but it bypasses the `SimilarityMeasure` strategy the spec asks to reuse; the measured cost is small enough.
  3. *A precomputed index (`Map<String, Set<String>>` term -> tickets)*: fastest, but it must be kept in step with every resolve, reopen and reclassify; not needed at 200 candidates.
  4. *Category as a ranking bonus instead of a hard filter*: lets a fix from another category win on wording; the spec asks for a hard filter, which is the default and can be switched off.
  5. *Only show fixes from tickets the viewer may open*: see decision 8.
  6. *Show stems as the explanation*: correct but unreadable (`databas`, `kubernet`).
- **Consequences**:
  1. **Tests**: `TfIdfResolutionSuggesterTest` (15), `SuggestionValueObjectsTest` (17, including `IncidentStatus.hasConfirmedResolution` for all 9 statuses), `ResolutionSuggestionServiceTest` (6, including the extension point), `ResolvedCaseRepositoryAdapterTest` (4, H2), `SuggestedResolutionRegressionTest` (4, end to end over HTTP), `SuggestionBenchmarkTest` (benchmark tag). Seven mutation checks each made a test fail (no category filter, self not excluded, minimum ignored, no top-N cut, access check removed, shared-term guard off, employees allowed through both security layers).
  2. **Measured** (`target/benchmarks/suggestion-benchmark.txt`, 27 past fixes in 9 categories, 24 new tickets in other words): top-3 hit rate 18/19 (0.947), top-1 18/19, 0 of 5 "no fit" tickets got a suggestion; the hit rate is 18/19 for every min-similarity from 0.10 to 0.25 and falls to 17, 16, 15 at 0.30, 0.35, 0.40, which is why the default is 0.20. The one miss is a printer ticket: `printer` and `toner` are not in the frozen duplicate vocabulary, so the content guard refuses it.
  3. **Known limits**: the vocabulary is the duplicate vocabulary of ADR-035 and misses some hardware words (the printer miss); the "no fit" tickets of the benchmark are kept out by the content guard, not by the score (the sweep never let one through), so they do not test the threshold; a fix older than the newest 200 of its category is not seen until K3; the newest-first sort reads `resolutions` without an index on `resolved_at` (fine at course scale, an index is the remedy at real scale); `connection` and `connections` stem differently and can both appear as terms; a ticket reclassified after resolution is found under its new category.
- **Reason**: Reusing the existing similarity and vocabulary keeps the feature explainable and consistent with duplicate detection, a hard window keeps one request cheap whatever the history, and putting every rule in the domain makes each one testable and swappable.

## ADR-041: Votes on Suggested Resolutions, Bounded in the Ranking (spec feature G, Phase K2)
- **Status**: Accepted (implemented 2026-11-07, Phase K2 of the suggested-resolution plan)
- **Context**: Phase K1 (ADR-040) ranks past fixes by text similarity only. The spec asks that a technician can say "this worked" or "this didn't" on a suggestion, that a voter has one vote per suggestion and ticket (voting again changes it), that the voter is stored by user id, and that votes adjust the ranking mildly without ever overriding similarity.
- **Decision**:
  1. **Storage**: Flyway **V9** `suggestion_votes` (V7 and V8 stay reserved for the conditional migrations of decision D21): `id` identity, `voter_id` -> `users`, `source_type` (`RESOLVED_TICKET` or `KB_ARTICLE`, check constraint), `source_id` (no foreign key, because an article is a source from K3 on), `target_incident_id` -> `incidents` with `ON DELETE CASCADE ON UPDATE CASCADE`, `worked`, `voted_at`; **unique (voter_id, source_type, source_id, target_incident_id)**; index on (source_type, source_id) for the counts. Same SQL on H2 and PostgreSQL, tested on both (`SuggestionVotesMigrationH2Test`, `SuggestionVotesMigrationPostgresTest`).
  2. **Domain**: `SuggestionVote` (immutable record: voter id, `SuggestionSourceKey`, target ticket, verdict, time; `cast` refuses a resolved ticket voted as its own fix with a `ValidationException`, HTTP 400; `recast` changes the verdict and keeps the key), `VoteTally` (worked and did-not-work counts; `smoothedWorkedShare` = (worked + 1) / (worked + didNotWork + 2)), `VoteTallies` (counts per source), `VoteBand` (weight w, factor = 1 - w + 2w x share). Port `SuggestionVoteRepository` (find, save as upsert, tallies in one query).
  3. **Ranking**: score = similarity x factor. With w = 0.2 (`iitsm.suggestions.vote-weight`) the factor stays **strictly** inside (0.8, 1.2) whatever the counts, and is exactly 1.0 without votes or with an even split. The minimum similarity (0.20) and the shared-term guard apply to the **raw similarity**, so votes can never let a weak match in or push a qualified one out. Votes are applied **before** the top-3 cut, so a praised close fourth can enter the list; candidates are ordered by score, then similarity, then source id. A clear similarity gap cannot be overturned: 0.30 x 1.2 < 0.50 x 0.8. `ResolutionSuggester.suggest` gained a `VoteTallies` argument (the two-argument form is a default method meaning "no votes"); `TfIdfResolutionSuggester` takes the `VoteBand`.
  4. **Counts are per source, over every ticket and voter**: a fix that worked on three tickets is better evidence for the fourth. The vote of one voter on one ticket is the unit of storage; the count is the unit of ranking.
  5. **Endpoint**: `POST /api/technician/incidents/{id}/suggested-resolutions/votes` with `{sourceType, sourceId, worked}` answers 200 with the stored verdict and the source's counts (`SuggestionVoteView`). The voter is `CurrentUser.idOf` (ADR-037). The ticket is loaded through `IncidentLifecycleService.getIncident`, so whoever may view the ticket may vote (other team 403, unknown ticket 404 `ERR_SERVICE_NOT_FOUND`, employee 403, no token 401).
  6. **Error choices (ADR-027, no new 500)**: unknown `sourceType` or broken JSON 400 `ERR_MALFORMED_JSON`; a missing field 400 `ERR_VALIDATION_FAILED` (bean validation on `SuggestionVoteRequest`); a source that does not exist **or is not a resolved case** (an open ticket, a rejected fix) 404 `ERR_NOT_FOUND` through the new `ResourceNotFoundException` (the code the web layer already used for an unknown path; decision 4 of the K1 plan); an article source is 404 until K3; a resolved ticket voted as its own fix 400 `ERR_VALIDATION_FAILED`; two first votes of the same voter on the same key racing: the loser's unique-key violation is 409 `ERR_CONCURRENT_MODIFICATION` (`ConcurrentUpdateException`).
  7. **Suggestion list**: `SuggestedResolutionView` gained `score`, `workedVotes`, `didNotWorkVotes` (staff view only). The list reads the counts of the whole candidate window (up to 200 sources) in **one** grouped query.
  8. **No event, no audit entry**: a vote is a technician's opinion about a fix, not a change of the ticket; nothing reaches the employee history (ADR-014).
- **Alternatives considered**:
  1. *Counts per (source, target ticket)*: votes on one ticket would not help the next; the purpose is to learn across tickets.
  2. *Unbounded or additive vote bonus*: a popular weak fix could beat a precise one; the spec asks for a mild, bounded adjustment.
  3. *Asymmetric band (min and max configured separately)*: no-vote suggestions would then not keep their similarity as score; one weight keeps "no votes = no change".
  4. *Apply the minimum to the adjusted score*: complaints could hide a correct fix and praise could surface a wrong one.
  5. *Cut to the top 3 before applying votes*: votes could then only reorder, never bring a close fourth in.
  6. *Database upsert (`MERGE` / `ON CONFLICT`)*: different SQL on H2 and PostgreSQL; a read-then-write in one transaction plus the unique key is portable, and the rare race is a clean 409.
  7. *Accept votes only for sources currently in the ticket's top 3*: the list changes as tickets are resolved, so a technician's honest verdict could be refused a minute later; the source only has to exist.
- **Consequences**:
  1. **Tests**: `SuggestionVoteRulesTest` (17: formula, neutrality, strict bounds at a billion votes, monotonic, weight range, tallies, the vote value object, and five ranking rules), `ResolutionSuggestionServiceTest` (12, six new for votes), `SuggestionVoteRepositoryAdapterTest` (6, H2: upsert, unique key, counts per source and type, cascade, `isResolvedCase`), `SuggestionVotesMigrationH2Test` and `SuggestionVotesMigrationPostgresTest` (4 each), `SuggestionVoteRegressionTest` (5, HTTP). Six mutation checks each made tests fail (unbounded factor, minimum on the adjusted score, votes ignored in the order, upsert turned into insert, unknown source accepted, self vote allowed).
  2. **Known limits**: anyone who may view a ticket can vote, including an administrator who never worked on it; a vote is not withdrawn when its ticket is later reopened or reclassified; there is no way to remove a vote, only to change it; votes on a ticket that is later promoted to the knowledge base stay with the ticket, not the article (K3); a voter can vote on many tickets for the same source, so one enthusiastic technician can move a source to the top of the band (the band bounds the effect at 20 %).
- **Reason**: The smoothed share and the symmetric band give the "mild, bounded" adjustment the spec asks for with one parameter, keep a suggestion without votes exactly where similarity put it, and keep similarity the deciding evidence.

## ADR-042: A Small Knowledge Base of Promoted Fixes (spec feature G, Phase K3)
- **Status**: Accepted (implemented 2026-11-07, Phase K3 of the suggested-resolution plan)
- **Context**: Suggestions read only the newest `candidate-window` (200) resolved tickets of a category (ADR-040), so a good fix becomes invisible once 200 newer tickets of its category are resolved. The spec asks that a technician can promote a good resolution into a small knowledge base so it stays suggestable, that a ticket is promoted once, that only the resolver, a team lead or an administrator may promote, and that no personal data of the reporter is copied. No list, edit or delete is in scope.
- **Decision**:
  1. **Storage**: Flyway **V10** `knowledge_articles`: `id` (`KB-` + source ticket id, stable and readable, no sequence), `title` (255), `category`, `problem`, `root_cause`, `steps_taken`, `preventive_action`, `source_incident_id` -> `incidents` **unique** with `ON DELETE CASCADE ON UPDATE CASCADE`, `created_by` -> `users`, `created_at` (injected `Clock`); index on (category, created_at). There is no column for the reporter, an e-mail or a department. Tested on H2 and PostgreSQL (`KnowledgeArticlesMigrationH2Test`, `KnowledgeArticlesMigrationPostgresTest`).
  2. **Domain**: `KnowledgeArticle` (domain/model, immutable, explicit constructor, invariants, no setters). `KnowledgeArticle.promote` refuses a ticket without a confirmed resolution (status not RESOLVED, VERIFIED or CLOSED, no resolution report, or no category) with `NotResolvedException` (409 `ERR_NOT_RESOLVED`) and an actor who may not promote with `UnauthorizedOperationException` (403). **The root cause is stored too** (decision 1 of the K1 plan), because a suggestion shows it.
  3. **Who may promote, by polymorphism**: `User.canPromoteResolution(Resolution)` is false by default (employees); `Technician` overrides it to "I resolved it" (`resolution.resolvedBy()` equals my id), `TeamLead` and `Administrator` to true. The ticket's access rules apply first (the service loads it through `IncidentLifecycleService.getIncident`), so a team lead of another team gets 403 for a ticket they cannot view.
  4. **Privacy (decision 3 of the K1 plan)**: `PersonalDataRedactor` (domain/model) removes from every copied text (title, problem, root cause, steps, preventive action) the reporter's full name, every name part of at least 3 letters, the e-mail address and its local part, and the department, each as a whole word ignoring case, replaced by `[removed]`. A title that was nothing but personal data becomes "Fix from ticket <id>". The cost: a department word that is also technical ("Finance portal") is removed too.
  5. **409 rather than 400 for an unresolved ticket (decision 5 of the K1 plan)**: the request is well formed; the ticket's state forbids it, like the other status rules (ADR-028). A second promotion of a ticket is 409 `ERR_ALREADY_PROMOTED` (checked by the service; the adapter also refuses an existing id, because an assigned id would make Spring Data merge and overwrite; two promotions racing past both checks end on the unique key as 409 `ERR_CONCURRENT_MODIFICATION`).
  6. **Endpoint**: `POST /api/technician/knowledge-articles` with `{sourceIncidentId, title?}` answers **201** with `KnowledgeArticleView` (new `KnowledgeArticleController`, `KnowledgeArticleService`). A blank title means the ticket's title; a missing `sourceIncidentId` or a title over 255 characters is 400 `ERR_VALIDATION_FAILED`, broken JSON 400 `ERR_MALFORMED_JSON`, an unknown ticket 404 `ERR_SERVICE_NOT_FOUND`, employee 403, no token 401. No list, edit or delete endpoint.
  7. **Articles as a suggestion source**: the service reads the newest `article-window` (200, `iitsm.suggestions.article-window`, its own setting so the knowledge base outlives the ticket window) articles of the ticket's category as `KB_ARTICLE` candidates in one query and merges them with the ticket window in `CandidatePool`: **a promoted ticket is offered once, as its article** (the curated text, which also collects the votes). Every candidate now carries its `originIncidentId` (the ticket itself, or the ticket an article came from); `SuggestionQuery.excludes` compares it, so a reopened ticket is never offered its own article and an article of a linked duplicate is excluded too. A vote on a `KB_ARTICLE` source is accepted when the article exists (else 404).
  8. **No event, no audit entry, nothing for employees** (as ADR-040 and ADR-041).
- **Alternatives considered**:
  1. *A sequence for article ids* (`KB-000001`): needs a counter table or database sequence for a feature without volume; the derived id is unique by construction because a ticket is promoted once.
  2. *Keep the KB free of the source ticket (no foreign key)*: the source must exist when promoting and the cascade keeps renamed ticket ids in step (V4 renamed ids once); tickets are never deleted by the application.
  3. *400 for an unresolved ticket*: it reads as "your JSON is wrong", which it is not.
  4. *Only check the reporter as a field and copy the text verbatim*: the ticket description is written by the reporter and often starts with their name; the spec says no personal data of the employee.
  5. *A generic personal-data detector (names, phone numbers)*: out of scope and error-prone; the redactor removes what the system knows about the reporter and says so.
  6. *Suggest both the ticket and its article*: the same fix twice in a list of three.
  7. *Move the ticket's votes to the article on promotion*: votes are opinions on a text; the article's text can differ (title, redaction), so it starts with none.
  8. *Role checks (`instanceof`, role enum) in the service*: the rule lives with the user types (Tell, Don't Ask).
- **Consequences**:
  1. **Tests**: `KnowledgeArticleTest` (18: who may promote, which ticket for every status, content and redaction, titles, invariants, the redactor's whole-word and e-mail rules, the candidate pool), `ResolutionSuggestionServiceTest` (+2: articles join the window and replace their ticket, article votes), `SuggestionValueObjectsTest` (+2, the old "an article with the ticket's id is not excluded" test replaced by "exclusion is by origin"), `KnowledgeArticleRepositoryAdapterTest` (4, H2), `KnowledgeArticlesMigrationH2Test` and `KnowledgeArticlesMigrationPostgresTest` (4 each), `KnowledgeBaseRegressionTest` (6, HTTP), `KnowledgeBaseWindowRegressionTest` (1, the reason for the feature: with a one-ticket window the article is still suggested). The suggestion regression classes now delete the resolutions of the tickets they create, so their identical texts never crowd another class's top 3 in the shared test database. Seven mutation checks each made tests fail (redaction off, second promotion allowed, any technician allowed, unresolved ticket allowed, promoted ticket offered twice, own article not excluded, articles left out).
  2. **Known limits**: only the reporter's known data is removed (a colleague's name, a phone number or a customer name written in the text is copied); the redaction also removes a department word used technically; an article cannot be edited, listed or deleted (out of scope), so a bad article stays; the article does not follow later changes of its ticket (reopen, new resolution, reclassify); old resolutions whose `resolvedBy` is a login e-mail (before ADR-037) can only be promoted by a team lead or an administrator; more than `article-window` articles of a category hide the oldest.
- **Reason**: Articles keep a good fix suggestable for as long as it is useful at the cost of one small table and one query per request; deriving the id, putting the rule in the user types and the redaction in one domain object keep each decision testable on its own.

## ADR-043: Suggested Fixes and Promotion in the Web App (spec feature G, Phase K4)
- **Status**: Accepted (implemented 2026-11-08, Phase K4 of the suggested-resolution plan)
- **Context**: Phases K1 to K3 (ADR-040 to ADR-042) built the API. The spec asks for a "Suggested fixes" control on technician ticket cards that loads on demand and shows up to three suggestions (score, source, root cause, steps, vote buttons and counts), and a "Promote to knowledge base" control on resolved tickets for the allowed roles. The project rules apply: vanilla JavaScript in `app.js`, no inline handlers, no CDN, every dynamic value through `escapeHtml`, the in-flight guard against double clicks, friendly messages and a refresh after a refused write (ADR-039), focus handling like the other dialogs, and a new asset version.
- **Decision**:
  1. **Where**: on the technician cards (`renderTechnicianQueue`, used by the technician's own and team modes and by team leads). An open ticket (not RESOLVED, VERIFIED or CLOSED) shows **"Suggested fixes"** (`btn-tech-suggest`); a resolved ticket shows **"Promote to knowledge base"** (`btn-tech-promote`) only when the server says so.
  2. **`promotable` comes from the server (decision 7 of the K1 plan)**: `TechnicianIncidentView.promotable` is `Incident.canBePromotedBy(viewer)`, the same rule as `KnowledgeArticle.promote` (confirmed resolution with a category, and `User.canPromoteResolution`: the resolver, a team lead or an administrator). `TechnicianController` passes the signed-in user to the mapper for every technician view (queue, team queue, detail and the action answers). The front end tests `t.promotable === true` and keeps no copy of the rule. Whether the ticket was already promoted is not in the flag (it would cost a query per card); the server's 409 answers that.
  3. **On demand**: drawing the list never asks for suggestions. The button opens the shared action dialog (`openModal`, so the Tab trap and the focus return of ADR-039 apply) and only then calls `GET .../suggested-resolutions`. A late answer for a dialog that was closed or replaced is discarded (`STATE.suggestions.requestSeq`, as the admin ticket dialog does).
  4. **Dialog content**: per suggestion the source ("Resolved ticket" with the staff ticket name, or "Knowledge base" with the article id), similarity and score with three decimals, title, root cause, steps, preventive action, the matched terms, and two vote buttons with their counts ("This worked n", "Didn't work n"). The empty answer says "No similar past fix was found for this ticket." Every value goes through `escapeHtml`, numbers through `formatSuggestionScore` / `suggestionVoteCount`.
  5. **Votes**: through `apiCall` (in-flight guard; refresh of the open tab after a refused write). After every vote, accepted or refused, the dialog is drawn again from the server, because the counts and the order change. The vote buttons are `btn-tech-vote-worked` / `btn-tech-vote-failed` with the source id as `data-id`, so `restoreFocus` gives keyboard focus back to the redrawn twin.
  6. **Promotion**: a small dialog with an optional title (placeholder: the ticket's title; blank sends `null`, the server uses the ticket's title) and a note that the reporter's personal data is removed. The submit has its own in-flight flag (`STATE.suggestions.promoteInFlight`) because Enter pressed twice is not a click and so is not covered by the click-based guard. Success: a toast naming the article and the list is reloaded. Refusal: a friendly message (`ERR_ALREADY_PROMOTED`, `ERR_NOT_RESOLVED`, `ERR_NOT_FOUND`, 403, 404), and the dialog closes unless the answer was a 400 (the user can correct the title).
  7. **Styles**: a new section in `styles.css` (`.suggestion-*`); asset version **3.9** for both files.
  8. **Not in the admin Command Centre**: administrators may promote and see suggestions through the API, but the spec places the controls on technician cards and the administrator's screen has no technician cards; adding them to the admin ticket dialog would be a feature the spec does not list.
- **Alternatives considered**:
  1. *A panel expanded inside the card*: lost whenever the list is redrawn (after any write or refresh); the dialog survives a redraw and already has focus handling.
  2. *Fetch suggestions with the queue*: one request per card on every list render; the spec asks for on-demand loading.
  3. *Decide "promotable" in JavaScript from the role and `resolution.resolvedBy`*: a second copy of the domain rule that can drift; the server already knows the viewer.
  4. *Hide "Promote" after a promotion*: needs a knowledge-base lookup per card; the 409 message tells the user the same.
  5. *Update only the counts after a vote*: the order can change too (votes move the score); one redraw from the server is simpler and always right.
- **Consequences**:
  1. **Tests**: `SuggestedResolutionMarkupTest` (8: card buttons and the `promotable` rule, on-demand loading, late answers, escaping of every card value, writes through `apiCall` and the promote guard, friendly messages, focus prefix, styles, no inline handlers, asset version), `KnowledgeArticleTest` (+1: `Incident.canBePromotedBy` matches `promote`), `KnowledgeBaseRegressionTest` (+1: the flag over HTTP for resolver, lead, open ticket, the queue, and nothing in the employee view); changed on purpose: the six markup tests that pin the asset version (3.9). New browser script `scripts/live-checks/suggestions_browser.py` (Edge, 24 checks). Seven mutation checks each made a check fail: five of the front end against the browser script (root cause not escaped, late-answer guard removed, promote guard removed, no redraw after a vote, suggestions offered on resolved tickets) and two of the back end against the tests (the flag ignores who the viewer is, the controller passes no viewer).
  2. **Live scripts repeatable**: the three API live checks and the browser script resolve the open tickets they create at the end (otherwise TECH-NET-1 ran out of capacity after a few runs) and give tickets A and B four words that only that run uses. Without those words a repeated run failed: the open tickets of earlier runs, once resolved, are word-for-word clones of the new B, so three of them tied at similarity 0.636 and filled the whole top 3 ahead of the run's own A (found by printing the scores; always the same three ids). Unseen words weigh most in TF-IDF, so four shared ones put the run's A well above clones that carry other unique words. The scripts now pass four rounds in a row on one database.
  3. **Known limits**: the controls are on technician cards only (not in the admin Command Centre); "Promote" stays visible after a promotion (the second click gets the 409 message); the employee screen has none of it (by design); a lost race of two promotions of the same ticket answers a clean 409 but Hibernate logs the unique-key violation at ERROR level once; the browser run uses Microsoft Edge only; there is no JavaScript unit-test runner, so structure is pinned as text and behaviour by the browser script; one early browser run failed once on the first card lookup (queue card not drawn within 15 s) and did not reproduce in later runs (not explained); **near-identical resolved tickets can fill the whole list**: ranking has no diversification, so three word-for-word similar past fixes show the same fix three times and hide a slightly less similar one, including an article (seen in the live checks, ADR-040's top-N rule works as specified); the API live checks need a few seconds after start-up before the seeded accounts accept a login.
- **Reason**: The dialog reuses the focus and write rules every other technician action already follows, the server stays the only place that decides who may promote, and loading on demand keeps the queue as cheap as before.

## ADR-044: Explainable Technician Assignment and Offline Strategy Comparison (spec feature D, Phases L1 to L3)
- **Status**: Phases L1 (explainable ranking in the domain), L2 (a decision recorded on every assignment path, the administrator's "Why this technician") and L3 (offline strategy comparison) accepted and implemented 2026-11-08. Phase L4 (a service-experience factor, which changes production assignment) was approved by the user after L3 and implemented the same day.
- **Context**: Spec feature D ("Smart Technician Recommendation") and the "Intelligent Technician Assignment" section ask the system to say *why* a technician got a ticket and, for the project report, *why* the default strategy was chosen. `AssignmentStrategy.recommend` returned one technician, a score and a free-text rationale; nothing showed how the other candidates scored. `WeightedCompositeStrategy` computed skill, load and experience inline with magic numbers (rule 15) and picked the first best on a strict `>`. `SkillBasedStrategy` has a load penalty (0.10 x load ratio) that no document mentioned. `RoundRobinStrategy` advances a shared counter on every `recommend`, so "explain the choice" and "make the choice" could not be separated. The registry is a live singleton.
- **Decision (Phase L1)**:
  1. **Value objects** (domain, records, lists copied): `FactorScore(factorKey, rawScore, weight, contribution, detail)` with `contribution = rawScore x weight` computed by the factory, and `CandidateScore(technicianId, factorScores, total, rank, chosen)` where exactly rank 1 is chosen. A weight of 0 marks a tie-break-only factor (shown, but not scored); a negative weight marks a penalty (skill-based `LOAD_PENALTY`, weight -0.10).
  2. **Strategy contract**: `AssignmentStrategy` gains `rank(incident, candidates) -> List<CandidateScore>` (best first, no side effect) and `freshInstance()` (stateless strategies return `this`, round robin a new instance; used by the L3 replay). `AssignmentRecommendation` gains a fifth component `ranking`; the four-argument constructor stays, so existing callers and test stubs compile unchanged. The default `rank` serves strategies written before this ADR (it returns the ranking their recommendation carries, or the chosen technician alone with one `STRATEGY_SCORE` factor); because it calls `recommend`, a strategy with state must override it, as round robin does.
  3. **One ranking, one choice**: every built-in strategy scores the candidates once into `RankedCandidates` (domain); `recommend` takes its top entry and attaches the same ranking, `rank` returns it. The recommendation therefore cannot disagree with its explanation, and a real assignment carries the explanation computed with the state that made the choice (L2 stores it without recomputing). Ranking is a **stable** sort by the strategy's own order (total for the weighted strategies; load then experience for load-based; experience then load for experience-based), so equal candidates keep their input order and the first one wins, exactly as the old strict `>` loops and `Stream.min/max` did.
  4. **Round robin**: `rank` reads the rotation position (`counter.get()`) and lists the candidates in the order the rotation will serve them; `recommend` takes and advances the position in one atomic `getAndIncrement` and builds its explanation from that same index. Every candidate scores 0.80 (the old constant); the factor `ROTATION` carries "queue slot #k of n, turn t in the rotation".
  5. **Factor extraction (Open/Closed)**: `AssignmentFactor` (key, label, `read(context, technician) -> Reading(rawScore, detail)`) with `SkillMatchFactor`, `LoadFactor`, `ExperienceFactor(fullScoreYears)`; `SkillEvidence` counts skill matches once for both skill-aware strategies; `AssignmentContext` reads the ticket text once per ranking; `FactorWeights` holds the weights per priority (P1/P2 0.45/0.20/0.35, P3 0.50/0.30/0.20, P4 0.30/0.50/0.20 for skill/load/experience) and refuses a priority whose weights do not sum to 1. `WeightedCompositeStrategy(List<AssignmentFactor>, FactorWeights)` accepts more factors (L4 would use this); the no-argument constructor builds the historic three. Every number is a named constant; the two experience scales stay as they were (12 years in the composite, 15 in the experience strategy).
  6. **Characterization first**: before the refactor, `AssignmentStrategyCharacterizationTest` recorded 456 observations from the unchanged code into `src/test/resources/assignment/strategy-characterization.txt`: the four stateless strategies x 11 tickets (P1 to P4 for two categories, a token-only match, two unclassified tickets) x 8 candidate lists (all, reversed, one, exact tie in both orders, experience tie in both orders, mixed) plus the empty and the null list, and a 15-call round-robin sequence; each line holds the chosen technician, the exact score (`Double.toString`), the strategy name and the rationale text. The refactored code reproduces every line bit for bit. The unreachable fallback branches of the composite and skill-based loops (a best score below -1) were removed; the characterization confirms no case reached them.
  7. **Decisions taken with the user for later phases** (2026-11-08): the L3 simulator lets a technician work on **several tickets at the same time, up to `maxCapacity`** (the live app already lets a technician hold and acknowledge several tickets; no bulk-acknowledge feature is added); the comparison endpoint defaults to seed 42, 500 tickets and 10 replications, with maxima of 5000 tickets, 50 replications and 50,000 tickets x replications per request; Phase K4 was committed before L2 starts; no `PROMPT.md` is created (the Operating Protocol's reference to it is covered by `CLAUDE.md`, this ADR and the user's task text).
- **Alternatives considered**:
  1. *Make `rank` abstract on the interface*: forces every custom strategy (including the OCP test's anonymous one) to change; the default keeps old strategies working and still explains them.
  2. *Derive `recommend` from `rank` in a default method*: the rationale texts differ per strategy and are pinned by the characterization; each strategy keeps its own text but builds it from the top of its own ranking.
  3. *Rank by the total only*: load-based and experience-based rank by two keys, so equal totals would hide their tie-break; each strategy keeps its own order and shows the tie-break factor with weight 0.

- **Decision (Phase L3, implemented 2026-11-08: offline strategy comparison)**:
  1. **Where it lives**: a pure domain package `com.iitsm.domain.simulation.assignment` (no Spring, no Jakarta, no repository, no clock; `SimulationSourceContractTest` reads the sources and refuses `Instant.now`, `Clock`, `Math.random`, an unseeded `Random`, threads and any import of the repository, event, application, infrastructure, web or live-simulation packages), a facade `StrategyComparisonService` in the application layer, and `POST /api/simulation/strategy-comparison` in the existing administrator-only `SimulationController`. It is **not** part of `SimulationService` (scenarios S1 to S5): that one runs against the live services, the live database and the shared `AdjustableClock`; this one touches none of them.
  2. **The engine** (`StrategyReplay`, a discrete-event simulation): one `PriorityQueue` of events (arrival and completion; ordered by virtual time, then completion before arrival so a slot that frees at an instant serves a ticket arriving at that instant, then insertion order) and one waiting `PriorityQueue` per category ordered by the production `IncidentUrgencyOrdering` (priority, then SLA deadline, then arrival). Tickets of one category all see the same candidate pool, so the next ticket to serve is the most urgent among the heads that can be served now, which equals scanning a single queue in urgency order without its cost. Candidates come from the **real** `CandidateFilter.route` (ADR-036: the owning team's technicians with free capacity, then skilled technicians of other teams, otherwise the ticket waits) and the strategy is asked through its public `recommend`, so the replay measures what production would do. A strategy that picks a technician it was not offered is refused (`IllegalStateException`); tickets nobody can ever serve fail loudly instead of being dropped (the stream only draws categories the pool can serve, so this cannot happen from the API).
  3. **Capacity model** (the user's decision of 2026-11-08): a technician works on **several tickets at once, up to `maxCapacity`**; a ticket that finds nobody with capacity waits. Because independent parallel work would make load cost no time (and the load-based strategy pointless), the work-time model adds one assumption of its own, recorded here and returned with every result: a ticket is slower by `penalty x (tickets already in service / capacity)` at the moment it starts (default penalty 0.30; 0 gives independent parallel work), and its service time does not change afterwards. This is the softest assumption of the model; the benchmark shows how the result moves when it is 0, 0.30 or 0.60.
  4. **Work-time model** (`WorkTimeModel`, named constants, all returned in the response): service time = base minutes of the priority (P1 40, P2 75, P3 150, P4 240) x category factor (0.8 authentication to 1.3 security) x skill factor (1, or 1.6 for a technician without a skill of the ticket's category) x experience factor (linear from 1.25 at 0 years to 0.80 at 12 years or more) x concurrency factor x the ticket's own noise (log-normal, mean 1, sigma 0.35, drawn once per ticket). Resolution time runs from arrival to the end of service, waiting included. These are modelling assumptions, not measurements; the notice on every result says so.
  5. **Streams and common random numbers** (`TicketStreamGenerator`, `StrategyComparison`): arrivals are a Poisson process (exponential gaps from `RandomGenerator.nextExponential`), priority mix P1 5 %, P2 15 %, P3 50 %, P4 30 %, a fixed category mix restricted to the categories the pool can serve, one of three text templates per category (technical words, so skill-name matching works), the noise drawn once. The draws happen in a fixed order per ticket. The generator is a seeded `SplittableRandom`; replication `r` uses `root.split()` number `r`, so replication `r` is the same whatever the number of replications (tested). The stream is generated **once per replication** and replayed through every strategy; tickets are in-memory `Incident`s `SIM-000001...` built without any sequence or repository and shared by the strategies of that replication (a spy strategy proves every strategy is asked about exactly the same tickets).
  6. **Strategies**: from `AssignmentStrategyRegistry.getAllStrategies()` (a strategy registered later is compared automatically, tested), sorted by name; each replay uses `strategy.freshInstance()` (decision of L1: stateless returns itself, round robin a new rotation), so the live round-robin rotation never moves (tested over HTTP against the real registry). The **reference** for the paired differences is `WEIGHTED_COMPOSITE` (the system default), or the first strategy by name when it is not among those compared.
  7. **Pool**: copied by value from the roster (`TechnicianProfile.of`, read only) and **sorted by id**; the category to team map comes from `SupportTeamRepository.findByHandledCategory` through `RoutingPolicy` (smallest id first, like the live rule). Without a usable roster (empty, or serving no category) a small invented pool is used (`SimulationPool.syntheticDefault()`: three teams of four) and the response says `poolSource: SYNTHETIC`. The sort was added after a test showed the result depended on the order the database returned the roster (the order breaks ties between equal candidates).
  8. **Metrics** (`ReplayMetrics`, all "lower is better"): mean and 95th percentile (nearest rank) of the time to resolve; SLA resolution breach rate (resolution time strictly above the repository's resolution target of the ticket's priority, `Map<Priority, Duration>` passed in); mean wait before assignment; maximum queue length; share of tickets given to a technician without the category skill; Gini coefficient of the tickets handled and of the busy minutes over **every** technician of the pool (one who handled nothing counts as 0). `GiniCoefficient` is a small tested class: all equal gives 0, one with everything gives (n - 1) / n, an empty list, one technician or all zeros is defined as 0 (nothing to measure), the result is always in [0, 1).
  9. **Statistics** (`ReplicationStatistics`): per metric and strategy the value of every replication, the mean, the sample standard deviation and the 95 % half width `t x s / sqrt(R)` (t tabulated up to 30 degrees of freedom, a Cornish-Fisher term above); for every strategy but the reference the **paired difference** against the reference, replication by replication (the replications are paired because every strategy replays the same stream), its half width and `distinguishable` (the interval excludes 0; never with one replication). The winner of a metric is the strategy with the lowest mean (all tied strategies are named). No test asserts that a particular strategy wins: that depends on the model; the tests assert ranges, consistency, determinism and the invariants (every ticket served, no technician above capacity at any virtual time by a sweep over the intervals, totals add up).
  10. **API** (`POST /api/simulation/strategy-comparison`, administrator only, read-only and idempotent): body `{seed, ticketCount, replications, arrivalsPerHour, strategies}`, every field optional (defaults seed 42, 500 tickets, 10 replications, 15 tickets per hour, all strategies); bounds in the domain (`ComparisonParameters`): ticketCount 1 to 5000, replications 1 to 50, **ticketCount x replications at most 25,000**, arrivalsPerHour 0.1 to 1000, strategy names known (trimmed, case-insensitive, de-duplicated). A bad value is HTTP 400 `ERR_VALIDATION_FAILED` naming the field (ADR-027), an unknown strategy lists the valid ones, a broken or mistyped body is `ERR_MALFORMED_JSON`, no token 401, any other role 403, GET 405. The answer holds the parameters used, the reference, the pool source and size, the metric descriptions, per strategy and metric the mean, standard deviation, 95 % half width, every replication's value and the paired difference, the winners, the assumptions, the run time and the notice "Simulated results from a synthetic work-time model, not production data". It is equal for equal requests except the run time. The default arrival rate (15 per hour) was chosen by running the model: it is busy but stable (about 40 % of the seeded roster's capacity overall, about 75 % for its busiest team); 40 per hour overloaded both pools and queueing swamped the differences between strategies.
  11. **No side effects**: the service has no writing repository, no event publisher, no notification channel, no `Clock` and no way to change the registry's active strategy (a reflection test pins its constructor); it reads the roster, the owning teams and the SLA targets in **one short read-only transaction** (`TransactionOperations`) and runs the experiment outside it, so no database connection is held while it computes; the run time is measured with `System.nanoTime()` (an elapsed-time counter), because the application clock is the live `AdjustableClock`, which the simulation must not read. `StrategyComparisonNoSideEffectsRegressionTest` proves over the real database, clock, event publisher and registry that row counts and versions, the clock, the published events, the active strategy and the live round-robin rotation are the same before and after, and that no `SIM-` id reaches any table.
  12. **Panel** (Simulation tab, `#strategy-comparison-card`, section 17 of `app.js`): seed, tickets and replications (the three inputs of the brief), a run button, a status line, the notice, the results table (strategies as rows, the eight metrics as columns, each cell the mean, the 95 % half width and the difference to the reference), the best value of every column highlighted (ties all highlighted), a dot where the difference is larger than chance, the summary line and the assumptions. A second click or Enter while a run is in progress sends nothing (`strategyComparisonInFlight`); the three values are checked before sending (friendly message, nothing sent); a refused value shows the server's explanation, a 403 says who may run it; signing out clears the result (administrator data); every dynamic value goes through `tdEsc`; no inline handlers, no CDN, no charts; asset version **4.1**.
- **Alternatives considered (Phase L3)**:
  1. *Run the comparison through `SimulationService` and the live services with the shared clock*: it writes tickets and notifications and moves the clock; the brief forbids all three.
  2. *One global waiting queue scanned in urgency order*: the same result, but every completion walks the whole queue (thousands of tickets in an overload); one queue per category with a check of the heads is exact and cheap.
  3. *Parallel replications*: faster, but the thread pool, the shared strategies and the order of results would put determinism at risk for a request that already takes a second or two.
  4. *Processor sharing (a ticket's service time changes whenever the technician's other tickets start or end)*: more realistic and much more complicated to implement and to explain; a fixed service time with a concurrency penalty at start keeps the model explainable in one sentence.
  5. *Independent random streams per strategy*: the differences between strategies would be swamped by luck; the paired design needs the same stream.
  6. *A normal approximation of the interval*: wrong for 3 to 10 replications; the t distribution is used.
  7. *Mean time to resolve from production data*: there is not enough history, and the point is to compare strategies on the same load.
  8. *An asynchronous job with a status endpoint*: a request takes about a quarter of a second to under a second at the defaults; a job queue would be more machinery than the feature.
  9. *The earlier proposal of 50,000 tickets x replications*: measured at about 16 s, too long for a synchronous request; halved to 25,000 (1.2 s measured for the 25,000 ticket replays of the cap).

- **Decision (Phase L4, implemented 2026-11-08: the service-experience factor; this phase changes production assignment)**:
  1. **What it is**: `ServiceExperienceFactor`, a new `AssignmentFactor` (key `SERVICE_EXPERIENCE`, label "Service"): the number of tickets of the ticket's IT service that the technician has resolved, divided by 5 and capped at 1 (`iitsm.assignment.service-experience-full-score-tickets`, default 5). It was added by writing a new class and registering it with its weight; `SkillMatchFactor`, `LoadFactor`, `ExperienceFactor` and every other strategy are unchanged (the Open/Closed point of ADR-044).
  2. **Fed through a domain port, not a repository**: `ServiceExperienceSource.resolvedTicketCounts(serviceId, technicianIds)` (domain interface, a functional one; `ServiceExperienceSource.none()` knows nothing). The weighted composite makes **one lookup per ranking** for all candidates, only when the factor is configured and the ticket has a specific service, and carries the answer in the immutable `ServiceExperience` inside the `AssignmentContext`; the factor reads the context, so no strategy or factor queries anything. The application adapter `ServiceExperienceAdapter` (infrastructure, `@Component`) answers with one grouped read-only query over `resolutions` joined with `incidents` (service id, resolver, status in RESOLVED, VERIFIED, CLOSED: a ticket the employee sent back is in progress again and does not count until it is resolved again). It joins the assignment's transaction. A ticket without a service, or with the general service (`SRV-GEN-001`, "no specific service matched"), makes the factor score every candidate 0 and costs no query.
  3. **Weights keep summing to 1.0**: `FactorWeights.withFactor(key, w)` scales every existing weight of every priority by `1 - w` and gives the new factor `w` (the table refuses a priority whose weights do not sum to 1). At the default w = 0.10 the P3 weights are skills 0.45, load 0.27, experience 0.18, service 0.10 (P1/P2: 0.405, 0.18, 0.315, 0.10; P4: 0.27, 0.45, 0.18, 0.10). The factor appears in the stored decision and in the administrator's "Why this technician" table as one more column ("Service experience", `raw x weight = contribution`, with the detail "n ticket(s) of this service resolved (full score at 5)"), with no change to the decision, JSON or API format.
  4. **Configurable, with a kill switch**: `iitsm.assignment.service-experience-weight` (env `ASSIGNMENT_SERVICE_EXPERIENCE_WEIGHT`), default **0.10**, valid 0 to 0.5 (a larger or negative value stops the start-up with a message naming the property: skills, load and experience must stay in charge). **A weight of 0 is exactly the historic strategy**: `withServiceExperience(source, 0, n)` returns `new WeightedCompositeStrategy()`, never asks the source, and reproduces every recorded line of the pre-L4 golden file bit for bit (`ServiceExperienceCharacterizationTest`). The default is written twice (the shipped `application.yml` and the `@Value` fallback, which is what the test profile sees because it has its own `application.yml`); `ServiceExperienceConfigContractTest` pins that they agree and equal the chosen weight. `AssignmentStrategyRegistry` gained a constructor that takes the configured default strategy (the no-argument constructor is unchanged, so every existing test and caller is untouched).
  5. **The offline comparison keeps its promises**: `WeightedCompositeStrategy` is `ServiceExperienceBindable`; `StrategyReplay` re-binds any such strategy to **its own in-memory counts** (tickets resolved so far in the replay) before the replay, so a strategy wired to the real database never reads it during a simulation (tested with a source that fails the test if touched). Without the familiarity assumption the replay shows the strategy no experience at all, so the default comparison of Phase L3 ranks exactly as before. The simulator gained, as options used by the benchmark and tests only (the endpoint's body is unchanged): `SyntheticTicket.serviceId` (a second constructor keeps the old call sites), `TicketStreamGenerator.withServices` (services per category drawn from a generator split off after the base stream, so the base stream is identical), `WorkTimeModel.withServiceFamiliarity(speedup, fullTickets)` (time x `1 - speedup x min(1, resolved / fullTickets)`, off by default), `StrategyComparison(model, servicesPerCategory)`, and `WeightedCompositeStrategy.named(...)` so weight variants can be compared side by side.
  6. **Choosing the weight with the simulation** (`ServiceExperienceWeightBenchmarkTest`, report `target/benchmarks/service-experience-weights.txt`): the composite at weights 0, 0.05, 0.10, 0.15, 0.20, 0.30, 0.40 and 0.50 replayed on the same seeded streams (1,000 tickets x 10 replications, seed 42, 2 services per category, full score at 5) under three familiarity assumptions (no speed-up, 15 %, 30 % faster) and three arrival rates (8, 15, 25 per hour), on two pools: the invented pool (one skill per technician) and a **control pool** where every technician has all the skills of their team (like the seeded roster). **The first sweep was misleading and the rule changed twice after seeing numbers**: (a) the first rule was evaluated on the invented pool only, where the factor helped even with no familiarity speed-up (mean time -3.8 min, unskilled assignments 10 % -> 6 %), because there "has resolved this service before" also tells who has the right skill: a proxy effect of that pool, not familiarity; (b) rule (d) "no harm without benefit" was moved to the control pool, where that proxy cannot exist; (c) the fairness condition first looked only at the Gini of tickets on the invented pool (where it fell) and was then applied on the control pool with the Gini of busy time too, where the factor does cost fairness. **Final rule**: the largest weight that, on the control pool at 15 tickets per hour, (a) shortens the mean time to resolve distinguishably when familiarity really gives a 30 % speed-up, (b) changes it by less than 1 % when familiarity gives no speed-up at all, and (c) at 30 % raises the Gini of tickets handled by at most 0.05 and the Gini of busy time by at most 0.10; the factor stays off if none passes. **Result: 0.10** (0.05 and 0.10 pass; 0.15 fails (c): busy-time Gini +0.107; larger weights fail more).
  7. **What the sweep says, without sugar** (control pool, 15 per hour, weight 0.10 against 0): with a real 30 % familiarity effect the mean time to resolve falls by 4.3 min (3.3 %, 128.6 -> 124.3), with 15 % by 2.5 min (1.7 %), with none it is neutral (-0.8 min, within 0.5 %); in every case the work concentrates on the technicians with history: Gini of tickets handled +0.03 to +0.04 (0.50 -> 0.54 at 30 %) and Gini of busy time +0.05 to +0.07; the SLA breach rate moves by about a tenth of a percentage point (0.0485 to 0.0498 with no familiarity, 0.0200 to 0.0208 at 30 %). So the gain exists only if familiarity really speeds technicians up (an assumption of the model, not a measurement), the cost in evenness of work is certain, and the default weight is a conservative compromise, not an optimum; the real effect must be measured in production, and the weight is one environment variable to change or switch off.
- **Alternatives considered (Phase L4)**:
  1. *Count every ticket a technician resolved, not only of this service*: that is the existing experience factor (years); the point of the factor is the service.
  2. *Query the repository inside the factor or the strategy*: breaks the "strategies depend on interfaces and never on repositories" rule and would make the offline simulation read the real database; the port with a single batched lookup keeps both.
  3. *Cache the counts or keep a counter column per technician and service*: one grouped query per assignment is cheap at this size (see the limits) and cannot drift from the real resolutions; a counter table can be added behind the same port if it ever matters.
  4. *Redistribute the weight of the other three factors by a fixed table*: scaling by `1 - w` keeps their proportions and their tuning by priority, and w = 0 is then exactly the old table.
  5. *Default weight 0 (feature shipped off)*: the safest, but the brief asks for a weight chosen by the simulation and a factor shown in the breakdown; 0.10 is small, neutral where it cannot help, and one environment variable from off. Recorded as a decision the product owner can reverse.
  6. *Pick the weight that gains most (0.30 to 0.40)*: gains 7.5 min instead of 4.3 at 30 % familiarity but raises the Gini of busy time by 0.17 to 0.19 (work piles on the few technicians with history); rejected by rule (c).
  7. *Select the weight on the invented pool only*: the first rule did, and it would have chosen 0.15 for the wrong reason (a skill proxy). Kept in the report file as the first sweep.
- **Consequences (Phase L4)**:
  1. **Tests** (suite 1549 -> 1598): `ServiceExperienceTest` (8: applicability, counts, port, factor score, weight table), `WeightedCompositeServiceExperienceTest` (13: zero weight = historic and never asked, one lookup per ranking, none without a specific service, experience breaks a tie, no history or equal history changes no ranking, rank = recommend, `bindExperience`, `named`, bounds, registry constructor), `ServiceExperienceCharacterizationTest` (3: weight 0 reproduces the pre-L4 golden lines; the 88 recorded L4 observations at weight 0.10 in `service-experience-characterization.txt`; history changes some choices and none for tickets without a service), `ServiceFamiliaritySimulationTest` (12: what the replay shows a strategy, counts at completion, no experience without familiarity, the real source never read, speed-up, factor values, assumptions, `withServices` leaves the base stream alone, deterministic experiment with services), `IntelligenceConfigServiceExperienceTest` (4), `ServiceExperienceConfigContractTest` (1), `ServiceExperienceAdapterTest` (4, real schema), `ServiceExperienceAssignmentRegressionTest` (3, end to end through the real intake and the administrator's detail), `StrategyComparisonBenchmarkTest` unchanged, `ServiceExperienceWeightBenchmarkTest` (report-only). Changed on purpose: `AssignmentExplanationAccessRegressionTest` (the default decision now has four factors), the nine markup tests that pin the asset version (4.2: the dialog labels the new factor "Service experience").
  2. **Mutation checks** (each made tests fail, then undone): the historic weights not scaled; experience looked up for a ticket without a service; a sent-back ticket counted; the replay not re-binding the strategy (it would read the real source); the replay never counting a resolved ticket; a zero weight that is not the historic strategy; the general service treated as specific; the production default weight 0. Two first attempts did nothing (a sed pattern that did not match, and a change to the shipped yml that the test profile shadows); both were redone and the second led to `ServiceExperienceConfigContractTest`.
  3. **Live check** `scripts/live-checks/service_experience_check.py` (API and Edge): two VPN tickets resolved by one technician, a new VPN ticket whose decision has the factor for every candidate with weight 0.10, weights summing to 1, contribution = raw x weight, the experienced technician's raw score at least 0.4, a payment ticket (another service) not inheriting it, and the dialog's "Service experience" column and cells.
  4. **Known limits (L4)**: the benefit rests on the familiarity assumption, which is not measured (see 7); the factor concentrates work on technicians with history (fairness cost, 7), and with the default weight a technician who once solved a service's problem keeps attracting them until others catch up (full score at 5 tickets); history is the number of resolved tickets since the database began, with no decay and no weighting by recency or difficulty; resolutions stored with a login e-mail as resolver (before ADR-037) do not match a technician's id and count for nobody; the lookup is one grouped query over `resolutions` per assignment with no index on `resolutions.resolved_by` (fine at this size, to be added if the table grows large); a ticket of a service nobody has resolved yet ranks exactly as before; the fourth factor makes composite totals smaller whenever a ticket has no specific service (every candidate gets 0 of the 0.10), which changes totals but never the order; the 25,000 cap and the other L3 limits are unchanged.

## ADR-045: Team Lead Console Fixes (Phases M1 to M5)
- **Status**: Phases M1 (correct data on the panel), M2 (refresh), M3 (the lead can change the technician), M4 (dead or misleading buttons) and M5 (end-to-end proof) accepted and implemented 2026-11-19. Nothing is committed, at the user's instruction. The four open questions of the plan were not answered (the user was away and asked for the recommended choices to be taken): see decisions M3.1 to M3.4 below.
- **Context**: A run of the live app as the Network lead (2026-11-18) showed the server handles the lead's tickets correctly, and found twelve problems on the Team Lead tab itself. Phase M1 covers the five that show wrong data: (8) every technician showed no load because the screen read `activeIncidentsCount` while the API sends `activeIncidentCount`; (9) "Domain" and "Tier" were always the defaults "Engineering" and "L2" because the screen read `domain` and `designation`, which the API never sends; (10) the roster listed all 24 technicians of every team; (11) the escalation list kept resolved and closed tickets (the team queue holds every status) and the unassigned list used `!assigneeId || status === CLASSIFIED`; (12) the escalation card said "> 90% Threshold" and "Tier 2" while it listed anything at risk, put every P1 in it whatever its SLA state, and showed a missing priority as "P1".

The route and the roles (`ADMIN`, `TEAM_LEAD`) are unchanged, so no API break. `UserService.getAllTechnicians` stays for callers that need everyone.

  3. **Open tickets only**: one helper `isOpenTicket` (not RESOLVED, VERIFIED or CLOSED) feeds both lists. Unassigned = open and no assignee. Escalations = open and SLA status BREACHED, AT_RISK or WARNING.
  4. **A priority alone is not an escalation**: the P1 shortcut was dropped (a P1 on track is on the technician's normal list, and a P1 at risk is listed because of its SLA state). The card is titled "SLA Escalation Monitor (At Risk or Breached)" with a matching subtitle and empty text; the pill always shows the real SLA status; a missing priority shows "-".

  1. *Filter the roster in the browser by the lead's team id*: the API would still send all 24 technicians (emails, skills, load of other teams) to a lead; the scope belongs on the server.
  2. *Add `domain` and `designation` to `TechnicianSummaryDto`*: invents data the domain does not have (a technician has a support team and skills, no tier); showing the skill categories and role is honest and needs no API change.
  3. *Keep the P1 shortcut*: it listed on-track P1 tickets under an SLA warning title; the technician's own queue already sorts by urgency.

The lead still cannot change a technician (M3), the panel still refreshes only on demand (M2) and "Auto-Dispatch All", "Acknowledge & Handle" and "Inspect Escalation" are unchanged (M4).
- **Decision (Phase M2)**: the tab stays current and does not flicker (findings 1 to 3).

It reloads only when the Team Lead tab is the active tab, the browser tab is visible (`document.hidden`), no dialog is open (`openDialogElement()`), no write is running (`pendingWrites`, a counter kept by `apiCall` for every non-GET call) and no load is already waiting (`STATE.teamLead.inFlight`). A `visibilitychange` listener reloads at once when the browser tab becomes visible again. Opening the tab already reloaded it (`switchTab`).

The panel makes two requests every 10 s per open Team Lead tab. Each load still reads the whole team queue (every status), so a very large history makes the reload heavier (item for a later page-size change, not in this plan). Pinned by `TeamLeadRefreshMarkupTest` and checked in Edge by `scripts/live-checks/team_lead_refresh_browser.py`.

The team is checked again by the server. No other view has the field; the decision stays visible to administrators only (`AssignmentExplanationAccessRegressionTest`).
  5. **Dialog**: "Assign" / "Reassign" on the lead's unassigned list, on the monitor's cards and on every card of the Technician tab's team mode. ## ADR-046: Per-Address Rate Limiting of the Sign-In Endpoints (authentication hardening, Phase S2)
- **Status**: Phase S2 accepted and implemented 2026-11-19. Cross-references ADR-033 (the per-account lockout stays unchanged).
- **Context**: The account lockout (ADR-033) counts failures per account. It stops a guess run on one account, but an attacker can lock a known victim out every 15 minutes with five bad passwords, and slow guessing spread over many accounts is not limited at all. Registration can be called without limit.
- **Decision**:
  1. **Per client address and per route.** `RateLimitFilter` limits `POST` on `/api/auth/login`, `/register`, `/refresh` and `/mfa/verify` (the last two are configured now and used from S3 and S4). The key is `<route>:<address>`, so a burst of registrations does not use up the login allowance.
  2. **Token bucket, not fixed window.** `InMemoryRateLimiter` (port `RateLimiter`, domain) gives each key `capacity` attempts at once and refills continuously at `capacity` per `window`. A fixed window lets a client send `2 x capacity` attempts across a window boundary and resets in one step; the bucket has no boundary and gives an exact, honest `Retry-After` (time until one token is back, rounded up to whole seconds).
  3. **Bounded in-memory state.** A `ConcurrentHashMap` updated only inside `compute` (race-free per key). Above `max-tracked-clients` (10,000) the buckets that have refilled completely are dropped (they answer like a missing key, so nothing is lost), then the least recently used until 90 % of the limit remains. Pinned with 50,000 different keys and 200 threads on one key.
  4. **Proxy rule.** `ClientIpResolver` uses the TCP peer address. With `trusted-proxy-hops = N > 0` it uses the N-th entry from the **right** of `X-Forwarded-For` (each trusted proxy appends the address it saw; entries on the left were written by the client). With 0, the header is ignored, because any client can forge it and would otherwise get a fresh bucket per attempt. A missing, too short or malformed header falls back to the peer.
  5. **A refusal never reaches the login.** The filter runs before `JwtAuthenticationFilter` and answers HTTP 429 `ERR_RATE_LIMITED` (standard error body, `Retry-After`), so a refused request can neither guess a password nor count as a failed login or lock an account (pinned over HTTP). A Micrometer counter `iitsm.security.rate_limited` counts refusals (read as administrator, like `NotificationMetrics`).
  6. **Real time, not the simulation clock (rule R1).** The filter reads the `wallClock` bean (`SecurityTimeConfig`, `Clock.systemUTC()`); the simulation `AdjustableClock` became `@Primary`, so every existing injection keeps it. Advancing the simulation by years must not refill or empty a limit.
  7. **Off in dev, demo and test, on in prod.** `iitsm.security.rate-limit.enabled` is `${RATE_LIMIT_ENABLED:false}`, `${RATE_LIMIT_ENABLED:true}` in prod. The demo persona switcher and the 30-simultaneous-logins live check from one address would trip it. Defaults: login 10 per 60 s, register 5 per 600 s, refresh 60 per 60 s, MFA 10 per 60 s. A non-positive value stops the start-up naming the property.
  8. **The filter is built by hand.** `SecurityConfig.filterChain` creates it with `new` and adds it before `JwtAuthenticationFilter`. As a `@Component` or `@Bean`, Spring Boot would also register it in the servlet container's own chain, so it could run twice or outside Spring Security.
  9. **Front end.** The sign-in and registration forms read `Retry-After` and show "Too many attempts from this network. Try again in N seconds." (the old text on a 429 claimed a lock, which was wrong).
- **Alternatives considered**:
  1. *Fixed window per address*: burst of 2x at the boundary, a coarse `Retry-After`.
  2. *Bucket4j or another library*: a dependency for about 100 lines, and the memory bound would be the library's.
  3. *Limit per account instead of per address*: the account lockout already does that; it is the thing an attacker abuses.
  4. *Always trust `X-Forwarded-For`*: trivially bypassed.
  5. *Spring bean filter*: double registration (point 8).
  6. *A shared store (database or Redis)*: more moving parts than the course project needs; recorded as the known limit below.
- **Consequences**: a client that fails to sign in more than 10 times a minute from one address sees 429 and a wait time, and never locks anyone by that route. Known limits: the state is per application instance and lost on restart (several instances multiply the allowance); many users behind one address (a company NAT with no trusted proxy configured) share one bucket, so the login capacity of 10 per minute may be low for them (a deployment sets `RATE_LIMIT_TRUSTED_PROXY_HOPS` and the capacity); an attacker with many addresses is not limited by this control; the 429 body is not subject to the security layer's `errorCode` shape inconsistency (it uses the standard `code`).

## ADR-047: Sessions With a Short Access Token and a Rotating Refresh Token (authentication hardening, Phase S3)
- **Status**: Phase S3 accepted and implemented 2026-11-19. Cross-references ADR-033 (lockout, login without a transaction) and ADR-046 (the `refresh` rate limit is configured there).
- **Context**: Signing out only deleted the token in the browser; a copied token worked until it expired (2 hours in dev and demo). Prod tokens lived 15 minutes with no renewal, so users were signed out every 15 minutes. The token-version revocation existed but nothing triggered it.
- **Decision**:
  1. **Access token 15 minutes in every profile** (the 7,200,000 ms overrides in dev and demo were removed; `JWT_EXPIRATION_MS` still overrides). Silent renewal replaces the long lifetime. The test profile uses 15 minutes too (`RefreshConfigContractTest` pins every profile at 15 minutes or less).
  2. **Refresh token**: 32 random bytes from `SecureRandom`, Base64url (43 characters). Only its SHA-256 hex is stored (`refresh_tokens.token_hash`, unique). A fast hash is enough because the input is random, not a password. TTL 8 hours (`iitsm.security.refresh.ttl-hours`).
  3. **The 8 hours are absolute**: the token a refresh issues inherits the expiry of the one it replaces, so using the session does not extend it and a stolen token cannot be kept alive for ever by rotating it. Alternative: sliding expiry (a longer working day, an unbounded stolen session).
  4. **Rotation on every refresh, reuse revokes the family.** The tokens of one sign-in form a family (`family_id`, also the `sid` claim of its access tokens). A refresh claims the presented token with one conditional `UPDATE ... WHERE revoked_at IS NULL` (`claimForRotation`), then stores the next token. Presenting a token that was already rotated (`RefreshTokenRotation.REUSED`) revokes the whole family. **No grace window**: sessions live per browser tab in `sessionStorage`, so only a lost response can replay a token, and that safely ends the session (the user signs in again). Two simultaneous refreshes of one token end as one 200 and one 401 (pinned).
  5. **Immediate revocation.** `JwtAuthenticationFilter` asks `RefreshTokenRepository.isFamilyActive(sid)` on every request and answers 401 "Session revoked or expired" when the family is dead (sign-out, replay, end of the 8 hours). A token without `sid` (issued through `TokenPort.generateToken(User)` by tests or old code) is still accepted until it expires. Cost: one indexed query per authenticated request (the user is already loaded per request).
  6. **Account checks at refresh.** `refresh_tokens.token_version` stores the user's `tokenVersion` at issue; a refresh fails and revokes the family when the user is inactive, currently locked (judged with the shared clock, because the lock's expiry was set with it, ADR-033) or the version changed.
  7. **Endpoints**: `POST /api/auth/refresh`, `POST /api/auth/logout` (always 204 for a well-formed body, idempotent; an oversized value is 400), `POST /api/auth/logout-all` (authenticated, matcher before the `/api/auth/**` permit rule; revokes every family and raises the user's token version, which also ends tokens without `sid`). Every failure of `refresh` is one `InvalidRefreshTokenException` (401 `ERR_INVALID_REFRESH_TOKEN`, one generic message), so a client cannot tell unknown, expired, revoked and replayed tokens apart.
  8. **Session cap**: `max-sessions-per-user` (10); a sign-in above it revokes the user's least recently refreshed session.
  9. **Real time (rule R1)**: `JwtTokenProvider`, `RefreshTokenService`, the filter and the cleanup scheduler use the `wallClock` bean; the simulation clock cannot expire or extend a session (`SimulationClockDoesNotExpireSessionsRegressionTest`: a simulated day and five simulated years). The sign-in still does not run in a transaction (`verifyCredentials`, then a short transaction for the session; `LoginTransactionContractTest`).
  10. **Front end**: `authorizedFetch` repeats a 401 request once after a renewal. The renewal is single-flight (`refreshSession` shares one promise, so concurrent calls send one refresh request; without it the second would replay the used token and end the session, shown by the browser check). `apiCall` starts its write guard once per call, not per attempt. Sign-out sends `POST /api/auth/logout` with `keepalive` before clearing the state. The SPA has no SSE client (it polls), so there is no stream to reconnect.
  11. **The refresh token stays in `sessionStorage`** like the access token. An HttpOnly cookie would hide it from scripts but is shared by all tabs of the browser, so tab B's user could be refreshed into tab A's session; the app keeps one session per tab on purpose (different users in different tabs during a demonstration), and a cookie would need CSRF protection that the bearer-header design avoids (ADR-046 and `docs/security-considerations.md`).
  12. **Audit**: the `SECURITY_AUDIT` logger records LOGIN_SUCCESS, REFRESH_ROTATED, REFRESH_REUSE_DETECTED, LOGOUT and LOGOUT_ALL with user and session ids only; no token, hash or password is ever logged (`SecurityLogHygieneTest`).
  13. **Cleanup**: `RefreshTokenCleanupScheduler` deletes tokens that expired more than 7 days ago (kept a while so that a replay of an old token is still recognised).
- **Alternatives considered**:
  1. *Keep long-lived access tokens and a denylist of revoked token ids*: a growing list to check on every request, and the tokens still live for hours.
  2. *Stateful server sessions*: gives up the stateless design of the whole API.
  3. *A grace window for the previous refresh token*: it tolerates a lost response but also lets a thief who replays within the window keep a session.
  4. *An HttpOnly cookie for the refresh token*: see point 11.
  5. *Store the refresh token encrypted instead of hashed*: the server never needs the token back, so a hash is strictly safer.
- **Consequences**: a copied token stops working at sign-out, on a replay and at "sign out everywhere", and anyway 15 minutes after its last renewal. Known limits: one extra indexed query per authenticated request; the claim, new token and link are one transaction but a failure between them ends that session (the user signs in again); a lost refresh response signs the user out (no grace window, by design); the `sessionStorage` tokens are still readable by a script that runs on the page (mitigated by the strict CSP and escaping, not removed); sessions are not listed or revoked one by one from a screen; the 8-hour absolute limit signs a user out in the middle of a longer working day.

## ADR-048: Optional TOTP Two-Step Verification for Administrators (authentication hardening, Phase S4)
- **Status**: Phase S4 accepted and implemented 2026-11-19. Cross-references ADR-033 (the lockout that wrong codes count toward), ADR-046 (the `mfa` rate limit on `POST /api/auth/mfa/verify`, configured there) and ADR-047 (the session issued after the second step).
- **Context**: A stolen or guessed administrator password gave full control of the system: administrators see every ticket, change priorities, reassign work and run the simulation. Passwords, lockout and rate limits slow guessing but do not stop a correct password that leaked.
- **Decision**:
  1. **Time-based one-time passwords, RFC 6238**: HMAC-SHA-1, 6 digits, 30-second steps, which is what every authenticator app implements. Written in pure Java on `javax.crypto.Mac` (`TotpGenerator`, `Base32`, `RecoveryCodes` in `domain/security`), checked against the RFC 6238 Appendix B vectors and the RFC 4648 Base32 vectors. The secret is 20 random bytes (160 bits).
  2. **Only administrators may enrol** (`User.canEnrollMfa()`, true only in `Administrator`; the URL rules answer 403 first, the domain refuses again). Optional: nothing forces an administrator to enrol (see alternatives).
  3. **Verification window of +/-1 step** (`iitsm.security.mfa.window-steps`, for phone clock drift), compared in constant time over every candidate step. **No replay**: the newest accepted step is stored (`users.mfa_last_step`), and a code for that step or an older one is refused. The step comes from the real wall clock (rule R1), never the simulation clock.
  4. **The secret is stored encrypted**: AES-256-GCM, a fresh random 12-byte nonce per encryption, the user id bound as associated data (a stored secret copied into another user's row does not decrypt), key `iitsm.security.mfa.encryption-key` (Base64 of 32 bytes). The key is checked when the bean is created: a missing or malformed key stops the start-up, and the prod profile has **no default** (`MFA_ENCRYPTION_KEY` must be set, like `JWT_SECRET`). The dev and demo profiles carry a committed development key (a known limit, same as the JWT secret). The secret is returned once, by `POST /api/auth/mfa/setup`; no other response carries it.
  5. **Two-step sign-in**: the password step of an account with two-step verification returns `mfaRequired` and a challenge token (`purpose=mfa`, 5 minutes, wall clock) and **no access token and no refresh token**. `POST /api/auth/mfa/verify {mfaToken, code}` then starts the session of ADR-047. The challenge is not a credential: `JwtAuthenticationFilter` answers 401 for any `purpose=mfa` token used as a Bearer token, and `parseMfaChallenge` accepts only tokens with that purpose, so an access token is never a challenge.
  6. **Recovery codes**: 8 codes of 10 Base32 characters (50 bits), returned once at enabling, stored as BCrypt hashes (`mfa_recovery_codes`), each usable once (a conditional single-statement update, so two simultaneous sign-ins cannot both use one). A recovery code is accepted wherever a one-time code is, typed in any case with or without hyphens.
  7. **Wrong codes count toward the existing lockout** (5 failures, 15 minutes). The password step does **not** clear the failure count of an account with two-step verification; only a correct second step does. Otherwise an attacker who knows the password could reset the count before every guess of the code (found while designing the tests: pinned by `passwordStepDoesNotResetTheCount`). A locked, deactivated, unknown or unenrolled account all give the same refusal as a wrong code (`ERR_INVALID_MFA_CODE`, one message). The `mfa` rate limit of ADR-046 applies to the verify endpoint.
  8. **Turning it off** (`POST /api/auth/mfa/disable`): the password and a valid code (or recovery code) are both required, so a stolen access token alone cannot remove the protection. **Reset by another administrator** (`POST /api/admin/users/{id}/mfa/reset`, for a lost phone and no recovery codes): switches it off, deletes the codes and ends every session of the target; resetting oneself is refused (400), a target without it is 409. Every enable, disable, reset, refused code and recovery-code use is written to the `SECURITY_AUDIT` log (ids only; `SecurityLogHygieneTest` proves no secret, code or challenge is logged).
  9. **No QR image.** The dialog shows the secret and the `otpauth://` link as text: a QR image needs a library or an external service, and the project allows neither a CDN nor extra front-end dependencies. Authenticator apps accept the key typed by hand.
  10. **Front end** (`app.js` section 18, asset version 4.8): a second step on the sign-in card (`#form-mfa`), an administrators-only Security button, and a Security dialog drawn through the shared `openModal` (Tab trap, focus return) with status, setup, confirmation, one-time recovery-code list, disable and "Sign out everywhere". The dialog tells a wrong code or password (`code` in the body) from an ended session (`errorCode` of the security layer) so a wrong code never signs the user out; sign-out closes the dialog, because it can show a secret.
  11. **Migration V13**: `users.mfa_enabled` (not null, default false), `mfa_secret`, `mfa_last_step`; `mfa_recovery_codes` (cascade on the user).
- **Alternatives considered**:
  1. *A TOTP library* (for example a Java OTP package): a dependency for about 60 lines, and the RFC vectors give the same assurance.
  2. *A QR image* (library or CDN): see point 9.
  3. *Force enrolment of every administrator*: locks out the demonstration accounts and every existing deployment at once, with no recovery path built; recorded as the next step.
  4. *Two-step verification for every role*: the work lies with administrators, and the lockout and rate limits already protect the rest; not requested.
  5. *SMS or e-mail codes*: the system has no trusted delivery channel for secrets (the SMS channel is a simulator).
  6. *Hash the secret instead of encrypting it*: the server needs the secret back to compute codes.
  7. *Clear the failure count at the password step*: see point 7.
- **Consequences**: a leaked administrator password alone no longer signs in, once the administrator has enrolled. Known limits: optional and for administrators only (no forced enrolment, no MFA for other roles); no QR image; the committed development key in dev and demo (anyone with the repository can decrypt a development database's secrets; prod has none); a code is accepted once per account, so two real sign-ins within one 30-second step need the next step's code (the second one waits up to 30 seconds, or uses a recovery code); two simultaneous verifications with the same code can both pass the read before either writes, and end as one success and one optimistic-lock conflict (HTTP 409) rather than two sessions (not pinned by a test); the challenge is not single-use (it expires after 5 minutes; each code is); the 8 BCrypt checks of a recovery-code attempt hold one database connection for about half a second under the `mfa` rate limit; SHA-1 is what authenticator apps use (it is not weak in HMAC form); the verification window accepts a code up to 30 seconds old or new.

## ADR-049: Complete Admin Search Filters (Status, SLA Status, Service, Technician, Dates)
- **Status**: Accepted (2026-11-20)
- **Context**: The course specification asks that incidents can be filtered by Incident ID, Date, Status, Priority, Category, Service, Technician and SLA status. `GET /api/admin/incidents` accepted one status, priority and category sets (ADR-012), a service id, an assignee id, a reporter id, a text query (which matches the ticket id) and a creation window, but had no SLA-status filter; the Admin Command Centre sent only the text, category and priority; no endpoint listed the IT services for a dropdown; a creation window whose start lay after its end was accepted silently and returned nothing.
- **Decision**:
  1. **D1, multi-value status**: `status` binds to `Set<IncidentStatus>` (repeated parameters, OR-ed like priority and category). `IncidentSpecifications.hasStatusIn`; `hasStatus` stays for its tests. A single value still works; an unknown value stays 400 `ERR_INVALID_PARAMETER` (ADR-027).
  2. **D2, SLA status**: new `slaStatus` parameter (`Set<SlaStatus>`, OR-ed) on the **stored** `sla_trackers.status` column through an inner join (`IncidentSpecifications.hasSlaStatusIn`). A ticket without a tracker never matches a non-empty SLA filter. The value is the one written at the last SLA evaluation (the scan, or an action that announces its transition: acknowledge, resolve, override), so a ticket that crossed a threshold since the last scan is found under its previous state for up to one scan interval (`iitsm.sla.scan-interval-ms`). A paused (`PENDING_INFO`) ticket keeps the status it had when it was paused (ADR-019). The tracker is one-to-one, so the join never duplicates a row (pinned by a test; no `distinct`).
  3. **D3, date range**: `SearchService` refuses `fromDate` after `toDate` with `ValidationException("fromDate", ...)`, HTTP 400 `ERR_VALIDATION_FAILED` (the field is named in the message; the handler's `fieldErrors` stay empty, as for every domain validation error). Equal dates and an open end are allowed. The web app also stops a reversed range before sending.
  4. **D4**: service and technician stay single-select dropdowns (the parameters are single values).
  5. **D5**: new read-only `GET /api/admin/services` (`ServiceCatalogService.listServices`, sorted by name ignoring case, then id; `ItServiceOptionDto` = id, name, criticality; administrators only by the controller's class rule). The technician dropdown reads the existing `GET /api/admin/technicians`.
  6. **D6**: the admin table has an **SLA** column (badge of `slaTracker.status`, "--" without a tracker), so the result of the SLA filter is visible; 9 columns.
  7. **Web app**: status and SLA multi-selects (same component as ADR-012), service and technician dropdowns (filled once per sign-in with `Promise.allSettled`, option labels as text, forgotten on sign-out, retried when a list failed), "Created from" / "Created to" date inputs (a chosen day is sent as local 00:00:00.000 to 23:59:59.999, as ISO instants), a Clear button (empties every control, searches once). The Filter button stays the trigger (ADR-012). Asset version 4.9.
  8. **D7**: this record is ADR-049.
- **Alternatives considered**:
  1. *Filter in the browser*: the list is already fetched whole, but it would make the API and the screen disagree, move logic into the client and not scale; the API is the contract the tests and other clients use.
  2. *Derive the SLA status in SQL from the deadlines and the clock*: always current, but it duplicates `SlaTracker.evaluateStatus` (pause, credit, response breach, ADR-019 to ADR-031) in a query and would drift from the domain rules; the stored status is what every other screen shows.
  3. *Evaluate every candidate ticket's tracker in Java before filtering*: correct but loads every ticket for each search.
  4. *Multi-select service and technician*: no backend support and not asked for.
  5. *A general IllegalArgumentException handler for the date check*: forbidden by ADR-027.
- **Reason**: The Specification pattern takes the two new filters without touching the existing ones; the stored SLA status keeps one source of truth; converting the date mistake at its source keeps errors 4xx with stable codes.
- **Consequences**: Every specified filter is available in the API and on the screen. Known limits: the SLA status lags up to one scan interval; no "unassigned" technician choice (the technician filter matches an assignee id only); service and technician are single-select; the reporter filter stays API-only; the dropdown lists are read once per sign-in (a technician or service added later appears after the next sign-in); the selection is not remembered across reload or sign-out (as ADR-012).

Known limits: the open row is not remembered across a page reload; "time left" can disagree with a simulated server clock for non-administrators (the status does not); the table scrolls sideways inside its card below 760 px; the card view of long descriptions is the row's detail, so the table shows no description; a technician with many tickets sees them all in one table (no paging, as before).

## ADR-052: Everyday Tickets Must Be Assigned Automatically (measurement first; classifier fixes in later phases)
- **Status**: Accepted and implemented (2026-11-21), phases 1 to 6; the 90 % target of decision 4 was **not** reached (88.6 %), see Phase 6 below and `docs/everyday-ticket-classification-fix-summary.md`.
- **Context**: The product owner reported that tickets were not assigned automatically when an employee raised them. A live run on 2026-11-21 (26 plain-language tickets through the employee API; 25 accepted, "Help" refused as a title under 5 characters) confirmed it for 8 of the 25 tickets (32 %), all clear IT faults ("Printer not working", "Internet is down", "Account locked", "Email not sending", "Need software installed", "Teams calls dropping", ...). The assignment code was not at fault: intake, `TicketDispatchService.dispatchOne`, routing and capacity all worked, and `AutoAssignmentRegressionTest` passes. Every unassigned ticket had a classification confidence below the 0.60 gate (ADR-009), so it was flagged `needsTriage`, left in the administrator's triage queue and deliberately skipped by the dispatcher. The causes, read from the classifier's own rationale: (a) the keyword lexicon (`KeywordClassifier`) lacks everyday words (printer, jam, internet, unreachable, email, outbox, webcam, virus, vm) and excludes "locked" as a generic word, and a ticket with no lexicon term is always capped at 0.55, however confident Naive Bayes is; (b) `CompositeClassifier` caps a ticket whose two or more keywords of one category are contradicted by an uncorroborated Naive Bayes answer, and in that case labels the triage ticket with the Naive Bayes guess; (c) the Naive Bayes corpus (`sim/corpus.csv`) has almost no such examples, so it guesses AUTHENTICATION for a printer jam and SECURITY for a webcam. The measurement also found two clear tickets routed **confidently to the wrong team**: "Wifi not working" to the Service Desk (one NETWORK and one HARDWARE keyword tie, Naive Bayes breaks the tie toward HARDWARE) and "AWS console access" to Security.
- **Decision**:
  1. **Measure before changing anything.** A labelled set of 42 everyday tickets (`src/test/resources/classification/everyday_tickets.tsv`: the 25 live tickets, the refused live ticket with a longer title, 10 clear control tickets so every category is covered, 1 mixed security control and 5 vague or non-IT controls; 35 clear tickets and 7 that must stay with a person) is the yardstick for the fix phases. Labels are written from the text, not from the classifier's answers.
  2. **Success is measured by team**, because the classified category only matters through the team it selects (ADR-036): SOFTWARE and APPLICATION, DATABASE and STORAGE, SECURITY and AUTHENTICATION share a team. Five verdicts: auto-routed to the right team (goal), missed to triage (the reported problem), auto-routed to a wrong team (the worst outcome), kept for a person (correct for TRIAGE labels), leaked (a TRIAGE-labelled ticket auto-routed).
  3. **Two instruments, one data file.** `EverydayTicketBenchmarkTest` (tag `benchmark`, same Spring context and `benchmarkdb` as `ClassificationBenchmarkTest`) classifies and routes every ticket with the production beans and writes `target/benchmarks/everyday-tickets.txt`; `scripts/live-checks/everyday_tickets_check.py` raises the same tickets through the running application and checks that every unassigned one is in the administrator's triage queue. They agreed ticket for ticket on 2026-11-21.
  4. **Ratchet, then target.** Until the fix phases land the benchmark asserts only that no verdict count is worse than the Phase 1 baseline (right team 21 of 35 clear tickets, wrong team 2, leaked 0), so the build stays green; each fix phase raises the floor; Phase 6 asserts the target: at least 90 % of the clear tickets auto-routed to the right team, none to a wrong team, none leaked, and the existing D14 budget (ADR-034) and routing target (ADR-036) unchanged.
  5. **The 0.60 gate stays.** The fix belongs in the evidence (lexicon, fusion rules, corpus), not in the threshold.
- **Alternatives considered**:
  1. *Lower the gate to 0.50*: assigns more tickets at once but also the vague and non-IT ones (most of them score exactly 0.55 today) and every wrong Naive Bayes guess ("Printer jammed" as AUTHENTICATION, "Webcam not detected" as SECURITY).
  2. *Let the dispatcher assign triage tickets after a timeout*: hides the symptom and routes the ticket by the same wrong guess.
  3. *Measure by exact category*: penalises outcomes that reach the right people (a payment application ticket classified SOFTWARE goes to the same team as APPLICATION).
  4. *Fix first, measure with the existing held-out set only*: the held-out tickets are long, keyword-rich and synthetic; they do not contain the short reports that fail in practice (33 of 36 already pass).
- **Reason**: The reported problem is real but lies in classification, and changing the classifier without a yardstick for short everyday text risks trading missed tickets for wrongly routed ones, which is worse. The measurement makes both visible.
- **Consequences**: Phase 1 adds tests and a script only; no production code changes. The baseline (2026-11-21): 21 of 35 clear tickets (60.0 %) auto-routed to the right team, 12 left in triage, 2 routed to a wrong team, 7 of 7 vague, non-IT or mixed tickets kept for a person, 0 leaked. Existing figures unchanged: held-out 33 of 36, 3 in triage, 31 of 33 to the right team; audit examples 12 of 12. Known limits of the set: 42 tickets written by one person in English, no typos or very long tickets, one company's teams.
- **Phase 2 (2026-11-21): lexicon gaps.** `KeywordClassifier` gained everyday terms (HARDWARE printer, print, toner, jam, scanner, webcam, camera, charger, usb; NETWORK internet, unreachable, connectivity, proxy; SOFTWARE email, mail, inbox, outbox, zoom, webex; AUTHENTICATION unlock; SECURITY virus, antivirus; CLOUD vm) and **pair terms** (`PAIR_TERMS`, record `PairTerm`): two ordinary words that count as one term only together, `account`+`locked` and `account`+`disabled` for AUTHENTICATION, so "Account locked" is evidence while a locked drawer (A02) and a bank account are not. A pair in the title is a title match (0.55); split over title and description it is a weak match (0.50). Left out on purpose: "account" alone (a bank account in a fintech), "server", "call", "console" (an Okta admin console would tie CLOUD with AUTHENTICATION); "locked out" cannot be a pair because "out" is a stop word. The duplicate vocabulary is unchanged (ADR-035). Alternatives: lifting "locked" out of `GENERIC_WORDS` (brings back the A02 drawer defect of ADR-034); bigrams of adjacent tokens (miss "my account got locked", where a word stands between). Result: everyday clear tickets auto-routed to the right team 21 -> **24 of 35** (E01 printer, E13 server unreachable, E23 account locked); wrong team 2, leaked 0, held-out, audit, routing and duplicate figures unchanged. Five more tickets now carry two or more keywords of one category (E02, E18, E19, E27, E33) but stay capped by the `CompositeClassifier` rule for an uncorroborated Naive Bayes answer, which is Phase 3.
- **Phase 3 (2026-11-21): fusion rules** (`CompositeClassifier`, `ClassificationResult`). (a) *Decisive keywords*: two or more distinct terms of one category, more than any other category (`leadsAllOtherCategories`), stand against a Naive Bayes answer that no keyword supports; the ADR-034 cap remains for everything less decisive (Need software installed, Email not sending, Antivirus found a virus, Azure VM not starting are now auto-routed). (b) *Label of a capped ticket*: when the keywords name one category above a lone description word (confidence above 0.50) and no keyword supports the Naive Bayes category, the suggestion shown to the administrator is the keyword category, not the unsupported guess (Teams calls dropping was suggested as DATABASE). A lone description word does not relabel (`Round3RegressionTest.N2`: "Wi-Fi access points ... after a firmware update" must stay NETWORK). (c) *Title-led tie*: when the keywords tie and exactly one of the tied categories has a term in the title, Naive Bayes may not break the tie against the title; the ticket goes to a person with the title's category ("Wifi not working ... on my laptop" went to the Service Desk, confidently). (d) "virus" is a security indicator, so a ticket another category wins goes to a person. The fused result now carries the keyword support and the security flag (`withKeywordEvidence`). Measured on the everyday set: 24 -> **29 of 35** right team, wrong team 2 -> **0** (E11 now triage with NETWORK, E32 triage: the "unauthorized" word is a security indicator). Held-out routing 31/33 -> 32/34. Changed on purpose: two `CompositeClassifierTest` cases (they pinned the ADR-034 cap for two terms against an unsupported Naive Bayes answer) and the vague text of `DuplicateTriageGateRegressionTest` (its tickets now land in one category, so a longer shared sentence made them duplicates of each other). Alternatives: cap every disagreement (ADR-034 measured 7 of 36 held-out in triage); trusting Naive Bayes for a tie (the wifi defect).
- **Phase 4 (2026-11-21): corpus, tried and reverted.** 72 new training rows (8 per category: printer, e-mail, internet, lockout, Teams, antivirus, cloud console, ...) raised the tuning set 29 -> 31, but the rows are near-paraphrases of those tickets (leakage), the **validation set** (`everyday_validation.tsv`, 24 tickets written before the corpus was touched and never used for tuning) did not improve (13 of 19, E13 got worse), and the duplicate-detection recall fell from 54/87 to 52/87, the minimum, with no headroom (the TF-IDF vectoriser is trained on the same corpus). A change with no validated gain and a measured risk to another feature is not kept: `sim/corpus.csv` is unchanged. A corpus change needs its own held-out evidence; that is future work.
- **Phase 5 (2026-11-21): the matched IT service as evidence** (`ServiceCorroboration`, `IncidentIntakePipeline`). A capped ticket is lifted to exactly the gate when three things hold: a keyword supports the final category, the IT service the text matched (not the general one) is owned by the team that handles that category (`TicketRouter.owningTeamId(category, null)`), and there is no security indicator. A service match alone routes nothing and cannot change the category, so a loose service keyword ("connect", "customer", "other") is harmless. Fixes Report fails with database error (SVC-CORE-DB), Wifi not working (SVC-VPN, same team), Scanner on second floor broken (validation). Measured: tuning 29 -> **31 of 35** (with Phase 3), validation 13 -> **14 of 19**, wrong team 0 and 1 (V14, unchanged), leaked 0, held-out 33/36 met with 2 in triage, audit 12/12. This closes CLAUDE.md section 7 item 4 for tickets with a keyword; a ticket with a service match and no keyword still goes to triage. The pipeline gained the `TicketRouter` dependency. Alternative: put the service in the classifier (it would need the service list and the team table in the domain classifier, and the unit tests that build it).
- **Phase 6 (2026-11-21): result against the target.** Decision 4 asked for at least 90 % of the clear everyday tickets auto-routed to the right team. Reached: **31 of 35 = 88.6 %** on the tuning set and **14 of 19 = 73.7 %** on the validation set; 0 routed to a wrong team on the tuning set, 1 on the validation set (V14 "Lost my work laptop", a security matter classified HARDWARE with Naive Bayes at 1.00, the same as before the fix); 0 vague or non-IT tickets routed. The target was **not** met. The four tickets still in triage on the tuning set (Webcam not detected, Internet is down, Server unreachable, AWS console access) each have one keyword and a Naive Bayes answer that is wrong, weak or accompanied by a security word; routing them needs either a retrained model with its own held-out evidence (Phase 4 showed that the current corpus change does not generalise) or a looser gate, and the gate is not changed (decision 5). The benchmark floors are the measured values (right team 31 and 14, wrong team 0 and 1, leaked 0), so a regression fails the build. Remaining limits: 42 and 24 tickets by one author; the validation set was seen once for the Phase 4 decision and for the Phase 5 what-if, so it is no longer completely blind; a triage ticket is still silent (no alert to administrators; the employee sees NEW).


## ADR-053: Employee Tab Boxes Aligned on One Grid (CSS only, nothing inside the boxes changes)
- **Status**: Accepted and implemented (2026-11-21), phases 0 to 4; summary `docs/employee-layout-alignment-summary.md`.
- **Context**: The boxes of the Employee tab did not line up: the four KPI cards ended at x = 333, 679 and 1026 (1400 px wide) while the ticket column ended at 901 and the tracking box began at 922, the tracking box ended 108 px above the ticket column, the KPI cards were 14 px apart and everything else 21 px, and on a tablet the tracking box dropped below all the others. The product owner asked for the boxes to be arranged systematically, with parallel edges, in blocks of related features, and for **only the arrangement of the boxes to change, not the matter inside them**.
- **Decision**:
  1. **One grid.** The KPI row and the ticket area use the same four columns and the same gap (`--emp-gap`, 1.5rem, defined on `#console-employee`). The featured ticket and the ticket list (`.emp-main`) span columns 1 to 3, Live Tracking is column 4; the two columns have equal tops and bottoms (`align-items: stretch`; `.emp-main` is a flex column whose last card grows).
  2. **Narrow screens.** 1025 to 1199 px: tickets and tracking take two columns each (the tracking box would be only 234 to 277 px wide otherwise and its text wrapped badly). 1024 px and below: the boxes stack at full width with equal gaps; the KPI cards keep their own 2 x 2 and 1 x 4 arrangement.
  3. **Scope.** Only the Employee block of `styles.css` changes (about 16 lines). No HTML, no JavaScript, no padding, text, icon, colour or button; the banner, the sub-navigation buttons and the report form keep their contents and their full-width boxes. The asset version becomes `?v=5.2`.
- **Alternatives considered**:
  1. *Wrap the contents in four block elements (HTML)*: the same result is reached with the existing elements, and wrappers would have touched `index.html` and every test that fingerprints it.
  2. *Move the sub-navigation buttons into the privacy banner, give all cards the same padding, put the report form beside the tickets*: rejected by the instruction not to change the matter inside the boxes.
  3. *A 12-column grid*: no benefit; the KPI row already has four columns, and tickets 3 + tracking 1 (or 2 + 2) land exactly on its column lines.
  4. *Keep the old 2fr/1fr split and only equalise the gaps*: leaves the edges of the KPI row and the ticket area unrelated.
- **Reason**: Reusing the KPI row's four columns makes every box edge continue from one row to the next without adding elements, and keeps the change reviewable as one CSS block.
- **Consequences**: The tracking box and the ticket column end together, so a shorter tracking box has empty space at its bottom (a taller one stretches the ticket list box instead). `TechnicianPortalMarkupTest` fingerprints the whole of `styles.css` outside the Technician block, so its recorded hash was re-recorded (computed with the test's own rule: line endings normalised to LF, version numbers normalised; the rule first reproduced the old value on the committed file). The 13 markup tests that pin the asset version now expect `?v=5.2`. Verified in Microsoft Edge at 13 widths (39 scenarios, 0 failures) and by the 153 `*MarkupTest` classes; the full `mvn verify` was not re-run for this change. The 640 px sideways scroll of the page comes from the header's button row (outside the tab) and was left alone.
